# 自研引擎：三个决策（拍板结论）

> 日期 2026-10-27 · 对应《自研美颜引擎替换方案 v1》第 9 节
> 已在同日完成 M0 基线冻结（见 `06_离线验证/goldens/` 与 `goldens_legacy/`）

---

## 决策一：推理跑 CPU 还是 GPU

**结论：渲染走 GPU，推理先走 CPU（ONNX Runtime CPU/AVX2），硬件后端留接口后续切。**

### 依据（实测/源码记录）

| 环节 | 实测值 | 出处 |
|---|---|---|
| SDK 渲染（稳态） | 3.7 ~ 5.2 ms/帧（640×394） | 本次 M0 采集，78 组 |
| SDK 渲染（1074×604） | 5.0 ms/帧 | `nama_engine.cpp` 注释 |
| fuai 皮肤分割推理 | 2.55 ms/帧（关关键点后） | `nama_region.cpp` 注释，**本来就是 CPU 上的 tflite** |
| 全分辨率美白掩码 | 38 ms/帧（1080p）→ 已改 1/4 分辨率规避 | `nama_engine.cpp` 注释 |

### 为什么这么分

1. **推理现在就是 CPU**。fuai 内部跑的是 tflite CPU 推理（2.55 ms/帧），换成 ONNX Runtime CPU
   不会引入新瓶颈；而 ORT 有 CUDA EP，将来想切 GPU 推理只需换 Execution Provider，业务代码不动。
2. **真正的大头在回读**。当前架构是「GPU 纹理 → stagesurface 回读 → CPU 全帧处理 → 上传」。
   回读是同步操作，加上 CPU 侧逐像素处理（美白掩码曾在 1080p 上吃到 38 ms/帧）。
   **只有把渲染搬到 GPU 才能去掉回读**，这是唯一可能拿到数量级提升的地方。
3. **改动面最小**：推理侧只换 DLL + 模型；渲染侧是新增的 `gs_effect` pass 图。

### 反面意见（记录以便复核）

若目标改为「最快拿到一个能跑的自研引擎」，CPU 全流程工作量最小 —— 现有
`applyRegionEffects` / `applySharpen` / 美白掩码三段 CPU 代码可直接复用。
代价是回读开销保留，1080p60 压力大，且等于放弃方案 v1 的 M1 目标。

### GPU 路线的已知风险

- OBS 的 `gs_*` 抽象层只暴露到 pixel shader + render target，**没有 compute shader**，
  多 pass 要用 `gs_texrender` 串联。
- 跨后端（D3D11 / OpenGL）行为差异、sRGB / linear 色彩空间处理都要单独验。
- 性能数字要等 M1 结束才有第一个测量点（方案 v1 原话：D13–14 才首次测性能）。

## 决策二：「训练工具算不算第三方」是什么意思

**这句话问的是：允许不允许用 PyTorch 训练模型。**

方案 v1 里「全自研」的边界是**运行时** —— 发出去的 `obs-nama-beauty.dll` 和数据目录里，
跑起来的每一行代码、每一字节权重和贴图都得是我们自己产出的。PyTorch 是**离线训练工具**，
只在你本机跑，产物（权重文件）是我们自己的产出，不进运行时。

| 选项 | 含义 | 成本 |
|---|---|---|
| **允许用 PyTorch 训练**（推荐） | 离线用 PyTorch / numpy 训练，只导出权重进运行时 | 0 额外成本 |
| 不允许 | 连训练框架也要自写，得自研反向传播 | 方案 v1 估 +4~6 周，且没有质量收益 |

许可上不用担心：PyTorch 是 **BSD-3-Clause** 许可，允许自由的商业使用、修改与分发。
（PyTorch 现由 Linux Foundation 下的 PyTorch Foundation 治理。）

**建议：允许。省 4~6 周，且不损失任何质量。**

## 决策三：保留老观感

**结论：提供「经典」预设，用 M0 基线拟合旧参数；默认走新版。**

### ⚠️ 先把对齐目标钉死

M0 采集时发现一个会影响对齐对象的事实：

**发布出去的产品里，fuai 语义皮肤掩码是不可用的。**
`04_依赖与SDK/installer-stage/` 与 `08_安装包/obs-nama-beauty.nsi`（`File /r "${SRCDIR}\sdk\*.*"`）
都只包含**加密的** `ai_face_processor_pc.bundle`，没有明文件。而 `nama_region.cpp` 需要
`ai_face_processor_pc_plain.bundle`（明文）才能初始化语义区域 —— 缺了就退回
v1.4 的 YCbCr 颜色判据。

所以基线采了**两套**，对齐对象不同：

| 基线目录 | 掩码状态 | 用途 |
|---|---|---|
| `06_离线验证/goldens_legacy/` | **off · 颜色启发式** | **对齐「老观感」用这一套**（产品实际行为） |
| `06_离线验证/goldens/` | on · fuai AI 分割 | 自研引擎的目标（完整能力），不要拿它对标老观感 |

### 拟合做法

1. 新引擎在同一批 golden 素材上跑同一套参数矩阵。
2. 逐档比对四个指标：细节保留率、Δ亮度、改动像素占比、掩码覆盖率。
3. 调新引擎参数使指标逼近 `goldens_legacy`；把拟合结果固化成「经典」预设的参数映射表
   （旧档位 → 新档位），**而不是让新引擎去复刻旧算法** —— 复刻算法会把自己重新绑死。
4. 默认走新版曲线，用户可在面板切「经典」。

- `goldens/`（region=on）：78 组 flat + 2 条 motion 序列，**复现率 78/78 逐字节一致**
- `goldens_legacy/`（region=off）：同矩阵采集中
- 采集工具：`06_离线验证/golden_capture.py` + `build_golden.bat` + `00_源码/golden_capture.cpp`

- flat 每组跑在**独立进程**（SDK 人脸跟踪是进程全局状态，同进程内先跑哪一档会影响后一档）；
  motion 组同进程连续调用
