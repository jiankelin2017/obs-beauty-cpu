## 2. 架构与数据流

### 2.1 两个 DLL，缺一不可

| 模块 | 产物 | 安装位置 | 作用 |
|---|---|---|---|
| 滤镜 | `obs-nama-beauty.dll` | `C:\Program Files\obs-studio\obs-plugins\64bit\` | 视频处理核心 |
| 菜单/面板 | `obs-nama-beauty-ui.dll` | `C:\ProgramData\obs-studio\plugins\obs-nama-beauty-ui\bin\64bit\` | 顶层菜单入口 + 参数面板 |

面板不是硬编码的：`build_form()` 会动态调用 `obs_source_properties()` 枚举滤镜属性，
**所以新增滑块不需要改 UI 模块、也不需要重编 UI DLL**（但改 UI 文案需要重编）。

### 2.2 每帧数据流

```
OBS 源纹理 → 拷回 CPU (buf_in)
   → NamaEngine::process()  ← NamaSDK (fuai.dll) 推理：人脸框/关键点/皮肤分割/头部掩码
   → 磨皮 + 美白 + 红润 + 锐化 + 五官立体 ...
   → 拷回 GPU (buf_out) → 画到目标纹理
```

### 2.3 三个源文件各自的职责

| 文件 | 职责 |
|---|---|
| `nama_region.cpp/.h` | **健康守卫**。包住 fuai 的裸调用（SEH + VEH），统计 `inferCnt`、`cov`；推理失败时按 `failStreak_` 决定是沿用旧掩码还是彻底放弃 |
| `nama_engine.cpp/.h` | **图像管线**。磨皮混合、细节层/中频层分离、美白、锐化、参数下发到 SDK |
| `nama_log.cpp/.h` | 引擎日志桥接进 OBS 日志 |
| `obs-nama-beauty.cpp` | OBS 滤镜插件本体：参数定义、属性 UI、渲染回调 |
| `obs-nama-beauty-ui.cpp` | Qt 顶层菜单 + 面板 |

### 2.4 当前参数表（`obs-nama-beauty.cpp` 的 `g_params[]`）

| key | 中文 | 默认 | 备注 |
|---|---|---|---|
| `blur_level` | 磨皮 | 20 | 滑块 0–100，常用 50 |
| `clarity` | 清晰 | 0 | **3.0.16 起真正下发到 SDK**（3.0.2~3.0.15 被 `if (i == P_CLARITY) continue;` 屏蔽，只做 CPU 中频增益）。实测纯增益：细节 +11.1%、立体感效果量 +107%、背景不动 |
| `color_level` | 美白 | 0 | 3.0.9 做过重标定 |
| `red_level` | 红润 | 0 | |
| `sharpen` | 锐化 | 0 | 只作用于掩码内 |
| `global_sharpen` | 全局锐化 | 0 | 3.0.13 新增；**0 时背景逐字节不变** |
| `face_threed` | 五官立体 | 0 | |
| `eye_bright` | 亮眼 | 0 | |
| `remove_pouch_strength` | 去黑眼圈 | 0 | |
| `remove_nasolabial_folds_strength` | 去法令纹 | 0 | |
| `delspot_level` | 祛斑痘 | 0 | **3.0.16 新增**。SDK 侧生效（效果量 +9.4%），但帧间闪动 +55.8%，故默认关；0~1 与 0~50 输出相同（SDK 内部 clamp），给 0~1 即可 |
| `blur_type` | 磨皮算法 | 1 | 1=双边滤波（最强·推荐）/ 0=高斯 / 2=弱磨皮；3、4 已从列表移除但 SDK 仍接受 |
| `skin_detect` | 精准美肤 | — | bool，只磨皮肤 |

> 改枚举或改表要同步：`NAMA_NPARAM == P_COUNT` 是编译期约束（`static_assert`），改动会直接报错，不会静默错位。

### 2.5 已确认对 SDK **无效**的参数（别浪费时间再试）

`heavy_blur`（0~5、0~50）、`clear_smooth`、`fine_smooth`、`balance_smooth`、`hazy_smooth`（0/1 与 50）
—— 共 14 组实验，输出与基线**逐位相同**。已用「阳性对照（`blur_type=2` 有效）」排除注入通道故障，
并在升级到 `face_beautification_v2` 道具（即第三方日志里那个道具名）后**复测，依然无效**。
结论：第三方的「磨皮模式四档」不是 NamaSDK 参数，是它自己的后处理。

## 3. 我们的方法

### 3.1 逆向方法（OBS美颜摄像头 / fuai.dll）

- 工具：**Ghidra 12.1.4**，目标 `fuai.dll`（`C:\Program Files\Common Files\OFX\Plugins\NamaBeauty.ofx.bundle\Contents\Win64\fuai.dll`，
  sha256 `4cc73522254271911f9b544719809fec6748eb4a9b7770f4a8da25982b83ddc6`）。
- 产物形态：反编译伪 C（`.c`）+ Ghidra 证据包（`.json`，含地址与调用关系）。
- 已逆向的四类（在 `03_逆向资料\`）：**人脸框** `FUAI_FaceProcessorSetFaceRect`、
  **关键点** `FUAI_FaceProcessorGetLandmarksFromResult`、**头部掩码** `FUAI_FaceProcessorGetHeadMaskFromResult`、
  **皮肤分割** `FUAI_FaceProcessorGetSkinSegResult`。
- **fuai 是闭源 DLL，没有 PDB**，函数签名靠伪 C + 字符串 + 导出表交叉验证。不要臆断签名，
  以 `03_逆向资料\` 里的证据包为准。

### 3.2 评测方法（离线、可复现）

不靠肉眼，靠三个数值指标。同一输入：**磨皮 50、60 帧、脸内 88811 px**。

| 指标 | 定义 | 怎么读 |
|---|---|---|
| 脸内细节 | `std(Y - 3×3 box/9)`，只在人脸掩码内 | **越高越有纹理**（磨皮过度会掉） |
| 帧间闪动 | 脸内相邻帧 `mean\|ΔY\|` | **越低越稳**（高了会看到颗粒沸腾/屏闪） |
| 纹理保留率 | 处理后细节 / 原图细节 | 对标用的综合指标 |

评测入口在 `06_离线验证\`（原 `C:\nama_e2e` 全量副本）：

- `nz_probe_dlldir.py` —— 主探针。它会 `os.add_dll_directory()` 加载完整插件 DLL
  （直接 `ctypes` 加载会报缺 `obs.dll`，必须加这句）。
- `ab_batch.py` / `exp_batch*.py` —— 批量跑对比实验。
- `cmp4.py` / `cmp4b.py` / `cmp_308.py` / `cmp_309.py` —— 各版本两两比对。
- `build_test_manual.bat` —— 编一个只含引擎的测试 DLL（绕开 OBS 依赖）用于离线跑分。

> 闪动统计有个历史 bug：**用 2D mask 去索引 1D 数组**。正确写法是 `inner.ravel()`。别再踩。

### 3.3 构建方法（重要：环境有坑）

沙箱会拦 `reg.exe`，所以 **`vcvars64.bat` 跑不起来**。必须用手动环境脚本：

```
01_构建\build_manual.bat        -> obs-nama-beauty.dll      (滤镜)
01_构建\build-ui_manual.bat     -> obs-nama-beauty-ui.dll   (菜单/面板，需 Qt 6.8.3 在 C:\Qt)
```

依赖：MSVC 14.51.36231、Windows SDK 10.0.26100.0；UI 还需 `/Zc:__cplusplus /permissive- /utf-8`。

### 3.4 装机方法

1. **先关 OBS**（DLL 被占用会失败，脚本有预检）。
2. 双击 `install_nama_317.bat`。未提权时它会自己弹一次 UAC，点「是」。
3. 脚本流程：预检 `obs64.exe` → 带时间戳备份 → 临时文件 + 原子改名 → 校验 size 与 md5。
   两个模块一次装完。日志同目录下的 `install_317.log`；回滚是 `rollback_nama_317.bat`。

### 3.5 变更纪律

- **版本号规则**：任何改动后次版本号 +1（3.0.17 → 3.0.18）；大重构才动主版本。
- 改 `nama_engine.h` 的 `NAMA_BUILD_PATCH` 和 `NAMA_BUILD_STR`，两处一起改。
- 每次装机前自动备份，装机后必查 md5。

## 5. 关键结论与禁忌（必读，都是踩过的坑）

### 5.1 图像参数

- `kBlendBetaStill = 1.0`（`nama_engine.cpp:916`）——**不要为降闪动收回 0.25**，那正是磨皮变糊的元凶。
  源码注释写得很清楚：β=1 时与 3.0.8 逐位相同。
- `kDetailBetaStill = 0.20`、细节/中频层 0.20 / 0.08、`kDetailVelFull = 0.40`：**一直没动过**，别顺手改。
- `kMaxFailStreak = 12`、`kMaskHoldFrames = 6`（`nama_region.cpp`）：容错阈值，改小会变脆。
- `clarity` 的下发**不要再次屏蔽**：3.0.2 屏蔽它的理由是「会整帧提亮 +2.84、违反背景零改动」，
  但 3.0.16 实测重测时该副作用已不存在（背景改动 0.005），且它是立体感的唯一 SDK 来源。

### 5.2 已撤回的错误结论（别再复述）

- ❌ 「3.0.13 失败率远高于 3.0.12」——受控压测**反转**：3.0.13 丢帧 **0.75%** vs 3.0.11 **3.31%**
  （Fisher 精确检验 p≈9e-13），且 3.0.13 短爆发 7/7 自愈、3.0.11 整进程永久失效。**此结论已撤回。**
- ❌ 「srcT 让细节 −4.7%」——反推不可靠，实测含 srcT 的版本细节更高（闪动 0.590 是 srcT 的指纹）。
- ❌ 「磨皮模式四档是 `heavy_blur` / `*_smooth` 参数」——**14 组实验逐位相同，无效**；
  且在 `face_beautification_v2` 道具上复测仍无效。此假设已排除。

### 5.3 工程坑

| 坑 | 表现 | 解法 |
|---|---|---|
| `vcvars64.bat` | 沙箱拦 `reg.exe`，跑不起来 | 用 `build_manual.bat` / `build-ui_manual.bat` |

### 5.4 3.0.17 磨皮模式：抗噪，但会被"错位掩码"废掉（必读）

#### 5.4.1 结论三句话

1. **算法对噪声是鲁棒的**：主素材加噪 ±5 → ±15，收益反而更强（平坦 −16.8% → **−25.0%**，
   闪动 −3.8% → **−11.5%**）；±30 才失效（平坦 +13.9%）。
2. **换素材"失败"的原因是掩码，不是算法**：另一段素材上四档只改动 19% 的脸内像素，
   把掩码叠回画面一看，是根**窄竖条**压在右半脸和头发上，第 10 帧又飘到左侧。
   `mv≈0` → `am≈0` → 四档全打空。
3. **上游掩码没有自检**，这是当前最大的现实风险：影响的是"只磨皮肤"这个设定本身，
   不只是 3.0.17 的新档。

#### 5.4.2 数据

| 素材 | 平坦高频 | 边缘对比 | 总细节 | 闪动 | 脸内被改动像素 |
|---|---|---|---|---|---|
| A 1074×604 噪声 ±5 | 1.767 → **1.470（−16.8%）** | +16.5% | +13.1% | −3.8% | 91.2% |
| A 1074×604 噪声 ±15 | 6.187 → **4.639（−25.0%）** | +17.1% | +0.8% | −11.5% | — |
| A 1074×604 噪声 ±30 | 12.475 → **14.211（+13.9%）** | +16.4% | +2.2% | +11.6% | — |
| B 640×394（掩码错位） | 6.818 → 7.567（+11.0%） | +6.8% | +0.8% | +2.1% | 19.3% |
| B 2× 1280×788（掩码错位） | 2.073 → 2.239（+8.0%） | +3.4% | +0.3% | +0.7% | 7.6% |

A ±5 那行在改代码重编后**逐位复现**（`recheck_big.py`），不是测量漂移。
注意 **±15 的平坦本底 6.187 与素材 B 的 6.43~6.82 几乎相同，而那一档效果最好** ——
所以"噪声大"不是 B 失败的原因。

#### 5.4.3 已排除的测量假象（别重踩）

`nz_probe_dlldir.run()` 原来用 `sorted(mask_dump_*)[-1]` 取掩码，而 `clear_dump()`
被改成空操作（避开沙箱删除计数），于是目录里残留上一次 60 帧运行的
`mask_dump_059.raw` 会被当成"本次掩码"。后果：B 素材第一次分析用了 A 的掩码
（两份 md5 都是 `c4bf880d…`），得出过一个假的 "+4.01%"。
**已改为按 mtime 取本次 run 写出的最后一个转储。**

#### 5.4.4 下一棒该做什么

| 优先级 | 事项 |
|---|---|
| **P0** | 给掩码加自检兜底：覆盖率 + 与上帧重合度做廉价判据，异常时退回整脸/整帧，而不是拿错位掩码硬磨。**不要**先调 `kTexModes` 数值 |

| P2 | `kTexLo/kTexHi` 噪声自适应（用脸内 `\|h_mid\|` 中位数当噪声底），±30 那档失效就是它 |
