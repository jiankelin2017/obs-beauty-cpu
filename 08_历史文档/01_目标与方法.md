# 目标与方法（给接手的 AI）

> 这份文档只回答三个问题：**我们要做到什么程度、凭什么说做到了、用什么方法去做。**
> 架构细节看 `04_完整交接文档.md`，本轮实验数据看 `05_优化报告_3.0.17.md`。
>
> 标注约定：**【实测】** = 有离线脚本输出或文件指纹可复核；**【推断】** = 我的判断，未有直接证据。

---

## 1. 目标

### 1.1 原始目标（用户原话，2026-10-25）

> 把自制插件效果达到 **OBS美颜摄像头**（第三方插件「美颜 2.4.2」）的 **90%~95%**。

### 1.2 这个目标的结构性问题

**"90%~95%" 无法直接计算。【推断】**

理由：第三方是闭源插件，它的四档「磨皮模式」经实验确认是自己写的后处理，不是 SDK 参数
（证据见 §3.3）。我们拿不到它对同一输入的画面输出，也就没有逐像素对标的 ground truth。
凡是声称"已经达到 92%"的说法，都不可能是测出来的。

### 1.3 所以拆成四层可验证的子目标

| 层 | 子目标 | 判定依据 | 状态 |
|---|---|---|---|
| **L1 能力对齐** | 对方能调的维度，我们都有对应开关 | 参数表逐项比对 | ✅ 11 个美化滑块 + `blur_type` / `smooth_mode` 两个下拉 + `skin_detect` 勾选 |
| **L2 语义同源** | 同名参数在两边含义一致 | 两边 `fuai.dll` / `CNamaSDK.dll` / `face_beautification.bundle` **md5 完全相同** | ✅ 已实证 |
| **L3 观感代理** | 同一档位下，纹理保留率 / 细节 / 闪动三项不劣于对方已知标定 | 离线分区域指标 | ✅ 3.0.14 起纹理保留 87.1%，对标 3.0.8 的 ~86% 标定 |
| **L4 差异项补齐** | 对方有、SDK 没有的能力，自己实现 | 自研模块 + 实测 | ✅ 3.0.17 磨皮模式四档（平坦 −16.8%、边缘 +16.5%） |
| — | **总体 90~95%** | — | ❌ **无法验证**，只能靠人眼验收 |

> 一句话给接手的人：**L1~L4 全部有据，总体百分比没有据。** 不要向用户承诺一个具体百分数。

### 1.4 非目标（明确不做）

- 不联网、不上传图像、不做云端推理。
- 不引入 Rust 或新工具链（本机没装 Rust）。
- 不做"自包含 Runtime"重构（那是另一个项目 DaVinci Resolve Qwen ASR 插件的诉求）。
- 不改 OBS 源码，只做插件。

## 2. 方法：四阶段路线

### 阶段一 · 参数面穷举（先证伪，再动手）

**做法**：从第三方三个二进制（`obs-cam-beauty_qt6.dll` / `obs-cam-beauty.dll` / `beauty.exe`）
提取字符串，加上 NamaSDK 已知的经典参数名，凑出 **166 个候选 key**；
逐个注入 `key=1.0`，与基线做逐像素比对，增量写 CSV（可中断续跑）。

**结果【实测】**：只有 **12 个**生效，其余 154 个是 noop，0 次崩溃。

| 生效 key | 影响量级 |
|---|---|
| `color_level` | 0.937 |
| `clarity` | 0.546 |
| `face_threed` | 0.173 |
| `delspot_level` | 0.161 |
| `red_level` | 0.146 |
| `cheek_small` | 0.132 |
| `blur_level` | 0.066 |
| `remove_nasolabial_folds_strength` | 0.016 |
| `intensity_eye_lid` | 0.014 |
| `remove_pouch_strength` | 0.007 |
| `intensity_lip_thick` | 0.005 |
| `change_frames` | 0.001 |

**意义**：这一步把"可能有个隐藏参数能让磨皮更好"这条路彻底关掉了。
后面所有的提升必须来自算法层，不可能来自调参。

### 阶段二 · 同源确认（决定能不能照抄语义）

**做法**：比对第三方安装目录 `AppData\Roaming\obsplus\plugins\obs-cam-beauty\bin\64bit\`
下的三个文件与我们手上的副本。

**结果【实测】**：`fuai.dll`（`a6c2e7b495c9…`）、`CNamaSDK.dll`（`14652aa53722…`）、
`face_beautification.bundle` **md5 完全相同** → 同一版本 SDK，参数语义一致。

**意义**：这条结论让"我们的 `blur_level=50` 和对方的 50 是同一件事"成立，
后面的指标对标才有意义。

### 阶段三 · 逆向（只为拿数据，不为抄代码）

**做法**：Ghidra 12.1.4 反编译 `fuai.dll`，产物 = 伪 C + Ghidra 证据包（含地址与调用关系）。

**已拿到四类【实测】**：人脸框 `FUAI_FaceProcessorSetFaceRect`、关键点
`FUAI_FaceProcessorGetLandmarksFromResult`、头部掩码 `FUAI_FaceProcessorGetHeadMaskFromResult`、
皮肤分割 `FUAI_FaceProcessorGetSkinSegResult`。文件在 `逆向资料\`。

**纪律**：`fuai` 闭源无 PDB，**签名不许臆断**，一律以 `逆向资料\` 里的证据包为准。

### 阶段四 · 算法层自研（3.0.17 的实际工作）

**问题**：磨皮质感上去了，立体感就下来了。原因是 1~2 px 的细频带里，
"平坦皮肤的毛孔/噪点"和"睫毛/鼻翼/镜框边缘"混在一起，一刀切地压或留都不对。

**做法**：测量局部结构强度 `|h_mid| = |box3 − box7|`（3~7 px 带，1/64 定点），
按强度分配到 0..1 的权重 `t`，再用 `t` 调制**脸内**那份回填量 `am`：
平坦区少回填（更干净），边缘区多回填（更立体）。**只动 `am`，不动 `amG`**，所以背景仍然零改动。

**阈值标定【实测】**：脸内 88811 px 的 `|h_mid|` 分布 P50 0.744 / P75 1.465 / P90 4.134 /
P95 10.181 / max 71（单位：灰度级）→ 取 `kTexLo = 0.75 级`、`kTexHi = 4.0 级`。

**结果【实测】**（磨皮 50 / 锐化 50 / 10 帧 / 1074×604 / 脸内）：

| 指标 | 人像磨皮（默认） | 清晰磨皮 | 变化 |
|---|---|---|---|
| 平坦区残留高频（↓更好） | 1.767 | 1.470 | **−16.8%** |
| 边缘/轮廓对比（↑更好） | 11.964 | 13.932 | **+16.5%** |
| 脸内总细节（↑更好） | 5.691 | 6.435 | **+13.1%** |
| 帧间闪动（↓更好） | 1.650 | 1.587 | **−3.8%** |

代价【实测】：纯 CPU +1.1 ms/帧 @1074×604（+4.4%），且**只在非默认档产生**。

## 3. 五条实验纪律（每条都是踩出来的）

### 3.1 相对指标不能跨素材横比

同一条规则在素材 A 上给出 −16.8%，在素材 B 上给出 +11.0%。原因不是算法不稳定，
而是两份素材的"平坦区本底"不同（A 1.767 / B 6.818），相对变化率会被本底放大。
**必须同时看三个数：绝对值、变化率、被改动的像素占脸内比例。**
（A 是 91.2%，B 只有 19.3% —— 一看就知道 B 那轮根本没生效。）

### 3.2 出现异常，先查夹具，再怀疑算法

B 素材第一轮算出 "+4.01%"，查了两小时才发现是**夹具 bug**：
探针按文件名取 `mask_dump_*` 的最后一个，而 `clear_dump()` 早已被改成空操作，
于是拿到了上一次 60 帧运行的残档，用 A 的掩码去量 B 的画面。
修法：按 mtime 取本次 run 写出的转储。**假数据差点被写进报告。**

### 3.3 不宣称"逐位相同"，除非同源重建能复现

3.0.17 的默认档号称"等于 3.0.16"，实测每帧有 1110~1645 字节差异（0.03~0.06%），最大差 2~3 级。
做了三方比对（原 3.0.16 / 同源重建的 3.0.16 / 3.0.17 默认档）：连**同源重建本身**都有差异。
所以改口径为 **PSNR 平均 81.1 dB、最低 79.7 dB**，不再说逐位相同。

### 3.4 必须做阳性对照

验证"某参数无效"时，同时跑一个**已知有效**的对照（`blur_type=2`），确认注入通道没坏。
没有阳性对照的"无效"结论不可信。

### 3.5 负结果必须留档

14 组无效参数实验、154 个 noop key 都写进了报告。这些是资产，
它防止下一个 AI 重复烧掉一周时间走同一条死路。

## 4. 已否证的路线（别再走）

| 曾以为 | 实际 | 证据 |
|---|---|---|
| 第三方四档模式是 `heavy_blur` / `clear_smooth` / `fine_smooth` / `balance_smooth` / `hazy_smooth` 参数 | **14 组实验输出与基线逐位相同**，无效 | 有阳性对照，且在 `face_beautification_v2` 道具上复测仍无效 |
| 3.0.13 的推理失败率远高于 3.0.12 | **反转**：3.0.13 丢帧 0.75% vs 3.0.11 3.31%（Fisher p≈9e-13） | 受控压测 |
| 屏蔽 `clarity` 更好（因为整帧提亮 +2.84） | 3.0.16 重测时该副作用已不存在（背景改动 0.005），而它是立体感唯一来源 | 3.0.16 实验 |
| 把 `kBlendBetaStill` 收回到 0.25 可以降闪动 | 那正是磨皮变糊的元凶；1.0 才对齐 3.0.8 观感 | 3.0.14 |

## 5. 尚未闭环的部分（诚实清单）

| 项 | 状态 | 为什么重要 |

| 2 万帧 soak | ❌ 未做 | 只有 10~30 帧序列 |
| `kTexLo/kTexHi` 噪声自适应 | ❌ 未做 | ±30 噪声下失效（平坦 +13.9%），需用脸内中位数当噪声底 |

## 6. 交付与版本纪律

- **版本号**：每次改动次版本号 +1（3.0.17 → 3.0.18）；大重构才动主版本。
  改 `nama_engine.h` 的 `NAMA_BUILD_PATCH` 与 `NAMA_BUILD_STR` 时**两处必须一起改**。
- **装机前必备份、装机后必查 md5**，脚本已内置。
- **改完源码不用再同步第二处**：旧工作副本 `D:\插件\obs-beauty-filter\` 已于 2026-10-26 删除，
  `00_源码\` 现在是唯一源码。构建产物落 `01_构建\build_output\`，装机件归档到 `02_装机\`。
