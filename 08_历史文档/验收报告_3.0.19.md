# OBS 美颜插件 v3.0.19 工程验收报告

> 验收时间：2026-10-26 13:20 ~ 14:10
> 被测件：`obs-nama-beauty.dll` 3.0.19（304,640 B，md5 `1ae34e35f8063d273856e7a929eeb70b`，已装机）
> 结论：**通过**。4 项验收全部达标，另有 1 个老问题被量化、2 处文档需要修正。

---

## 一句话结论

3.0.19 在 2 万帧连续运行下**零崩溃、零内存泄漏、零性能漂移**，异常场景（无人脸/遮脸/双人/侧脸）**全部安全降级**，与 3.0.18 的差异被精确锁定在「模式 1/2 且锐化=0」这一小块、幅度仅 ±1 级。**可以定为日常使用版本。**

同时这次验收挖出两件之前没量化的事：一是「磨皮 + 锐化同时开」存在 **3 倍性能悬崖**（老问题，非本版引入），二是「肤色掩码把木色家具当皮肤」有了**可复现的数字证据**（无人脸时仍有 8.44% 像素被改动）。

20,000 帧连续运行，1074×604，满载参数，输入 60 帧循环复用。

| 总耗时 | 557.9 s |
| 平均每帧 | 27.0 ms（最大 107.9 ms，出现在预热帧） |
| 语义区域推理 | **20000 / 20000 全成功**，累计 6.79 ms |
| 区域覆盖率 | 恒定 0.1444 |

## 三、性能实测

### 3.1 分辨率 × 参数（单帧耗时 / 折算帧率）

| 配置 | 640×480 | 1280×720 | 1920×1080 |
|---|---|---|---|
| 全关（仅人脸检测 + 语义区域） | — | — | 20.9 ms（47.8 fps） |
| 磨皮 20（默认档） | — | — | 25.4 ms（39.4 fps） |
| 磨皮 50 / 美白 20 | — | — | 25.5 ms（39.2 fps） |
| **满载 磨皮80/美白30/锐化80** | **18.2 ms**（54.9 fps） | **33.8~35.6 ms**（28~30 fps） | **62.9~63.3 ms**（15.8~15.9 fps） |

线性拟合（满载）：`耗时 ≈ 10.7 ms + 24.3 ns/像素`。
即约 11 ms 是固定开销（人脸检测 + 语义分割 + 一次 GPU 往返），其余随像素数线性增长。

**对照你的实际采集分辨率**：

- 640×480 → 55 fps，很宽裕
- 1280×720 → **28~30 fps，卡在 30fps 线上，会偶发掉帧**
- 1920×1080 → 15.9 fps，**不可用**

### 3.2 性能悬崖：磨皮与锐化同时开 = 3 倍开销

1080p，只改一个滑块：

| 参数 | 耗时 |
|---|---|
| 全关 | 20.9 ms |
| 只开 磨皮 80 | 25.8 ms |
| 只开 锐化 80 | 21.9 ms |
| 只开 美白 30 | 21.6 ms |
| **磨皮 80 + 锐化 80** | **63.3~65.7 ms** |

再固定锐化 80，扫磨皮档位：

| 磨皮 | 0 | 20 | 40 | 60 | 80 |
|---|---|---|---|---|---|
| 耗时 | **22.2 ms** | **68.6 ms** | 66.3 ms | 62.4 ms | 63.9 ms |

**这是二值跳变，不是渐变**：磨皮从 0 到 20 就一步跨到 3 倍，之后再往上加几乎不变。

原因在代码里很清楚：`applySharpen()` 开头有一句
`if (a <= 0 && g <= 0 && aG <= 0 && gG <= 0) return;`
磨皮为 0 时 `am` 也是 0，整个锐化管线**整块跳过**；一旦磨皮 > 0，语义掩码就非空，整帧的 3-tap/7-tap 双频带 + EMA 全部启动。

### 3.3 这是老问题，不是 3.0.19 引入的

1080p 满载，同一台机器、同一份输入、同一参数：

| 版本 | 3.0.16 | 3.0.17 | 3.0.18 | 3.0.19 |
|---|---|---|---|---|
| 耗时 | 55.3 ms | 58.9 ms | 62.6 ms | **65.7 ms** |

从 3.0.16 起就在 55 ms 以上。3.0.19 相对 3.0.18 是 **+5%**（+3.1 ms），来自新增的 `edge` 门控计算，符合预期。

## 四、异常场景

四组人工构造序列，各 12 帧，满载参数。输出与输入的对照图见 `out/scenes.png`。

| 场景 | 构造方式 | 检出人脸 | 返回码 | 改动 >2 级像素 | 判定 |
|---|---|---|---|---|---|
| 无人脸 | 整帧高斯模糊 14px | 0 | 0 | **0（0.00%）** | 纯透传，正确 |
| 遮脸 | 脸区盖 340×290 灰色块 | 0 | 0 | 8.44% | 不崩，但见下方问题 |
| 双人 | 两张半尺寸人像左右并排 | **2**（人物个数=4） | 0 | 5.90% | 两张脸都处理 |
| 侧脸 | 脸区横向压到 55% | 0 | 0 | 6.91% | 不崩，退化透传 |

**全部 `ret=0`，无崩溃、无黑块、无花屏。** 无人脸时是严格透传（最大差 2 级，是 RGBA/BGRA 的舍入）。

### 发现的问题：无人脸时背景被误美颜

遮脸场景里 `faces=0`，但仍有 **8.44% 的像素被改动**。改动热区图（`out/diff_sc_cover.png`）显示，被改的不是脸（脸被遮住了），而是：

- 左侧**木色书架**的竖条
- **墙角**的米色墙面
- 下方**颈部与胸口**的皮肤

原因是语义区域掩码（fuai 皮肤分割）把木色/米色物体也判成了皮肤，锐化与美白照常作用上去。这与待办里的「P0：肤色掩码自检兜底」是同一件事，**这次第一次拿到可复现的量化数字**。

### 附带确认：双人上限正常

早先一次测试只检出 1 张脸，排查后确认是测试素材把画面横向压扁了 2 倍导致第二张脸不可检出，**不是产品缺陷**。用不失真素材复测：`人物个数=1` → 检出 1 张，`人物个数=4`（生产默认）→ 检出 2 张。

## 五、回归一致性：3.0.18 vs 3.0.19

条件：同一份 10 帧输入，磨皮 50 / 美白 0 / **锐化 0**，逐字节比对输出。

| 磨皮模式 | 结果 | 首处差异 |
|---|---|---|
| 0 人像 | **逐位一致**（10/10 帧） | — |
| 1 清晰 | 10/10 帧不同 | 差 **1 级**（如 106 vs 107） |
| 2 精细 | 10/10 帧不同 | 差 **1 级**（如 123 vs 122） |
| 3 朦胧 | **逐位一致**（10/10 帧） | — |

### 结论：文档里那句话是错的，需要改

源码注释（约 1184-1192 行）与 CHANGELOG 的已知限制里都写着：

> 锐化 = 0（默认值）时本版**逐位等价于 3.0.18**

实测证明这句**只对模式 0 和 3 成立**。原因在 `nama_engine.cpp:2115`：

```cpp
const bool texModeNeedsBaseline = (s.smooth_mode == 1 || s.smooth_mode == 2);
```

清晰磨皮与精细磨皮在「锐化=0 且 清晰=0」时会把 `faceAmt` 兜底成 50，于是 `wantFaceSharpen = true`、`am = 128 > 0`，3.0.19 的 `edge` 项照常生效 —— 所以这两档在锐化=0 时也会变。

**幅度只有 ±1 级**（1/255），肉眼不可见，不影响可用性，但文档必须改准。这也解释了为什么模式 1/2 的耗时（29.5 ms）明显高于模式 0/3（17.3 ms）：前者锐化管线一直在跑，后者整块跳过。

## 七、遗留问题（按优先级）

### P0-1 「磨皮 + 锐化同时开」的 3 倍开销

- 现象：磨皮 0→20 一步让 1080p 耗时从 22 ms 跳到 69 ms
- 影响：这是**最常用的组合**（磨皮+锐化是标配），也是 720p 卡在 30fps 线的主要原因
- 方向：`applySharpen()` 目前对整帧无条件做 3-tap/7-tap 双频带。可考虑
  (a) 只在掩码包围盒内计算，(b) 两个频带按需计算（中频带只在锐化>0 时算），
  (c) 把水平/垂直两趟合并成单趟
- 建议：**下一版专门做性能**，预期能把这一档从 69 ms 压到 30 ms 以内

### P0-2 肤色掩码误判（老问题，本次量化）

- 现象：`faces=0` 时仍有 8.44% 像素被改动，热区是木色书架与米色墙面
- 影响：无人脸/侧脸时背景被平白锐化、美白
- 方向：覆盖率 + 与上帧重合度自检，异常时退回整脸或整帧；再加一个「掩码必须包含人脸框」的硬约束
- 建议：**与 P0-1 同版处理**

### P1 文档修正（不改代码、不升版本号）

1. `nama_engine.cpp` 约 1184-1192 行的注释：把「锐化=0 逐位等价 3.0.18」限定为「模式 0/3」
2. `CHANGELOG_提交记录.md` v3.0.19 章节「已知限制」同一条

### 观察项 语义区域推理偶发失败

一次 1080p 测试出现 `inferCnt=37/60`（23 帧推理失败，SDK 抛访问违例后被 catch）。三次独立复跑均为 60/60，**不可复现**；且失败时掩码沿用上一帧，`cov` 保持 0.1442，输出无异常。判定为偶发、有兜底，暂不处理，留作观察。

## 八、复现方式

所有脚本在 `C:\nama_e2e\`：

```bash
# 长时 soak（单进程！两个进程同时初始化 FaceUnity 会互相阻塞）
python soak2.py 20000 1074 604 "C:/nama_e2e/flick/nz_in" "C:/nama_e2e/nama_engine_test_319.dll"

# 分辨率耗时
python soak2.py 120 1920 1080 "C:/nama_e2e/res/r1080" "C:/nama_e2e/nama_engine_test_319.dll"

# 异常场景（生成 → 跑 → 出对照图）
python mk_scenes.py && python vis_scenes.py

# 回归一致性
python regr_cmp.py
```

**踩过的三个坑，写在这里免得重犯**：

1. **不能用 `subprocess.PIPE` 收子进程输出** —— SDK 会打印大量 TensorFlow/GL 日志，管道 64 KB 写满后子进程阻塞在 `write`，表现是「CPU 停在 1.3 秒、13 个线程全在等」。必须重定向到文件。
2. **venv 的 `Scripts\python.exe` 是重定向 stub** —— `Popen` 拿到的 pid 指向这个只占 4 MB 的壳，外部读内存永远读到 4 MB。要读真实内存必须用基础解释器 `binaries\python\versions\3.13.12\python.exe`。
3. **同一时刻只能有一个进程初始化 FaceUnity** —— 两个进程同时建 TensorFlow-Lite + OpenCL delegate 会卡死在驱动里。
