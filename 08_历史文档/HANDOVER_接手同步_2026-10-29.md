## 2. 思路（为什么走到今天）

| 阶段 | 做法 | 结果 | 教训 |
|---|---|---|---|
| 1 | 双边滤波 `d=9, sigmaColor=40` | 曲线 RMSE 1.16，100 档糊 | 双边强磨时保不住纹理 |
| 2 | 盒式低通 + 幅度门控（3.1.12/3.1.13） | 四区域平均差 2.0pp，100 档仍过磨 | 门控是启发式，不是 SDK 机制 |
| 3 | 按 GLSL 公式写 surface3（P0） | 真机加权分 1.55，face_src 退步 | **用等效参数补结构性差异：数字对、观感不对** |
| 4 | 拿到动态真值（uniform + 中间纹理） | 发现核结构根本不同 | **从"拟合"转向"照抄"** |

**核心教训（唯一必须记住的一条）**：在没有中间纹理和 uniform 真值之前拟合出的所有参数，都只是「等效参数」—— 能对上平均能量，对不上局部结构。**不要回到拟合路线。**

当前代码里的 surface3 就停在阶段 3：它是阶段 3 的产物，参数（`r0=2 → r100=14`、`thr=0`、`e` 线性 0.45→0.60）全部是拟合出来的等效值。阶段 4 已证明这些参数对应的**结构**是错的，所以下一步是重写，不是继续调。

## 3. 逻辑：SDK 磨皮真实管线

### 3.1 档位映射

```
面板 t (0–100) → OBS 恒等透传（不 ÷100）→ SDK 内部 ÷100 → blur_amount ∈ [0,1]
blur_intensity = 0.75 × blur_amount          （精确成立）
blur_amount < 0.001 → 直接返回原图
```

> `master_analysis.md §7` 用 Frida hook `fuItemSetParamd` 动态坐实了「OBS 侧裸传 0–100」，÷100 发生在 SDK 内部。

### 3.2 两级管线

```
原图
 ├─ 第一级（prog 64，void main）
 │    tex_pre_blur 预模糊 → dis 带通门控 → shader_main_s_pre_enlighten（LUT 提亮）
 │    见 §3.3（这一级 HANDOVER 写漏了门控，容易实现成"全图预模糊"）
 │
 └─ 第二级（prog 70，shader_main_s_surfaceblur_mix）
      blur1 = tex_surfaceblur1（pass1 输出）
      blur2 = tex_surfaceblur2（pass2 输出，读 pass1）
      diff  = (C − blur1)·0.5 + 0.5
      even  = clamp(2·diff + blur2 − 1, 0, 1)      ≡ clamp(C − blur1 + blur2, 0, 1)
      even  = mix(C,    even,  skin)               ← ①
      even  = mix(even, blur2, skin · evenfactor)  ← ②
      res   = mix(C, even, intensity)
      out   = mix(C, res, 1 − eye)                 // 眼完全不磨
```

### 3.3 第一级：带通门控的预模糊（**HANDOVER 漏写，必须补**）

```glsl
if (mask.a > 0.001) {                              // 仅皮肤
  blur = texture2D(tex_pre_blur, st);
  dis  = distance(vec3(0), max(blur.rgb - origin.rgb, 0)) * 30.0;
  factor = step(0.5, dis);                          // dis<0.5 平坦区：不磨
  factor = (1.0 - smoothstep(5.0, 6.0, dis)) * factor;  // dis>6 强边缘：不磨
  if (dis > 0.5 && dis < 5.0)                       // 只磨中频
    ret = shader_main_s_pre_enlighten(origin, factor * blur_intensity * mask.a * 0.25);
}
```

| `dis` 区间 | 含义 | 处理 |
|---|---|---|
| < 0.5 | 平坦皮肤 | **不磨**（防塑料感/噪点放大） |
| 0.5 ~ 6.0 | 中频（毛孔/细纹） | **磨** |
| > 6.0 | 五官强边缘 | **不磨**（保边） |

**这条纠正了 `INDEX §1.4` 的说法**：第一级不是"3D-LUT 预提亮、不是模糊"。LUT 确实在 `shader_main_s_pre_enlighten` 内部，但它的**入口被 `dis` 带通门控包着，且混合系数带 0.25**。按 INDEX 那样直接实现成 LUT 提亮是错的。

### 3.4 第二级：表面模糊核（prog 67，逐字数学式）

**同一核串行两趟**，不是两种模糊：

| | blur1 | blur2 |
|---|---|---|
| 趟次 | pass 1 | pass 2 |
| 输入 | 原图 | **blur1 本身** |
| `yFactor` | 40 | 20 |
| 色差容限 | 0.1581 | 0.2236 |
| 输出 | 540×960 | 540×960 |

```
Δgk = Ck.g − C0.g
wk  = 1 − min(Δgk² · yFactor, 1)        ∈ [0,1]
out = (Σ wk·Ck + C0) / (Σ wk + 1)
```

必须照抄的四个细节：

1. **空间权重恒为 1**（盒式核，不是高斯）
2. **值域权重是二次抛物线截断**（不是指数，不是 L1）
3. **只测绿通道**（不是亮度，不是 HSV 的 V）
4. **25 tap**：8 方向 × 3 环（`lens = 1,2,5`，比例 1:2:5）+ 1 个中心点

### 3.5 采样几何

UV 空间半轴固定：`sx = 0.002640845`、`sy = 0.0046875`（比值 1.775）。

| 输入 | 处理分辨率 | 环1 | 环2 | 环3 | 形状 |
|---|---|---|---|---|---|
| 1920×1080 | 960×540 | 2.53 / 2.53 | 5.07 / 5.07 | 12.67 / 12.67 | **圆** |
| 1080×1920 | 540×960 | 1.43 / 4.50 | 2.85 / 9.00 | 7.13 / 22.50 | **椭圆 3.16:1** |

**核按 `1136×640` 参考分辨率生成，没有随画幅自适应**。我们之前拟合的 `r=14` 正好等于竖屏最大环的水平步长 —— 数字对得上，但形状是圆的，所以观感不对。

### 3.6 肤色判定与眼保护

```
r > 0.371 && g > 0.156 && b > 0.078
&& r > b && r > g
&& |r − g| > 0.059 && (max − min) > 0.059
```

`nonskin_blur_scale = 0` → **非肤区域一点都不磨**，输出原图，没有渐变带。

眼保护只有 `eye`（`mask.g`，且要求 `mask.r ≤ 0.1 && mask.b ≤ 0.1`），**没有 mouth**。
`out = C + (res − C)·(1 − eye)`。

### 3.7 已知无效项

- `use_stf2 = 1` 在当前 build 等于没开：`stf2 = (st1 − st3)×intensity` 而 `real_main` 是恒等函数 → `stf2 ≡ 0`。
- `blur2` 永远取 `tex_surfaceblur2`，与 `use_stf2` 无关。

## 6. 接手核对代码时发现的新问题

### 6.1 「`evenfactor` 位置待确认」这个阻塞项，其实已有答案

`HANDOVER §6.3` 把它列为「未取到（阻塞项）」，`§9` 还要用户去确认。但答案就在 `beauty_source_readable.md:109-110`：

```glsl
even = mix(C.rgb, even, skin_mask);                   // ① 先按皮肤与原始色混合
even = mix(even, blur2, skin_mask * evenfactor);      // ② 再按 skin·evenfactor 拉向 blur2
```

**HANDOVER §3.3 抄漏了第 ① 行**，所以看起来像"位置不明"。顺序是确定的：① 在 ② 之前。

**这条同时暴露代码缺陷**：`beauty_smooth.cpp:758-759` 只有 ②，没有 ①。

```cpp
float even = c - v1 + v2;
even += (v2 - even) * se;      // ② 有了
                               // ① 缺：even = c + (even - c) * skin
```

影响：当 `skin ∈ (0,1)`（掩码边缘、羽化带）时，`even` 没有先被 `skin` 拉回原色，`b2` 的贡献在非纯皮肤区被**高估**。这是过渡带与掩码边缘偏差的一个结构性来源，**改它不需要等任何外部输入**。

> 注意：`surface3Rgb` 在 `m==0` 时逐字节还原，所以 ① 缺失只在 `0 < skin < 1` 的连续掩码区起作用。

### 6.5 **`blur_type` 是一个整条文档链都没覆盖的维度**（最重要）

第三方磨皮**不是一条管线**，而是**三种算法可选**。这是产品面板上的一个下拉框，我们的自研插件已经抄了这个控件（`obs-beauty.cpp:577`），但**CoreEngine 完全没实现它**（`beauty_core.cpp` 里搜不到 `blur_type`）。

`obs-beauty.cpp:579-587` 的实测注释：

| `blur_type` | 算法 | 细节能量（越小越平滑） | 产品默认 |
|---|---|---|---|
| 1 | 双边滤波 | 2.358（最强） | ✅ **默认** |
| 0 | 高斯 | 2.719（中等） | |
| 2 | 弱磨皮 | 3.762（较弱） | |
| 3 | — | 4.180（≈没磨） | 已从列表移除 |
| 4 | — | 与高斯逐字节相同 | 已从列表移除 |
| — | 完全不磨 | 4.184 | 基准 |

**为什么这条比缺数据更严重**

1. **它很可能是第一级 `tex_pre_blur` 的生成算法选择器。** `dis = |blur − origin| × 30`，而 `factor = step(0.5, dis)`。若 `blur_type=3`（pre_blur 等于原图）→ `dis = 0` → `factor = 0` → **整级不磨**。这与"3 = 实测 4.180 ≈ 等于没磨"完全吻合，是强证据。
2. **`blur_type` 默认 = 1（双边）**，也就是说真机 A/B 时 SDK 跑的是**双边预模糊**，而我们 surface3 连第一级都没有。**我们一直在和"双边+表面模糊"对比，却只实现了"表面模糊"** —— 这不是参数差，是少了一条腿。
3. **它解释了 INDEX §1.4 的困惑**：INDEX 说第一级"是 LUT 不是模糊"，很可能是因为取到的源码片段属于 `blur_type=3/4` 那两条退化分支。
4. 阶段 1 我们用双边滤波（`d=9, sigmaColor=40`）追过一次，曲线 RMSE 1.16 —— 那其实**方向是对的**，只是当时没有第二级表面模糊，才在 100 档糊掉。

**旁证（2026-10-29 14:58 补充，来自被埋没的 `05_文档\S2_磨皮核对拍结论.md`）**

这份 10-28 的文档做了一件事：拿 `goldens_legacy/flat/blur100_bt1/out.raw` 当平滑核真值，扫参找能复现档位曲线的核。
结果 **前 10 名全是双边滤波**，`bilateral d=9 σc=40` 的曲线 RMSE **1.16 个百分点**；引导滤波最好只有 2.20。

它当时被当成"保老观感的依据"用了，但**没人注意到 `bt1` 就是 `blur_type=1`（双边）** —— 也就是说，
这份文档实际上已经用实验证明了「SDK 默认路径 = 双边」这一件事。它之所以没起作用，是因为：

- 文件名 `S2_` 与 `S2_自研引擎集成现状.md` **编号撞车**；
- INDEX §2 的路由表里**没有它的入口**；
- 后来 INDEX §6.1 又写了"不要再用双边"的禁令（那是针对"双边做第二级"说的，不是针对第一级）。

**这解释了阶段 1 的困惑**：双边 RMSE 1.16 但 100 档"糊"。曲线对得上（平均能量对），像素级 RMSE 3.98（"在哪保边"不对）——
这正是"等效参数"的典型症状。而真正的解法不是换掉双边，是**双边做第一级 + 表面模糊做第二级**。

**待解决的数据冲突**：`goldens_legacy/flat` 里 `blur100_bt0/bt1/bt2` 的细纹理保留率是 **97.22 / 98.26 / 99.00**，即 **bt0 磨得最多**；而上面代码注释说 **bt1（双边）最强**。两者排序相反。可能是指标口径不同（细纹理 3.287→… vs 细节能量 4.184→…），也可能是 goldens 的 bt 编号与面板值不同源。**这个可以自己用 `nama_golden.dll` 跑三档、统一口径复测，不需要外部资料。**

**影响面**：P0 的"同档位观感不可分辨"这个目标，在 `blur_type` 未对齐前**定义是不完整的** —— 不知道对的是三种算法里的哪一种，验收数字就没有意义。

## 8. 坑

1. **不要回到拟合路线**。等效参数对得上平均值，对不上结构。
2. **不要用 `BEAUTY_BLUR_SAT` 追 100 档**，那是 legacy 的天花板。
3. **`r1 < r2` 会削穿中频**（旧结构结论，但说明半径不对称很危险）。
4. **固定阈值做不到「平坦区磨、纹理区保」**，必须 `Δg²·yFactor` 抛物线权重。
5. **`boxRgbRoi` 内部只外扩 `r×iters+2`**，大半径时调用方必须再外扩 `max(r×it)`。
6. **ROI 起点下对齐到 32**，否则浮点累加相位不同会差出灰阶。
7. **EMA 默认必须 = 1.0**。
8. **PowerShell `ConvertFrom-Json` 会被中文区域名打断**，解析 `s3_eval.py` 输出用 `[regex]::Match`。
9. **PowerShell 处理中文路径会乱码**，用 `read` 工具或 Python `os.listdir`。
10. **第三方源不能删**；**两个源不要指向同一台相机**（预览冻结根因）。
11. **版本纪律**：面板/滤镜同号，改动同步 CHANGELOG / INDEX / C 文档 / HANDOVER。
12. **`installer-stage` 仍是 3.1.7**，打包前必须同步。

### 9.1 关于 `evenfactor` 之外的第二个来源疑点

`HANDOVER §3.4` 称 25 tap / `yFactor` 40/20 是「逐字数学式」，但 `master_analysis.md §3.5` 明确写：

> `clear_blur` / `blur_h_fs` / `blur_v_fs` 三个**生成 shader 的逐行 GLSL 源码体在已解密堆文本中未干净捕获**（仅捕获到文件名清单）。本节给出的是**参数级结论 + 算法重建**，非逐字源码。

两者冲突。若 25 tap 是从动态纹理反推的，第 2 批就不能"盲抄"，必须留拟合余量。**这条决定第 2 批的实现方式，建议优先澄清。**

### 9.2 关于「缺 PNG 素材」的口径修正

`06_离线验证\goldens\src\` 里其实已有 **11 张 PNG**（face_src / crop_a-d / look1-2 / noface_gray / noface_skin / obs_grab / v_bright / v_dark），**但全部是 640×394**。宽高比 1.62，接近核的参考比 1.775 —— **椭圆核问题在这个分辨率下几乎不显现**。

所以真正的缺口不是"没有 PNG"，而是**没有高分辨率 / 竖屏（1080×1920）的源图**。有了源图，SDK 侧的 goldens 可以用 `nama_golden.dll` 自己生成，不需要外部提供。
