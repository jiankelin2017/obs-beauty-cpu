### 1.3 「预览卡死」定性（2026-10-29，已实锤）：**摄像头设备争夺，不是我们的滤镜**

真机 `blur=100` 时预览冻结、UI 仍能点、**不崩溃**。全内存 dump（`obs64_frozen_17416.dmp`，
2.77 GB）+ OBS 官方 32.1.1 PDB 符号解析后的结论：

| 判据 | 实测 | 含义 |
|---|---|---|
| 图形线程 TID 17240 | `obs_graphics_thread → obs_graphics_thread_loop+0x659 → video_sleep+0x2e → os_sleepto_ns+0xb7` | **正常帧间睡眠**，没卡在滤镜 |
| 两条采集线程 TID 18736 / 18740 | `DShowInput::DShowLoop+0x43 → GetMessage` | 两条 win-dshow 都在等消息，**没有新帧** |
| 全 189 线程活栈 | **无一条含 `obs-beauty.dll`** | 排除「图形线程卡在我们滤镜」（分支 A） |
| Profiler | `obs_graphics_thread` median **0.586 ms** / max 81.9 ms；帧间隔 median **33.332 ms** / max 11756 ms | 图形线程本身健康，是**输入断粮** |

**触发链**：10:55:03.409 我方 dshow 源打开 Integrated Camera（第二家）→ 10:55:03.575
`blur=100` 引擎开干（只渲染了 4 帧）→ 10:55:06.229 第三方进程 18768
`Camera Device Disconnect, Try Connect` → 10:55:06.384 第三方重设设备
（TID 18740 残留栈 `DShowInput::Activate + quartz.dll` 实锤）→ 摄像头被第三方占住，
**两个 dshow 源都再也拿不到帧** → 预览冻、UI 活、无 crash。

**结论：分支 B（设备争夺 / 采集断粮）**。健康对照：10:39 `blur=0` 直通不死；
**10:50 `blur=100` 连跑 4 分 15 秒不死**（Profiler median 0.578 ms / 帧间隔 32.1 ms）；
20:25 `blur=20` 活 3+ 分钟 —— 所以**不是「blur=100 太重」**，而是 10:54 那次
正好撞上第三方重连窗口（`blur=100` 只是让现场更显眼）。

- **终结性判别实验（待做）**：复现冻结后把第三方源的「设备」设为**无**（源保留，不删），
  预期我们预览立即复活。
- **产品级处置（未实施，待决策）**：① 文档/装机引导「两个源不要同时指向同一相机」；
  ② 面板加「无帧看门狗」，超时自动重启采集。

**当前状态（一句话）**：surface3 已落地但**默认关闭**（`BEAUTY_SMOOTH_MODEL=surface3`），它是"拟合阶段"的产物，

**两处必须知道的证伪**（原本节写错，已纠正）：

| 原写法 | 实际 | 依据 |
|---|---|---|

**新发现（原本节完全没有）**：第三方磨皮有 **`blur_type` 三档算法**（1=双边·**产品默认** / 0=高斯 / 2=弱磨皮），
我们的 CoreEngine 至今没实现这个概念。详见 L1 §6.5。

**还缺的外部资料**（原本节列的两样**已经拿到**，删掉）：

| 缺什么 | 卡什么 |

| 真机 50/100 并排截图 | P1 人眼判据 |
| 25 tap / `yFactor 40/20` 的**来源**（逐字源码 or 动态反推） | 第 2 批能不能"盲抄" |

**开发计划**：见 L1 §7（第 0 批定 `blur_type` 口径 → 第 1 批低风险四项 → 第 2 批核心改造 → 第 3 批 LUT）。

## 6. 最容易踩的雷（细节见 HANDOVER §5 / §6）

### 6.1 自研引擎线（当前，3.1.x）

1. **ORT 自旋必须关**（`beauty_onnx.cpp` 里 `intra_op/inter_op.allow_spinning=0`）—— 默认值 1 会让推理线程在两次 `Run()` 之间忙等，33ms 节奏下白烧 1.4 核。CPU 对不上先查这条。
2. **同步/异步提交周期不能合并** —— 异步 `maskEveryAsync=0`（生产）、同步 `kMaskEverySync=4`（离线台架）。把同步也改 0，`cpu_bench` / `verify_roi` / `detail_test` 基线全部作废。
3. **台架必须按真实帧率节流**（`BENCH_FPS=30`）—— 不节流会跑到 80fps、磨皮线程占满核，争用被放大成「每帧多 1.4ms」的假象。
4. **回归只认哈希**：改完核/路径后 `verify_roi.py` 三档应 `maxdiff=0` 且输出哈希仍为当前基线 **`b7fb312e…` / `4fb7a20e…` / `7e0fb6c7…`**（2026-10-29 实跑两次逐位复现，对应 3.1.13 修订构建）。旧基线 `3f41f430… / 40946fc9… / fda807e2…` 是 3.1.8~3.1.11（双边滤波族 + 掩码默认关自适应）时代的，**3.1.12 盒式低通（C15）与 3.1.13 肤色自适应默认开（C20）有意改了像素输出**，哈希合法变化 —— 拿旧哈希当现在的判定会误报。3.1.13 起哈希变只有三种理由：动态范围重标 / 掩码几何改 / 环境变量（如 `BEAUTY_BLUR_SAT`）默认值变。**3.1.14 换 surface3 三层核后哈希必然变，这是有意改像素**：旧基线留在 `goldens_legacy`，新基线单独建，两次连跑仍须逐位一致。
5. **磨皮是三层，不是两层** —— 不要再用 `BEAUTY_BLUR_SAT` 去追 100 档。SDK 的 `b1/b2` 半径差 + **表面模糊颜色阈值**才是主因；两层模型（C + 单尺度 low）在结构上就到不了。见 §1.4。
6. **`beauty_source_readable.md` 是反编译 GLSL，不是可编译源码** —— 缺 `tex_surfaceblur1/2` 的生成 pass 和面板→uniform 映射；`lowp` 精度、单边 `max(blur−origin,0)`、sharpen 的 clamp 溢出都可能是伪影。当“结构真值”用，别照抄。

### 6.2 旧 SDK 线（3.0.19，已冻结，改之前先想清楚为什么要回去）

1. **掩码没有自检兜底** —— 错位时 `mv≈0`，磨皮四档全部打空。先处理它，别先调阈值。
2. **`kBlendBetaStill` 不能收回 0.25** —— 3.0.14 改成 1.0 是磨皮质感达标的唯一原因。
3. **不要重新屏蔽 `clarity`** —— 它是立体感的唯一 SDK 来源。
4. **`applySharpen()` 开头的早退条件不是死代码** —— 它正是性能悬崖的成因。
