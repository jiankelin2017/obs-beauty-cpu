# 自研引擎替换：目标、方法与代价

> 日期 2026-10-27 · 对应源码 3.0.19 / UI 3.0.20
> 配套：《自研美颜引擎替换方案 v1》《自研引擎_三个决策》《引擎抽象层_beauty_core_第1步》

---

## 1. 目标

### 最终目标

把 `CNamaSDK.dll` / `fuai.dll` / `auth_package.bin` / `*.bundle` 全部移出运行时，
换成代码、着色器、模型、权重全部自产的美颜核心。判据一句话：**发出去的
`obs-nama-beauty.dll` + 数据目录里，跑起来的每一行代码、每一字节权重都是我们自己的。**

### 分期目标

| 阶段 | 目标 | 状态 |
|---|---|---|
| T0 抽象层 | OBS 胶水层与引擎解耦，随时可切换实现 | ✅ 已完成（2026-10-27） |
| T1 基线冻结 | SDK 输出固化成可复现回归集 | ✅ 已完成（2026-10-27） |
| T2 换零件 | 按「掩码 → 磨皮核 → 人脸检测」顺序逐个替换 | ⬜ 未开始 |
| T3 收敛 | 指标逼近基线，出「经典」预设，性能验收 | ⬜ 未开始 |

### 本次已交付

- `00_源码/beauty_core.{h,cpp}`：引擎抽象层 + `NAMA_ENGINE_IMPL` 开关
- `00_源码/golden_capture.cpp` + `06_离线验证/golden_capture.py` + `build_golden.bat`：基线采集
- `06_离线验证/goldens/`（AI 掩码开）与 `goldens_legacy/`（产品实际路径）各 78 组 + 2 条运动序列

## 2. 方法

```
T0 抽层     obs-nama-beauty.cpp ──> IBeautyEngine ──> NamaAdapter（现状）
                                                  └─> PassthroughEngine（降级）
                                                  └─> CoreEngine ──> beauty/（T2）

T1 冻结     goldens_legacy/  78 组 + motion（对齐老观感的基准）
            goldens/         78 组 + motion（AI 掩码开，自研的目标）

T2 换零件   S1 皮肤掩码  fuai ──> 自研分割模型（PPHumanSeg 类，Apache-2.0）
            S2 磨皮核    SDK 双边 ──> 自研保边平滑（引导滤波 / 表面模糊）
            S3 人脸检测  SDK ──> YuNet（MIT）
            每步都在 T0 的开关后面加一个实现，随时可切回、可 A/B

T3 收敛     新引擎跑同一批 golden，按指标拟合参数 → 固化成「经典」预设
```

**三条硬规矩：**

1. **每步都能独立回退**。`NAMA_ENGINE_IMPL` 一改就回到上一个可用状态；任何一步做砸了
   不影响已发布版本。
2. **每步都用同一批 golden 对拍**。不做肉眼评估 —— 细节保留率、Δ亮度、改动像素占比、
   掩码覆盖率四项指标说话。
3. **先冻结再动手**。SDK 还在手上的时候才有机会拿到基准；一旦先拆，就永远无法证明
   「新引擎不比旧的差」。

## 3. 为什么要这样干

### 3.1 为什么先抽层，而不是直接写新引擎

插件层现在有 11 处直接调用 `NamaEngine::inst()`。不抽层就替换，等于让 OBS 胶水层、
属性页、预设存取全部跟着改，任何一处回归都要在完整 OBS 里复现，调试成本极高。
抽层之后，T2/T3 的所有风险都被关在 `beauty_core.cpp` 一个类里。

### 3.2 为什么先冻结基线（T1 有时效性）

**SDK 还在手上，这是唯一能拿到基准的窗口。** 方案 v1 把 M0 标为「唯一有时效性的一步」，
就是这个意思。旧版 1.x 到 3.0.19 的磨皮观感差异，当时就是因为没有任何量化记录，
只能靠肉眼争论（见两份源码里那些「实测 43 张照片」「A/B 横评」的手工记录）。

本次采集还得到一个交叉验证：**产品实际路径下磨皮 50 档，全帧细节保留 87.33%**，
与 `nama_engine.cpp` 注释里记录的「50 档纹理保留约 86%」吻合（差 1.3 个百分点）。
说明采集链路可信，不是自说自话。

### 3.3 为什么按「掩码 → 磨皮核 → 人脸检测」这个顺序

| 顺序 | 理由 |
|---|---|
| 先换掩码 | 它是最脆弱的一环：依赖**明文 bundle**，而分发包里只有加密件（见下节）；换成开源模型同时解决脆弱性与合规 |
| 再换磨皮核 | 磨皮观感高度依赖掩码质量，掩码先定下来，磨皮核的调参才有稳定输入 |
| 最后换人脸检测 | 它只提供 `faces` 计数（门控美白/红润），影响面最小，替换风险最低 |

### 3.4 一个影响对齐对象的发现

**发布出去的产品里，fuai 语义皮肤掩码是不可用的。**
`04_依赖与SDK/installer-stage/` 与 `08_安装包/obs-nama-beauty.nsi` 都只包含加密的
`ai_face_processor_pc.bundle`，没有明文件，而 `nama_region.cpp` 要明文件才能初始化。
所以用户机器上的 3.0.19/3.0.20 跑的是 v1.4 的 YCbCr 颜色判据。

两套基线的实测差异印证了这一点（同为 face_src、blur_type=1）：

| 磨皮档 | legacy（颜色启发式）细节保留 | on（AI 掩码）细节保留 | legacy 改动像素 | on 改动像素 |
|---|---|---|---|---|
| 0 | 100.00% | 100.00% | 0.00% | 0.00% |
| 25 | 92.94% | 99.35% | 0.01% | 0.00% |
| 50 | 87.33% | 98.80% | 2.69% | 0.23% |
| 75 | 82.31% | 98.40% | 8.20% | 0.95% |
| 100 | 79.47% | 98.26% | 12.99% | 1.93% |

AI 掩码只覆盖 7.33% 的画面，所以几乎不动全帧细节 —— **这也意味着对齐时不能用全帧指标
去比 on 套**，必须换成掩码内统计，否则会得到「新引擎磨皮太弱」的错误结论。

**对齐「老观感」的基准是 `goldens_legacy`，不是 `goldens`。**

## 4. 好处与代价

### 4.1 整体

| | 内容 |
|---|---|
| **好处** | ① 彻底去掉逆向依赖（含「必须先导出明文 bundle」这个随时会断的环节）<br>② 合规：当前是逆向对接闭源 DLL，自研后无此问题<br>③ 参数真正可控：现在的 `kTexModes` / `kMidGain` 等标定全部绑定在 SDK 输出上，换引擎后每一档才是我们自己定的<br>④ 补齐产品当前缺失的能力（AI 皮肤掩码在用户机器上根本没跑起来） |
| **代价** | ① 工期：方案 v1 估 M1~M5 合计约 60~80 人日<br>② 画质回退风险：SDK 磨皮是与第三方对标多年的产物，自研要重新标定全部档位<br>③ 5 项人脸局部效果（五官立体/亮眼/去黑眼圈/去法令纹/祛斑痘）自研成本高，大概率要砍掉或降级<br>④ 性能未知：GPU 路线的第一个测量点要等 M1 结束 |

### 4.2 分阶段

| 阶段 | 好处 | 代价 / 风险 |
|---|---|---|
| T0 抽象层 | OBS 侧零改动即可换引擎；随时回退；新增降级兜底 | 一层虚函数调用（每帧一次，可忽略）；多两个文件要维护 |
| T1 基线冻结 | 后续所有对齐有量化基准；顺带暴露「产品实际没有 AI 掩码」这个事实 | 磁盘约 200 MB（156 组 × 1 MB）；采集耗时约 6 分钟/套 |
| T2-S1 换掩码 | 去掉最脆弱依赖；补齐产品缺失能力；Apache-2.0 合规 | 开源模型是「人像分割」不是「皮肤分割」，需二次处理（人像 ∩ 人脸框 或 叠肤色判据）——**未实测，需先做离线对拍** |
| T2-S2 换磨皮核 | 磨皮档位第一次真正由我们定义 | 现有全部标定失效（输入变了），要重标；保边平滑能否追平 SDK 双边质感**未经实测** |
| T2-S3 换人脸检测 | 影响面最小 | YuNet 只给 5 点关键点，拿不到 SDK 那套完整人脸跟踪 |
| T3 收敛 | 用户无感切换（有「经典」预设兜底） | 拟合工作量取决于前几步的差距有多大 |

### 4.3 已知未决（必须先验证再往下走）

1. 引导滤波 / 表面模糊能否追平 SDK 双边磨皮的质感 —— **推测，未实测**
2. PPHumanSeg 二次处理后能否替代 fuai 皮肤掩码 —— **推测，未实测**
3. GPU 渲染层最终能压到多少毫秒 —— 要等 M1 才有第一个数据点

## 5. 事实与推测的边界

**可验证事实**：本文所有指标来自本机采集（`06_离线验证/goldens*/baseline.md`，
78/78 逐字节可复现）；依赖盘点点自两份源码逐行核对；许可信息来自各官方仓库；
「分发包只有加密 bundle」由 `installer-stage` 目录清单与 nsi 的
`File /r "${SRCDIR}\sdk\*.*"` 共同确认。

**个人推测**：第 4.3 节三条均为工程判断，未经实测；「先换掩码再换磨皮核」的顺序是
基于依赖关系的推理，若 S1 离线对拍不通过，顺序需要调整。
