## 0. 三十秒状态

插件（`obs-beauty.dll`）有**两套引擎**，用环境变量 `NAMA_ENGINE_IMPL` 切换：

| 值 | 实现 | 状态 |
|---|---|---|
| 不设 / `core` / 未知值 | `CoreEngine`（**0.8**）自研：**盒式迭代低通 + 幅度门控**磨皮（3.1.12 起，见 `C15`）+ YuNet 人脸检测 + 肤色∩人脸框∩脖子通道掩码（**3.1.10 起掩码↔帧对齐 + 边界 8% smoothstep 羽化**）+ clarity + 美白红润 + 锐化/全局锐化（含**时序 EMA**）+ **五官立体/亮眼/去黑眼圈/去法令纹/祛斑痘** | ✅ **默认**（面板 **11/11** 项全覆盖） |
| `nama` | `NamaAdapter` → CNamaSDK + fuai（回退键，行为与抽层前逐位相同） | ✅ 可用 |
| `passthrough` | 直通（用于验证开关和降级） | ✅ 可用 |

> 未知值（比如写错成 `cor`）按「没设置」处理，走默认 core。为什么不静默退回 nama：
> 那样写错一个字母会悄悄跑回旧引擎，用户以为自己在测新引擎。写错是可见的 ——
> `init OK` 那行会打出 `engine=core/0.8`。

## 1. 边界：已经改了，别按旧文档干活

用户 2026-10-28 明确表态：

> **能用开源的就用开源的！自研只是为了把不可商用的第三方换掉、去掉责任风险。**

| | 旧边界（`自研引擎替换方案_v1.md`） | **新边界（以本节为准）** |
|---|---|---|
| 判据 | 运行时每一行代码、每一字节权重都得自己产 | **每个第三方件的许可允许商用 + 可再分发** |
| 自研的定位 | 目的本身 | 手段之一，只在没有合适开源件时才写 |

推论（这几条务必记住）：

- **OpenCV 可以用**（Apache-2.0，可商用可闭源分发）。我此前说「用 OpenCV 和继续用
  NamaSDK 没本质区别」是**错的**，已向用户纠正。
- **PyTorch 可以用于训练**（BSD-3），「训练工具算不算第三方」的纠结作废。
- 唯一还要避免的是：**逆向对接未授权的闭源件**（CNamaSDK / fuai / auth_package / bundle）。
- 方案 v1 里「必须清除/必须替换/保留」那张表仍然有效，只是「允许依赖」一栏放宽了。

### ~~P0 · 对拍口径修正~~ ✅ 已完成（2026-10-28），但结论和预期不同

**做完了什么**：`BeautyCoreMask` 导出已加（`core_probe.cpp`，格式同 `BeautyDumpMask`），

**三条要点（务必先读 S3，别照旧理解往下做）**：

1. 旧口径「SDK 改动过的像素」**不是皮肤区** —— 它 51.6% 是白蕾丝上衣和背景衣架。
   所以「1.09 个百分点」不成立（S2 的结论要重做），「99%」也不是磨皮失效。
2. 换成 fuai 肤色掩码后，在 **Laplacian 口径**下自研误差 8 个百分点、25~75 档明显偏弱。
   但这个数**只在 Laplacian 口径下成立**，不能当结论。
3. 换成项目验证过的**噪声地板**口径重测后，真实差距是 **3~7 个百分点**（见下面 P0 条）。
   教训：口径换了结论就变，**下结论前先确认用的是项目那把尺子**。

### ~~P0 · 噪声地板口径对齐~~ ✅ 已完成

覆盖率 5.35% → 6.91%（fuai 7.33%）。连 S1 的老大难 `v_skinbg`（当时 0.162）都到 0.838。
参数可用环境变量 `BEAUTY_NECK_HALFW` / `BEAUTY_NECK_LEN` 临时覆盖，便于复扫。

### ~~P2 · GPU 化磨皮核~~ → **已结案，改走 CPU 优化**

**2026-10-28 决定：不上 GPU，把 CPU 优化到底（用户拍板 C 路线）。**

原来的判断「CPU 到不了实时」基于 15 ms @640×394 这个观测，但那个观测的前提是
「代码已优化过」—— 实际当时是**单线程 + 全帧**，这两条都没做。

优化后实测（详见 `C1_CPU性能优化.md`）：

| 分辨率 | 优化前均摊 | 优化后均摊 | 加速 |
|---|---|---|---|
| 640×394 | 18.45 ms | 2.95 ms | 6.3× |
| 1080p | 117.75 ms | **7.25 ms** | **16.2×** |

四项优化：ROI 裁剪（只磨掩码包围盒，12.64% 面积）、多线程按行切分、
去掉全分辨率 RGB 中间缓冲、合并掩码统计遍历。**画质逐字节不变**
（`verify_roi.py` 三档分辨率 maxdiff=0，输出 SHA256 与优化前一致）。

顺带排除一条路：**降检测输入到 320 不可行** —— 我们的 YuNet ONNX 把输入声明成
固定 640×640，ORT 直接拒绝。OpenCV 能跑 320 是因为它的 dnn 引擎不认模型声明，
照它的表现推断「模型支持动态输入」会踩坑。检测提速改走推理多线程（1→2 线程）。

### ~~P3 · 补齐功能~~ ✅ 已完成（2026-10-28，面板 11/11）

分四批做完：美白/红润（`C6`）→ 清晰（`C9`）→ 锐化/全局锐化（`C11`）→
**人脸局部五项**（`C12`）。

关键做法：五项没有历史基线，所以**先采 SDK 再实现** —— 把每个参数单独拉满、

再把它们换算成"相对脸框的比例"。几何参数是量出来的，不是估的。

⚠️ 有一条被实测推翻的假设记录在 `C12 §1.1`：**「五官立体 = 大尺度 unsharp」是错的**

| 25 | **ROI 与全帧差 1 个灰阶**（`verify_roi` maxdiff=1，看着小但要命） | 盒式滑动窗 `s += add−rem` 的 float 误差会累积；我加的「每 32 像素重算」用的是**局部**坐标，ROI 模式的局部 x=0 对应全帧 x=bx0，两边重算点落在不同全局坐标 → 累加序列不同 → 最后四舍五入被放大成 1 | ROI 起点**下对齐到 32**（`alignDown32`），两模式重算点落在同一批全局坐标。⚠️ 中途试过给 `boxPlaneH/V` 传 `originX/originY`，漏了「首像素必须重算」→ 第一像素输出 0，maxdiff 涨到 **18** |

| 27 | 频带指标说「追平了」，像素级 RMSE 却说「离得更远了」 | 两个指标看的不是一回事：频带保留率是「相对原图削了多少」，不管削在哪；RMSE/相关系数看的是「削在哪」。SDK 磨皮 50 的改动本身只有 1.32 灰阶 RMSE，信噪比极低 | 同时报**两个数**：频带保留率 + 改动图相关系数（旧 0.201 → 新 0.520）。只有素材补齐后像素级指标才可信（`C15 §7`） |
| 25 | 加了羽化后每帧多出 ~10ms | 逐像素做 `dist*256/fe` 整数除法，1080p 脸框 40 万像素 | 查表 `g_featherRamp[65][65]`，`ensureReady` 里算一次 |
| 26 | **羽化 A/B 两趟完全一样、cmp 报「羽化没生效」的假阴性**（白排查了源码） | `BEAUTY_MASK_FEATHER` 在 `ensureReady()` 里只进程启动时读一次；`feather_ab.py` 旧版把 on/off 两趟跑在**同一个进程**里，两趟读到同一个值 | 改成**每趟 fork 独立子进程**、子进程自己设环境变量再加载 DLL |
| 27 | **真机仍拖影，羽化调多宽都没用** | 拖影本体不是"硬边"而是**掩码与帧脱钩**：worker 在帧 k 算掩码、渲染在 k+1 用，边界每帧在脸后扫。羽化只能把"硬边扫过"软成"淡边扫过"，治标不治本 | **掩码↔帧对齐**（3.1.10）：collectAsync 时把 worker 输入槽里的原始帧零拷贝 swap 进 `heldFrame_`，磨皮直接处理那一帧 —— 注意帧 swap 只在 **worker 空闲**（`ready` 已置位）时做，与 `submitAsync` 的 memcpy 同一约束，两者不会并发；分辨率变了 `async_.frame.size()` 不符就不换（对齐静默失效） |

## 7. 关键决策与理由（别重走）

| 决策 | 理由 |
|---|---|
| 掩码用「肤色 ∩ YuNet 人脸框」而不是 PPHumanSeg | PPHumanSeg 分的是人像（含头发/衣服），IoU 只 0.261；组合方案 0.727 |
| 人脸框外扩 **1.15** | 扫描 IoU 峰值（1.00→0.700、1.15→**0.727**、1.25→0.707、2.2→0.383） |
| 磨皮用双边而不是引导滤波 | 曲线匹配双边全胜（1.09 vs 引导最好 2.20） |
| 磨皮半径 **2** 而不是 4 | 半径小反而更贴合 SDK，且快 3 倍（15ms vs 45ms） |
| **不用降采样加速** | 降采样本身是低通，叠加后细节被多抹一截，曲线误差 27+，补偿不回来 |
| ORT 动态加载而非导入库链接 | 否则用户少装 ORT 时插件**加载阶段**就失败 |
| source id 双注册 | OBS 场景 JSON 存 id，硬改会让老场景丢滤镜 |
| `nama_engine/region/log` 不改名 | 名字准确（就是 NamaSDK 驱动），且即将删除 |
| **区域五项的坐标全部归一化到脸框** | 写死像素半径在 720p 会压到瞳孔、在 4K 会跑到下眼睑 |
| **区域五项先采 SDK 再实现** | 没有基线就调参等于凭想象；作用域的中心/σ/峰值都是量出来的 |
| **法令纹的旋转角在像素空间算** | 脸框不是正方形（107×141），在归一化空间取 `atan2` 会歪 |
| **增益按"脸内 dY 均值 + p95"回调，不用 SDK 峰值** | 峰值是连通域最亮的几个点，椭圆中心一大片都拿满增益；直接抄峰值会过冲 2~5 倍 |

## 8. 不要做的事

1. **不要**再试降采样加速磨皮（已证伪，误差 27+）。
2. **不要**指望 CPU 做到 1080p 实时（15ms@640×394 ≈ 120ms@1080p）。
3. **不要**用 `raw.githubusercontent.com` 下 opencv_zoo 的模型（LFS 指针）。
4. **不要**在没有基线的情况下改算法 —— 先跑 `smooth_compare.py curve` 看曲线。
5. **不要**自己决定"掩码只磨脸还是连脖子" —— 这是观感取舍，要问用户。
6. **不要**把 `03_逆向资料/` 里的反编译产物打进安装包。
7. **不要**硬改 `BEAUTY_FILTER_ID`（`obs_beauty_filter`）和 `BEAUTY_FILTER_ID_LEGACY`。
8. **不要**按单张 face_src 去精调 `C12 §4.1` 那三处偏差（素材不足，调了就是过拟合）。
9. **不要**把五项区域效果写成五个独立函数 —— 几何计算会复制五遍。`beauty_region` 这一层
   只做两件事：算几何、按几何改像素。
10. **不要**给区域效果写死像素半径，一律用「相对脸框的比例」。

## 8.5 接手后建议的执行顺序

1. 先跑一遍 `verify_roi.py` 确认当前二进制没跑偏（三档 maxdiff 应为 0）。
2. 读 `C12`（本轮交付）与 `C11`，这两篇里有 core 与 SDK 的全部差异说明。

   一张图看不出来。

5. 最后才动 P5（装机 + 切默认引擎）。切完必须真机 30fps 跑一轮。
