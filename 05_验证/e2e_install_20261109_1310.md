## 4. `PHASE R`：升级后卸载，机器上到底留下什么

`1.0.13.9` 的验收记录 §5 留了一条盲区：「`B2 … RESTORED from backup` 分不清
『文件根本没被删』和『从备份还原成功』，要真正验证还原，得先装一个不同版本再覆盖安装」。
本轮补上的 `PHASE R` 就是这个动作，全程只记录数字、不判 PASS/FAIL，**不占 40 项配额**。

流程与日志原文：

```
R0 wipe to a real clean slate (no INSTDIR, no backup, no registry)
R1 install 1.0.13.9 first (the "older version already installed" case)
  R1 exit 0  filter 505856 B  409d6a5288530f10f22cfa4fc12e5631
R2 install 1.0.13.10 over it
  R2 exit 0  filter 463872 B  8b0449cc122a02eb7b8032162c2a94ed
  [bak after R2] 4 file(s) in C:\Program Files\obs-beauty\backup
    obs-beauty-ui.dll.bak            218624 B  a35c6cd02c9744810e90987fa3107ade
    obs-beauty.dll.bak               505856 B  409d6a5288530f10f22cfa4fc12e5631
    onnxruntime.dll.bak            11569696 B  cd5e3b3eedbe6774b28d8fff9d0a3243
    yunet.onnx.bak                   232589 B  4ae92eeb150c82ce15ac80738b3b8167
R3 uninstall -> what is left behind?
(uninstall registry key gone: True)
  R3 exit 0
  survivor obs-beauty.dll         505856 B  409d6a5288530f10f22cfa4fc12e5631
  survivor onnxruntime.dll      11569696 B  cd5e3b3eedbe6774b28d8fff9d0a3243
  survivor yunet.onnx             232589 B  4ae92eeb150c82ce15ac80738b3b8167
  survivor obs-beauty-ui.dll      218624 B  a35c6cd02c9744810e90987fa3107ade
  INSTDIR exists=False  models dir exists=True
```

**读数**（`survivor` 行的路径是 `ProgramData` 下的插件路径，由脚本的 `$FILTER/$ORT/$MODEL/$UI`
四个常量决定；`INSTDIR exists=False` 只说明 `C:\Program Files\obs-beauty` 被删干净了）：

1. 卸载器**确实删掉了安装目录与两个注册表键** —— 卸载流程本身没有半途失败。
2. 但它**把 `backup\*.bak` 四件原样还原回了 `ProgramData`**，其中
   `obs-beauty.dll` 是 **505,856 B / `409d6a52…`**，与 R1 装的 `1.0.13.9` 逐位相同。
3. 结论：**「装过 1.0.13.9 → 升级到 1.0.13.10 → 卸载」之后，机器上留着的是完整的
   `1.0.13.9` 插件，而不是「什么都没有」。** 用户视角是「卸载不掉，且退回旧版」。

**同时排除了另一个假说**：「文件被占用导致 `Delete` 静默失败」。若如此，存活下来的会是
**新版** `463,872 B`；实测是 **505,856 B**，与备份文件逐位相同，只能是还原路径。

**机制**（读 `obs-beauty.nsi` 得到，本轮未改安装器）：

- `nsi:382 / 392 / 402 / 419`：卸载段「`backup\*.bak` 存在就还原」，无条件；
- `nsi:223`：安装段用 `IfNot FileExists` 写备份 —— 于是**已存在的备份永不刷新**。
  第一次装 `1.0.13.9` 时 ProgramData 里没有旧文件，不产生备份；装 `1.0.13.10` 时
  才把 `1.0.13.9` 写进 `backup\`。此后无论升级多少次，备份里永远是 `1.0.13.9`。

## 5. 首次失败（`18:55` 那轮 6 项 FAIL）的归因

首次运行（`18:55` 那轮正式回归）结果是 `34 PASS / 6 FAIL`，6 条全部落在 A3：

```
gone after wait: filter=False ort=False models=False ui=False
```

现场四件 MD5 与测试前完全一致（`8b0449cc / cd5e3b3e / 4ae92eeb / 69c4a865`），机器状态正常。

归因：**不是 `1.0.13.10` 的缺陷，是判据脚本的前置清理不全。** 上一轮测试遗留在
`C:\Program Files\obs-beauty\backup\` 的备份文件，在 Phase A 的卸载段被还原回
`ProgramData`，四件「卸载后仍在」，`Wait-PathGone()` 等满 8 秒后判假。
给 A0 补上「清 `$INSTDIR` + 两个注册表键」后，本轮同类断言全部首轮命中。

这条归因现在有 `PHASE R` 的数字支撑，不再是推断：**还原行为是真实存在的**，
只在「机器上残留着上一次的 backup」时才暴露。

## 6. 仍未消除的盲区与遗留决策

- **卸载语义本身没有改**：`PHASE R` 只是把现象量出来了。「升级后卸载是否应该退回旧版」
  属于产品语义决策，两种改法都动 `nsi`（安装段改为覆盖刷新备份 / 卸载段识别版本号而非盲还原），
  本轮**未动安装器**，等决策。
- **`PHASE R` 只覆盖单一升级路径**：`1.0.13.9 → 1.0.13.10`。跨大版本、连续三次升级
  （备份会不会被二次覆盖）、以及「装旧版但从未运行过」这些组合未测。
- **少核机器、多人脸、1080p 与录制链路**：本轴从未覆盖，引用本版装/卸结论时须一并说明。
