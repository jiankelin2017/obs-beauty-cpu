## 1. 要回答的问题

上一轮（`05_验证/ab_perf_20261108.md`）确认 `BEAUTY_MASK_EVERY=2` 有明确收益，但每帧仍
40 ms 量级、距 30 fps 的 33.3 ms 有缺口。本轮要回答：**不动代码，只调面板与现有环境变量，
能不能把缺口补上。**

## 2. 方法

| 项 | 做法 | 为什么 |
|---|---|---|
| 启动 | `ab_run.py`：改配置 → 起 OBS → 静置 15 s → 录制 → 停录 → 正常退出 | 静置让首帧预热与自动方向探测先走完 |
| 切换 | `SetSourceFilterSettings` 在**同一会话内**交替切换面板值，每段 30–36 s，跑 2 轮 | 重启 OBS 会换画面内容，1–2 ms 的差异会被内容方差吞掉；同会话交替把内容固定在一次拍摄里 |
| 归因 | 每次切换记墙钟时刻；日志「性能」窗口只有**整段落在某段内**才计入该段 | 跨边界的窗口混了两个相位，归到哪边都是错的 |
| 口径 | `engine_proc = (Σ engine×180 − 无脸帧×0.7 ms) / 处理帧数` | 无脸帧只做整帧 memcpy 就返回，却占分母；不折算会把「少算几帧」读成「引擎变快」 |
| 门槛 | 某段处理帧 < 30% 判样本不足，不计入 | 实测一段 720/720 无脸时折算值飙到 154 ms，那是分母效应不是性能 |

`0.7 ms` 取自 `beauty_core.cpp` `submitAsync` 处的源码注释（8 MB memcpy），**是估计值**。

## 3. 结果一：逐项消融（`abl1`，every=2）

| 相位 | 面板值 | 有效窗口 | 引擎 raw | 引擎 proc | 合计 proc |
|---|---|---|---|---|---|
| P0 基线 | 磨皮 100 / 美白 45 / 下巴 7 | 8 | 35.43 | **36.68** | **40.63** |
| P1 磨皮归零 | 磨皮 0 / 美白 45 / 下巴 7 | 9 | 4.18 | **6.04** | **9.41** |
| P2 关美白 | 磨皮 100 / 美白 0 / 下巴 7 | 4 | 33.41 | **33.41** | **37.63** |
| P3 关下巴 | 磨皮 100 / 美白 45 / 下巴 0 | 4 | 35.80 | **35.80** | **39.81** |

- 磨皮链本体 ≈ **30.6 ms**（36.68 → 6.04），占引擎时间 84%
- 美白 45 ≈ **3.3 ms**（36.68 → 33.41）
- 下巴 7 ≈ **0.4–0.9 ms**（对比同轮 P0 的 36.16 为 0.36；对比两轮合并值 36.68 为 0.88），已在噪声内
- P2 / P3 的第二轮因跨边界被全部剔除，各只有 4 个窗口，置信度低于 P0

## 4. 结果二：磨皮档位成本曲线（`ladder`，every=2）

| 磨皮档位 | 引擎 proc | 合计 proc |
|---|---|---|
| 100 | 38.02 | 42.08 |
| 70 | 40.53 | 44.63 |
| 50 | 34.99 | 38.81 |
| 30 | 35.35 | 39.41 |

只取第一轮（4 段均 0 无脸帧；第二轮被摄者离场，全部判样本不足）。

**档位与成本没有单调关系**：30/50/100 都在 35–38，70 反而最高。极差 5.5 ms 与同档位
重复测量的波动同量级。结论是成本由「磨皮是否 > 0」这个开关决定，不由档位决定。

## 5. 结论

1. **A 方案的两个抓手没有空间**：当前面板 `global_sharpen = 0`、五项妆容全 0，本来就不耗算力。
2. **剩两个零改动旋钮各自的量级是 3.3 ms 与 0.4–0.9 ms**。两个全关只能到 39.0–40.0 ms 量级，
   仍是 33.3 ms 的 1.17–1.20 倍。**只调面板不可能回到 30 fps。**
3. **降磨皮档位不省时间**（第 4 节）。要省只能把磨皮设成 0，那等于关掉产品本身。
4. 因此零改动旋钮**已用尽**。要再往下走只有三条路：改代码（渲染线程整帧拷贝、`blendWithMask`
   全帧遍历、surface3 的分辨率/ROI）、换成本模型（GPU 版）、或接受当前帧率。
5. **附带证伪**：昨晚「预览窗口低是编码器负载叠加」不成立。本轮 `probe` 段全程**未录制**，
   合计仍是 47.59 / 49.37 ms，比昨晚录制区间的 45.46 还高。预览与录制的差异来自画面内容，
   不是编码器。
6. **续篇**：编码器参数这一项也已验证，见 `05_验证/ab20261109_encoder_f1.md`。
   p5 → p2 并关掉 lookahead / multipass / b-frames，编码跳过率没有改善。
   加上这一项，零改动旋钮才算真正穷尽。

## 6. 局限与未验证

- 被摄者在两轮测试中多次离开画面（`P1` 469/900、`ladder` 第二轮 720/720 无脸），
  可比较窗口被打散，P2/P3 只有单轮样本。
- `ladder` 第二轮 00:17:44 → 00:19:12 有约 88 s 没有任何「性能」行，原因未查明
  （可能画面源停止渲染，也可能是采集卡重连）。这段时间的窗口全部丢弃。
- 美白 3.3 ms、下巴 0.4–0.9 ms 都是**差值**，没有做逐相位重复到统计显著。
- `0.7 ms` 的 memcpy 折算值未实测。
- 仓库 HEAD 仍是 `b92d042`，但工作区有未提交改动；本轮测的是装机 DLL
  `1d0b52f2…`，**HEAD 哈希不能标识被测二进制**。
