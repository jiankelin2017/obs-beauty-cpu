## 1. 结论先行

- **「指标改善」不等于「观感改善」**（`c17` §5.5）：这类优化**无法用看画面做 A/B**，
  必须靠离线指标；反过来，指标动了也不代表用户能看出来。
- **所有基于 `face_src` 的离线结论不可外推到真机**（`c19`）：离线素材是单张脸的裁剪，
  真机的白平衡、机位、脸宽都不同。
- **口径纪律**：不同统计区域的读数**不矛盾但不可混用**，见 §2。
- **证伪链终点**：「真机磨皮不足」的最终根因是肤色椭圆中心不随白平衡自适应，
  `c19` 的中间根因已被 `c20` 推翻；落地见 `docs/design/design-face-mask.md`。

## 2. 口径纪律（读任何历史数字之前先看）

- `c14` §4 与 `ab-metric`：**全掩码平均**会被大量非皮肤像素稀释，**分区细纹理频带**才回答「核够不够强」；
  两套读数不矛盾，但**绝对不可混用、不可相减**。
- `ab-metric`：「ROI 全区域」读数受块均值稀释，只能回答整体观感，不能回答核够不够强；
  旧比较区域里过半的「差异」来自白蕾丝上衣和背景衣架，**不是皮肤**。
- `ab-metric` 自述样本量只够判断方向、不够精调参数；`ab-mask` 的有效场景全是同一张脸的扰动。
- `c08`：「小幅度高频保留%」指标本身不可靠，应用「脸颊台阶像素占比」替代，
  见 `docs/design/design-smoothing.md` §3。
- `ab-smooth`：离线基准 DLL `blur_type=1` 的输出**不是产品真值**，两套口径不可混用；
  曲线 RMSE 是「曲线拟合」而非「结构同一性」。

### 2.1 产品真值基准与验收判据（口径定义，非验收数据）

本小节只登记「拿什么当基准、按什么算达标」这两条口径。它们此前只存在于
`.gitignore` 排除的历史真值件与归档件里，当前版文档体系没有继承；本节按
第 5 批裁定**不搬任何历史实测数字表**，也不给当前轴下验收结论。

- **产品真值档 = 不下发 `blur_type`**，等价 bundle 裸默认 `bt2`。第三方产品从不下发
  该参数；`ref_golden.dll` 显式下发 `bt1` 生成的 `goldens_legacy/flat/` 快照不是
  产品真值 (`docs/archive/ab-smooth-20261106.md`)。`01_源码/beauty_core.cpp` 在
  `smoothModel` 默认值旁亦写明「加密 bundle、不下发 blur_type = bt2」。
- 因此 `05_验证/real_frame_eval.py` 做对齐对拍必须显式传 `--gold-bt -1`；默认值 1
  只为兼容旧资产。产品真值金标的文件名后缀是 `_btM1`（`bt_suffix(-1)`），
  与 bt1 的旧金标是两份不同资产。
- **验收判据的口径**（标定于历史轴，是判据定义而非当前轴实测值）：单帧版为
  真机帧掩码内改动量 ≈ 2.03（±3%）、空间相关 ≥ 0.82、像素级 RMSE < 2.0、
  平坦/纹理改动比 ≥ 1.0；真机多帧版为各档改动量偏差 < ±8%、flat/tex 比
  1.25~1.45、75 与 100 档输出必须不同、100 档 RMSE < 2.0、空间相关 ≥ 0.80，
  并建议把 flat/tex 门槛由 ≥ 1.0 提高到 ≥ 1.25。原件见
  `04_文档/01_第三方磨皮真值.md`（`.gitignore` §10 排除件、不入库）与
  `docs/archive/ab-smooth-20261106.md` 更正块。
- ⚠️ **量纲隔离**：上款的 RMSE 是真机帧**掩码内的像素级** RMSE，由
  `05_验证/real_frame_eval.py` 计算；`05_验证/core_vs_sdk.py` 报的则是 `face_src`
  合成图上「档位细节保留率曲线」的**百分点** RMSE。两者素材、量纲、代码轴都不同，
  **不可比、不可互推达标**；曲线口径从未定义过达标阈值。
- ⚠️ 这些判据标定于历史轴 `3.1.x`，CPU `1.0.0.0` 未重测，见本文 §8 第 1 项。
  本小节只解决「口径查不到」的问题，**不改变任何验收状态**。

## 3. 证伪链（按时间顺序，只看结论）

1. **`c14` §5 五条假设全部被证伪**：`freqMagHi` 天花板 / 五官保护挡住唇纹 /
   掩码没盖到额头 / 加大迭代次数 / 羽化削弱——都不是差距来源。
2. **`c16`**：默认档位下**痘印不是差距来源**；用户看到的「痘印没了」更可能是第三方开了祛斑痘，
   真正该动的是**祛斑痘默认值**（面板默认 0）。
   方法论必须保留：**没有因变量就测不了、100% 保留也算假通过**（合成阳性样本的用处是证明指标有响应）。
3. **`c17`**：**「档位→尺度联动」假设错误**，加大低通尺度反而更差；真正主导的是幅度门控上限
   `freqMagHi`（环境变量 `BEAUTY_FREQ_MAG`）。§5.5「指标改善 ≠ 观感改善」是本组最重要的结论；
   §6「阴影频带双尺度缺口」属**新功能、未实施**。
4. **`c18`**：核尺度是**绝对像素常量、不随脸宽缩放**，固定值换分辨率 / 机位即失效；
   §5 可比性风险（`NamaGoldenRun`（历史轴离线脚本，非插件源码符号）后四参数、真机第三方默认配置未知）**这条从未核实**。
   放大图上看到的「变细」是**插值假象**，`c19` 已用真实素材修正。
5. **`c19`**：曾把真机磨皮不足归因于「核尺度不随脸宽缩放」——
   ⚠️ **已被 `c20` 推翻，不得据此施工**。仍有效的是它的方法论：
   `face_src` 离线结论不可外推、真机 0 档帧可作离线对拍输入（core 全 0 时逐字节透传）、
   不同时刻抓拍的截图信噪比不足、无法定量。
6. **`c20` → `c21`**：最终根因是肤色椭圆中心写死、不随摄像头白平衡自适应，
   解释了 `c17`「削过头」与 `c19`「削不够」为何方向翻转；已落地 `estimateSkinCenter()`。
   `c20` §5「候选修法」由 `c21` 落地，§7「下一步建议」属过程记录。
   `c18` §4「核尺度随脸宽自适应」的落地方向**未被采纳**。

> **引用规则**：`c19` 的根因段落只能作为「曾被推翻的中间结论」引用；
> 任何施工、调参、复现实验都必须以 `c20` / `c21` 与 `docs/design/design-face-mask.md` 为准。

## 4. 仍然有效的局限与坑

- `c20` 四条局限：单帧单摄像头、掩码占比是反推值、**掩码修好 ≠ 削对频段**、偏色并不极端。
- `c21` 三项遗留（未在当前轴复核）：高档位细纹理矫枉过正、阴影频带双尺度缺口、高档位耗时。
- `c14` §6「未实施候选」、`c20` §7「下一步建议」、`c17` §5「建议改动」**均属过程记录**，
  且 `c17` 的建议已被 `c20` / `c21` 路线取代。
- 应急调参口径：只调 `BEAUTY_BLUR_SAT`，不动核参数（`c21`）；不要动 `freqMagHi` 追强度（`c15`）。

### 8.1 产品真值画质复测（2026-11-06 · 8 帧判据复测 · 待人工确认）

本小节只登记「两批各测了什么、哪些判据过线、哪些没有」，按第 5 批裁定
**不写实测数字、不搬数字表格**；报告、逐帧指标与复现驱动都在 `05_验证/goldens/masks/`，
该目录被 `.gitignore` 忽略、不入库。口径按本文 §2.1：产品真值 = 不下发 `blur_type`
的 `btM1` 金标，判据是真机帧掩码内的**像素级**指标，与 `05_验证/core_vs_sdk.py`
的曲线百分点 RMSE 不可比。第二批补齐了第一批缺的资产与分类器。

- **复测条件**：第一批为单帧 `cam` 加真机 8 帧共 9 组；第二批为同一批真机 8 帧，
  按 25/50/75/100 四个档位逐组独立子进程、串行执行。两批的引擎都用
  `beauty_core_test.dll` 的默认磨皮核，不覆盖 `smoothModel` / `s3Band` 等开关；按
  `docs/design/design-face-mask.md` §3 关闭 EMA 以保证逐字节确定性。全程离线，
  **未启动或关闭 OBS、未采集新帧、未拉起 beauty.exe**；第二批由 `ref_golden.dll`
  在本脚本拉起的独立 Python 子进程内直接调用 SDK 封装生成 25/50/75 档产品真值金标，
  并用同批新生成的 100 档金标与 2026-10-30 的现成资产逐字节自检，全部一致后才
  采信补生成档位。这一点更正了第一批「未加载 `ref_golden.dll` 与 NamaSDK」的旧记录。
- **判据判定结果**：8 帧判据现已逐条跑完。各档改动量偏差、100 档平坦/纹理比、
  75 与 100 档输出必须不同、100 档像素级 RMSE、按 8 帧均值判的 100 档空间相关，
  这五项通过或数值过线；「平坦区与纹理区各自改动量比值」这一**建议项未通过**，
  两类区域都低于判据下限，但我方平坦/纹理比仍与产品接近，报告据此判断为结构
  选择性的形状对齐、整体强度偏低，成因本轮未查，不作推断。
- **两处必须单独说明的现象**：其一，我方 25 档在 8 帧肤色掩码内的改动量恒为零，
  即低档实际零响应；该档只是因为产品侧改动量本身接近零、绝对差小于判据容许值
  而数值过线，相对偏差并不小，**不能读作低档行为已对齐**，成因本轮未查。其二，
  上述建议项未通过是真实结果，不因其他判据过线而抵消。
- **资产与分类器已补齐**：第一批记的「缺 25/50/75 档产品真值金标」与「源图灰度
  局部标准差分类器未复刻」两项，第二批都已补齐。分类器逐字复用历史
  `flattex_eval.py` / `split_eval.py` 的 5×5 σ 定义，没有改用 `sdk_base.py` 的
  3×3 拉普拉斯代理，遵守真值文档「换分类器不许跨口径比」的禁令。
- **仍然存在的边界**：单帧版判据标定于历史轴 `T=8.3`，而本轮 DLL 默认 `T=6.5`，
  参数已变，单帧结果只记录数值位置、不下达标或不达标结论；本轮只测引擎层离线
  输出，不含插件层帧 I/O 往返，也不等于真机端到端画面。整套判据标定于历史轴
  `3.1.x`，是否完整沿用至 CPU `1.0.0.0` **待人工确认**。
- **状态边界**：根 `README.md` §8 第 3 项**仍不能关闭**，因为真机端到端对拍、
  少核机器与多人脸场景仍未做，且本轮有判据未通过。`docs/CHANGELOG.md` §1.1 第二层
  现已把「画质 golden A/B 复测」登记为「已完成（离线复测）」，并明确标注
  「不构成完整画质验收」；`1.0.0.1` 的补充 A/B 见 §8.2。无论措辞如何，
  第二层的验收判定维持原状，本小节不构成验收结论。

### 8.2 `1.0.0.1` 低档段重标定 A/B（2026-11-06 · 待人工确认）

本小节登记 `1.0.0.1` 候选的离线 A/B；报告、逐帧指标与复现驱动都在
`05_验证/goldens/masks/` 下的 `quality_ab_1001_20261106` 三件套（被 `.gitignore` 忽略、不入库）。
产品真值口径仍按 §2.1：不下发 `blur_type` 的 `btM1` 金标。

- **条件**：A 组 = 重编译 DLL + `BEAUTY_S3_LV_SHAPE=0`（旧五锚点表）；B 组 = 同一 DLL +
  默认 `=1`（新增七锚点非均匀表）；C 组 = 改动前备份 DLL。每帧一个独立子进程，
  8 帧 × 25/30/40/50/75/100 六档，避免同一进程内 `WinDLL` 句柄复用导致环境变量只首次生效。
- **结果**：25 档改动量 `0.00000 → 0.01024`（产品 `0.00994`）、非零帧 `0/8 → 8/8`；
  30 档 `0.00178 → 0.08011`、40 档 `0.19278 → 0.17496`，均更接近产品真值；
  50/75/100 档 A 与 B `8/8` 逐字节一致，A 与 C 六档 `8/8` 逐字节一致，
  证明新表只动低档段、回退分支可信。
- **判据**：§2.1 的 6 行硬判据改动前后均 `6/6`；建议项「两类比值各自
  `0.95~1.05`」改动前后都是 `0.917 / 0.910`，**仍未通过**。改动前的
  「25 档绝对差 < 0.02」是数值假象：我方恒为 0、产品改动量本身接近 0，绝对差自然过线。
- **幅度不等于结构**：25 档像素级 RMSE 由 `0.0997` 升到 `0.1244`，空间相关由
  无定义变为 `0.2342`；§2.1 未对该档设这两项门槛，故不算判据失败，但这两列
  **不支持「低档画质已对齐」**。30/40 档为判据外观察。
- **边界**：本轮只测引擎层离线输出，不含插件层 `gs_stagesurface_map` 下载与
  `gs_texture_set_image` 上传往返；未启动或关闭 OBS、未采集新帧；判据标定于历史轴
  `T=8.3`，本轮默认 `T=6.5`。`1.0.0.1` 安装包、装机脚本与真机装/卸回归**均未执行**。
- **状态**：本小节只登记复测结果，**不构成画质验收结论**；根 `README.md` §8 第 3 项
  与 `docs/CHANGELOG.md` §1.1 第二层的验收判定维持原状。
