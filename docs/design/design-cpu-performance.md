## 1. 结论先行

当前 CPU `1.0.13.0` 的性能底座 = **ROI 裁剪 + 按行多线程 + 去掉全分辨率 RGB 中间缓冲 + 合并掩码统计遍历 + 并行粒度按块宽算 + A 通道在引擎内一次做完 + 色调整帧走整数复合表 + A 通道并进色调写 + 跳过用不到的中频盒式 + 磨皮盒式三通道融合与 SSE 垂直趟**，不上 GPU。

- 此前「CPU 到不了实时、必须 GPU 化」的判断，前提是「现实现已优化过」；实际不成立 —— 优化前是**单线程 + 全帧**。
- 四项优化的共同点是「不再计算随后会被丢弃的东西」或「少写一份中间缓冲」，**不改变任何像素的输入**，因此画质逐字节不变（判据见 §5）。这不是拿画质换性能。
- **路线决策**：用户明确走纯 CPU；当前口径是不引入自定义 shader / hlsl / GPU 计算管线，美颜算法全在 CPU buffer 上完成。`obs-beauty.cpp` 的 `gs_texrender / gs_texture_* / gs_draw_sprite` 是 OBS 滤镜框架的帧 I/O 通道，不算 GPU 计算依赖。
- ⚠️ **本文不提供任何可直接对外引用的性能数字**：历史轴耗时 / 加速比 / SHA256 全部测于 `3.1.x`，**从未在 CPU `1.0.0.0` 上重测**（待人工确认）；§2.5–§2.11 的当前轴数字仅作内部取证，且其中绝对数已于同日判作废。两者都不得用于对外宣称或作为当前验收依据。

## 2. 四项优化（机制与不变量，`01_源码/` 复核）

### 2.1 ROI 裁剪

- **问题**：磨皮在全帧上跑，而掩码只覆盖人脸区域；`blendWithMask` 在 `mask[i]==0` 时逐字节还原原图，**根本不读磨皮结果**。全帧算出来的绝大部分像素随后被直接丢弃。
- **做法**：新增 `bilateralRgbaRoi()`，只在掩码包围盒（外扩 `radius+1`）内计算。
- **不变量**：双边滤波逐像素独立，每个输出像素只依赖原图 `src` 的邻域；裁剪 ROI 不改变任何像素的输入，只是不再算那些会被丢弃的像素。
- ⚠️ **坑**：ROI 必须覆盖所有 `mask!=0` 的像素并留够 `radius` 边距，否则边界像素的邻域会被切断。

### 2.2 多线程按行切分

- 行与行之间没有数据依赖；按 ROI 的行范围切成 N 块，每块一个 `std::thread`。
- 线程数策略：默认取 `hardware_concurrency()`、上限 8（超线程对内存密集的滤波帮助很小），且每线程至少 16 行、总行数少于 32 时退回单线程 —— 线程创建 / 汇合有固定开销，行数太少时纯亏。
- ⚠️ **与异步检测联动**：异步开启且磨皮线程数未显式指定时，源码会自动把线程数降为 `hardware_concurrency()-1`（核多时上限 8）留一核给 worker，详见 §8.2。做性能对比时必须把这个副作用计入口径。

### 2.3 去掉全分辨率 RGB 中间缓冲

- 原流程：`src(RGBA)` → `rgb_(w*h*3)` → letterbox → `640×640`。检测只吃 `640×640`，却先把整帧转成一份 RGB —— 那一步是纯浪费。
- 改为 `letterboxRgb(..., stride)` 直接从 RGBA 源取样（`stride=4`），一次遍历出结果。

### 2.4 合并掩码统计遍历

- 原先掩码生成完还要扫两遍全帧：一遍数像素（`maskPixels_`），一遍求包围盒（`maskBounds`），**全部只为了打诊断日志**。
- 改为在写掩码时顺带统计：用「只有从 0 变 255 才计数」避免脸框与脖子通道重叠处重复计；用 `any` 标志只在真的落了像素的行上扩 bbox，否则脸框下沿没肤色的几行会把包围盒拽满。

### 2.5 并行粒度：块宽同时是任务数（1.0.8.0）

**结论先行**：`runRange(a, b, threads, fn)` 的并行度只由 `b - a` 决定，而且内部有
「每线程至少 16 行」的硬约束（`effectiveThreads`）。所以凡是用「列块」当并行单位的地方，
**块宽就直接决定能开几条线程**，跟像素总量无关。

- **踩过的坑**：`boxPlaneV` / `bandBoxV` 的块宽取 32，理由是缓存（32 列 × 4 B = 128 B = 2 条
  cache line，行内连续）。半分辨率 ROI 的平面宽只有 384 左右 → `nblk = 12` → `12 < 32` →
  整个垂直 pass 被判成**单线程**。垂直 pass 是磨皮里最重的一段（13 平面 × 3 趟 × 3 组），
  自双尺度带通上线起一直只占一个核，而日志里「多线程已开」看起来一切正常。
- **改法**：块宽 32 → 8。同样宽度得到 48 个任务，3~6 线程。每块每行只读 32 B
  （cache line 用一半），用带宽换并行，实测净赚 −34%（磨皮 ROI 10.64 → 7.04 ms）。
- **不变量**：分块方式**不改变任何像素**。每块自己维护列和，`kFlush` 重算点按全局 `y`，
  块与块之间无依赖 —— 已在 `f1.raw` / `probe_in.raw` / `up10.raw` 三份素材上验到逐字节相同。
- **同类门槛**：`surface3RgbBand` 的 `bt = (np >= 150000) ? threads : 1` 也踩了同一个坑 ——
  150000 正好卡在半分辨率 ROI 的临界区间（14.6~18.4 万），人脸稍小就整段退回单线程。
  已改成 8192。**教训：任何「像素数阈值」都要先算一遍生产场景的实际取值**，卡在临界点上
  等于随机的性能。

### 2.6 A 通道置位的归属（1.0.8.0）

- 原位置在插件层 `obs-beauty.cpp`：引擎返回之后，对 `buf_out` 跑一遍 207 万次 32 位读改写
  （1080p 约 0.4 ms），只为了把 alpha 置 255。
- 挪到引擎 `CoreEngine::process()` 的返回点（`forceOpaque`，SSE2，一次 4 像素）。数据此刻
  刚被本帧写过、还在 cache 里；插件层那遍删除。
- **保留的一处**：面板全 0 时插件不调引擎（`allZero()` 直接 memcpy），那条分支仍有一份标量版。
  它只在上传段跑，而且只在用户把 11 个滑块全拉到 0 时发生。
- **不变量**：语义与原来完全一致（无条件全帧、在引擎输出之后、A 恒为 255），
  `dumpOut` 逐字节相同。
- **1.0.10.0 真机复测**：美形+alpha 段 1.42（A 在插件）→ 2.17（A 在引擎），上传段
  1.61 → 0.64；两段之和 3.03 → 2.80，净省 0.2 ms。方向正确但不显著，保留是因为
  它同时删掉了一整遍插件层全帧循环。

### 2.7 色调整数复合表（1.0.11.0）

- 场景：清晰 / 美白 / 红润三段默认**整帧**跑（`BEAUTY_TONE_GLOBAL=1`），1080p 是
  2.07 M 像素。原来的实现已经预展开成 3×256 项浮点表，但每像素仍要做 3~9 次
  浮点线性插值（`tab()` 里有 2 个分支 + 1 次 float→int）、6 次 byte↔float 往返。
  真机实测这一段 4.6 ms，仅次于磨皮。
- 关键观察：整帧模式下 `sk ≡ 1.0f` 是常量，于是「清晰→美白→红润」对某个通道
  就退化成**只取决于输入字节的纯函数** —— 输入 0..255 只有 256 种，输出也只有
  256 种，可以整条链预计算成一张 `uint8[256]`。每像素只剩 3 次查表 + 3 次存。
- **逐字节等价的前提**：表内算式必须与原逐像素版**逐字相同**。特别地，
  `r += (tab(tC, r) - r) * 1.0f` 不能手写成 `r = tab(tC, r)` —— 后者代数等价、
  浮点不等价（`tab - r` 再加回 `r` 有舍入差异）。同理 rosy 的 `* rosy * 1.0f`
  也不能省。
- 只在 `global && toneIntLutOn()` 时走表；掩码回退模式（`BEAUTY_TONE_GLOBAL=0`）
  里 `sk` 随像素变，没法查表，保持原路径。
- 代价边界：这条路径已经把工作压到「读 8.3 MB + 写 8.3 MB」，**内存带宽受限**，
  并行和向量化都不再有意义（SSE2 没有 byte gather，做不了查表向量化）。
- 台架：全开 36.85 → 31.05 ms（−5.79，四轮交替中位数）；三份素材输出逐字节相同。
- **真机（P/Q 两组，各录 28 秒）**：色调 **4.56 → 0.84（−3.72）**，引擎 14.66 → 10.89，
  全链 18.35 → 13.47（**−4.88，−27%**）。引擎差（3.77）与色调差（3.72）几乎相等，
  说明没有副作用外溢到磨皮/细节/美形那几段。真机比台架少省 2 ms，是因为真机上
  2.07 M 像素的读写要和编码器抢内存带宽。

### 2.8 下载零拷贝（1.0.11.0，默认关闭）

- 下载段 = `gs_stage_texture`（GPU→staging）+ `gs_stagesurface_map`（**含 GPU 同步**）
  + 一次 8.3 MB 整帧 memcpy。真机 2.1~3.3 ms，其中同步等待占大头。
- 做法：`linesize == cx*4`（行内无 padding）时把 map 出来的指针直接当引擎输入
  （`in_p`），省掉 memcpy。map 必须持有到引擎与细节自检读完，因此 unmap 延后到
  第 4 步之前 —— **必须在 self-check 之前**，那里会再次 `gs_stage_texture + map`
  `f->stage`，surface 还锁着那一步会失败。
- **默认关，`BEAUTY_ZERO_COPY=1` 才开**，理由是一个只能实测的风险：staging surface
  映射出来的内存往往是写合并/非缓存的，而引擎在掩码、磨皮、色调、细节四个 pass
  里会反复读同一片输入。省 0.6 ms 拷贝，可能被加倍的读取开销吃掉。
- 另一处必须处理：引擎失败的提前返回路径持有着 map，那条分支要先 unmap，
  否则 surface 一直锁着，下一帧 `gs_stage_texture` 会失败。
- unmap 的耗时计进「下载」那一段，否则零拷贝会把成本藏到引擎里，账面看起来像白赚。
- **真机判定（P/R 两组，各录 28 秒）= 证伪，默认保持关**：

  | 项 | P（拷贝） | R（零拷贝） | 差 |
  |---|---|---|---|
  | 下载 | 2.04 | 1.46 | **−0.58**（组内抖动仅 ±0.13，省得干净） |
  | 引擎 | 10.89 | 11.30 | +0.41 |
  | 上传 | 0.67 | 0.86 | +0.19 |
  | 合计 | 13.47 | 13.75 | **+0.28（更慢）** |

  两组 ROI 面积几乎相同（掩码 111k vs 102k），引擎那 +0.41 不是 ROI 差异。
  这正是上面预判的那条：非缓存内存被反复读，省下的一次顺序 memcpy 不够填。
  **代码留作开关不删** —— 换驱动/换 GPU 结论可能不同，成本只是一个 `if`。


### 2.9 A 通道并进色调写（1.0.12.0）

- 场景：`forceOpaque` 在管线最末端做一遍整帧 207 万次 32 位读改写，只为了把 A 置
  255。1080p 就是 8.3 MB 读 + 8.3 MB 写，真机实测约 0.75 ms（1.0.10.0 的 E 组
  `st_[4]` 2.17 vs G 组 1.42 之差）。
- 观察：色调整帧整数表分支（§2.7）本来就要逐像素读改写同一片内存。A 是同一
  cache line 里的第 4 个字节，顺手写是零边际成本 —— 而且写成一次 32 位存比
  「3 次查表后 8 位存 + 1 次 A 存」还少一半访存。
- 接口：`toneColor` 返回 `bool`，`true` = 「整帧每个像素的 A 已置 255」。只有
  「整帧 + 整数表」分支返回 `true`；三段全 0 的提前返回、掩码模式、浮点模式都
  返回 `false`，由调用方兜底跑 `forceOpaque`。
- **等价性依赖三件事实**（都逐条查过代码）：
  1. `applyFaceRegions`（五官五项）对 A 是 `dst[o+3] = src[o+3]`，保持原值；
  2. 细节回填（`detailRefill`）同样只写 RGB；
  3. `warpFace` 对 `c < 4` 一起做双线性插值 —— 255 与 255 插值仍是 255，边界
     clamp 取到的也是 255。
  台架用「磨皮 100 / 美白 45 / 下巴 7」的真实配置（下巴 7 会真的触发 warp）复验，
  输出与 1.0.11.0 逐字节相同、A 全 255。
- 不能省的一步：`alphaDone = false` 时必须照旧跑 `forceOpaque`。无脸帧（色调不跑）、
  三段参数全 0、`BEAUTY_TONE_GLOBAL=0`、`BEAUTY_TONE_LUT=0` 四种情况都走兜底。

### 2.10 跳过用不到的中频盒式（1.0.12.0）

- 场景：`detailRefill` 算两个频带 —— 细频 `hf = lum − b3`（3×3）、中频
  `hm = b3 − b7`（7×7）。为了这两个带，它要跑 4 趟盒式（3×3 的 H/V 与 7×7 的 H/V）
  外加 1 趟亮度转换。
- 但 `hm` **只在 `p.mid` 或 `p.globalMid` 非 0 时被读**。而生产的基准回填
  （`blurRefill`）把 `dp.mid` 明确写成 0（只还细频、不碰中频），全局锐化关时
  `dp.globalMid` 也是 0。此时 7×7 那两趟纯属白算：整片 ROI 再扫两遍，还多写满
  一个 `np` 大的 float 平面。
- 做法：`needMid = (p.mid != 0 || p.globalMid != 0)`，为 false 时不跑那两趟；同时把
  `hm` 的计算从循环体顶部挪进 `if (mwF != 0.0f || mwG != 0.0f)` 分支 —— 那里
  `mwF/mwG` 双双为 0，分支进不去，绝不会解引用未填充的 `b7`。
- 逐字节等价：跳过的只是「不会被读的中间结果」，输出与原来完全相同。
- **生效条件**：脸内锐化与全局锐化**都关**时才跳得掉。`detailMidGain` 默认 3.30，
  只要 `sharpen > 0`，`dp.mid` 就非 0，7×7 必须算。这不是缺陷 —— 中频带确实要用。
- 实测（真实面板复刻：磨皮 100 / 美白 45 / 下巴 7）：全开 16.13 → 14.44 ms。
  这个数含 §2.9 的贡献，两处合计 **−1.69（−10.5%）**，五轮交替区间不重叠。

### 2.11 磨皮盒式三通道融合 + 垂直趟 SSE（1.0.13.0）

**先说清磨皮到底跑的是哪条路**——这一步之前搞错过，代价是整轮白做：

| 冒烟判据 | `surface3`（默认 1，3.1.17 起） | `lowPath=3`（路线 C） |
|---|---|---|
| 谁在跑 | `surface3RgbBand` → `bandBoxN` → `bandBoxH/V` | `highLowSmooth` → `boxRgbRoi` → `boxPlaneH/V` |
| 触发条件 | 默认 | 只有 surface3 关掉且 `lowPath=3` 时才用 |
| 盒式组数 | b1 三平面 + b2 三平面 + amp 单平面，各 nPass 轮 | 3 通道 × iters 轮 |
| 决定趟数的旋钮 | `s3Passes` | `BEAUTY_BOX_ITERS` |

**判据**：扫 `BEAUTY_BOX_ITERS=1/2/4`，磨皮耗时若一条直线，说明你没在改 `boxRgbRoi`
（它没跑）；`BEAUTY_BOX_TRACE=1` 会往 stderr 打印入口，一次都没打印就是证据。

改动本身（`bandBoxHImpl<N>` / `bandBoxVImpl<N>`，`N ∈ {1,3}` 编译期常量）：

- **H 趟融合**：通道循环从 `x` 外层搬进内层，N 个累加器共享同一对 `(add, rem)` 与同一
  个 `kFlush` 重算点；`x % kFlush` 换成倒数计数器。每个平面的 float 累加序列一字不改。
- **V 趟 SSE**：块内一次算 4 列，`loadu/add/sub/mul/storeu`，尾部不足 4 列走标量。
  逐 lane 与标量同序，且这里没有 FMA 形态（不存在「少一次舍入」的差异）。

回退：`BEAUTY_BOX_FUSE=0` 走 `bandBoxHRef / bandBoxVRef`（原实现），逐字节等价。

台架（60 帧/档，8 轮交替，`BENCH_PROFILE` 复刻真实面板）：只开磨皮 7.86 → 6.69
（−14.9%），全开 15.10 → 12.27（−18.7%），8/8 轮配对全赢、区间不重叠。

**真机（同会话 S/F 交替 5 轮，13:42~13:50）**：磨皮 2.72 → 3.12 ms（fuse 开 → 关），
**−0.40（−12.8%）**，按 ROI 面积归一 −13.1%；引擎 5.60 → 5.97（−0.37）；下载 2.07
对 2.06（对照组打平，证明两组同状态）。相对降幅与台架一致，绝对收益只有台架的 1/5
—— 真机编码器占着核，`runRange` 的 8 条线程抢不满。

**这一节最重要的不是收益，是口径**：同一份 `fuse=off` 代码，13:13 测出磨皮 6.12、
13:44 测出 3.14。逐段比值显示所有多线程段齐降 1.8 倍，而单线程的人脸检测
（0.72 → 0.75）不变 —— 后台进程抢核的特征。**跨会话绝对值不可比**，详见
`05_验证/ab20261109_engine_stage.md` §11.4。

## 3. 已证伪路线与坑（别重试）

### 3.0b 「blurRefill 隔帧跑」做不到，别试（2026-11-09）

原本把「细频回填隔帧」列为 A7，预估省 0.3~0.6 ms。真正读代码后发现它不成立：

`blurRefill` 不是独立的一遍，它和「脸内锐化」「全局锐化」共用**同一次**
`detailRefill` 调用，只靠 `dp.fine` / `dp.mid` / `dp.globalFine` / `dp.globalMid`
四个权重区分。想让回填隔帧，就等于让整段细节回填隔帧 —— 锐化跟着变成 30 Hz，
在 30 fps 直播里是肉眼可见的「锐度跳动」。

真正的省法是 §2.10：**少算一个用不到的频带**，而不是少跑一帧。同样的 0.4~0.5 ms，
但零画质风险、可逐字节验证。

**教训**：把一项「优化」写进计划之前，先确认它在代码里是不是一个独立可调的单位。
按名字（`blurRefill` 听起来像独立开关）而不是按调用结构排计划，会排出做不了的活。

### 3.0 「1.0.8.0 比 1.0.7.0 慢 4 ms」是测量假象（2026-11-09 更正）

一度据此判过「A1/A2/A4 有害」。1.0.10.0 用 E/F/G/H 四组真机对照把这条推翻：

1. **H 组就是 1.0.7.0 的分工与并行参数**（`par_copy=0`、`alpha=plugin`、块32、阈值
   150000），它是四组里最慢的 19.02 ms，不是 10.4。
2. 磨皮耗时几乎完全由 **ROI 面积**决定（H 组五个窗口 ROI 从 297×270 涨到 561×291，
   磨皮 5.63 → 9.77）。跨组比中位数等于在比「这几组各自站得多近」。
3. 早期返回的帧不累加分段计时，分母却是全部帧数 —— **无脸窗口会把每一段同比拉低**
   （磨皮 5.57→1.21 时色调同步 4.58→0.93）。
4. 那条 10.41 的基线所在日志已被 OBS 轮转删除，无法复查，**基线作废**。

判据从此固定：只看 `无脸跳过 = 0` 且 `对齐 100%` 的窗口，并且先按 ROI 面积对齐。

### 3.1 降检测输入分辨率到 320 —— 在我们的模型上做不到

事实链：

4. 想真正降分辨率只有两条路：换原生动态导出的模型，或改 ONNX 的 `dim_param` 再重做 shape 推断；后者风险高 —— 网络内部的 `Reshape` 依赖具体尺寸。

**替代方案**：检测提速改走「推理多线程」`kInferThreads`，而不是降分辨率；不给满线程数是因为 OBS 的编码线程通常要占核，全占会掉帧。
`FaceDetector::setInputSize()` 保留但对固定 shape 的模型是**空操作**；`inputSizeFixed()` 可查当前模型是否锁死尺寸。

### 3.2 GPU 化推算已废止

- 其中**唯一仍成立**的是盲区提示：引擎层计时不含插件层 `gs_stagesurface_map` 下载与 `gs_texture_set_image` 上传往返；该开销在 CPU `1.0.0.0` 上**同样未实测**（待人工确认）。
- `BEAUTY_PROFILE=1` 埋点在当前源码仍存在（`01_源码/obs-beauty.cpp` 的性能埋点初始化与日志输出两处），但尚未在 CPU 版本轴上取数。

## 4. 为什么最终没上 GPU

- 用户 2026-10-28 的决定：**只优化 CPU，不上 GPU**；当前 `1.0.0.0` 沿用。
- 决策依据中仍有效的部分：磨皮 GPU 化本身跨厂商可行，真正的陷阱在**神经网络推理**那一环（CUDA 独占 / DirectML 已转入维护模式）；而 CPU 侧优化空间此前根本没被挖过。
- 代价面：GPU 方案需要画质全部重新标定、shader 不可调试、双后端验证。历史轴那版「CPU 优化后还剩多少差距」的推算数字已废止，见 `docs/archive/c1-cpu-performance-20261106.md`（`Deprecated`） §4。

## 8. 异步检测（第 4B 批并入，本批保留原文口径）

> 本节来自 `docs/archive/c10-async-detect-20261106.md`（`Deprecated`） 的归档头 + `01_源码/beauty_core.cpp` 逐字复核。
> **不搬历史轴计时、版本号与扫参表**；按 2026-11-06 裁定，历史验收数字只在 `docs/archive/` 归档件留存，不进当前版。
> 原归档件标 `Deprecated` 且「不得据此施工」；2026-11-10 重建于 `docs/archive/`，正文只在归档件留存。

### 8.1 结论与机制

检测从同步改为 **worker 线程 + `std::condition_variable` + `vector::swap`**：

- `g_cfg.asyncDetect` 默认开启（`beauty_core.cpp` 配置默认值）；`BEAUTY_ASYNC_DETECT=0` 一键回到同步。
- 结果交接用 `mask_.swap(async_.mask)` / `protect_.swap` / `faces_.swap` / `heldFrame_.swap`，
  是**零拷贝换手**，不是把掩码复制一份；改这里最容易破坏帧与掩码的对应关系。
- 掩码羽化 `BEAUTY_MASK_FEATHER` 与帧对齐 `BEAUTY_MASK_ALIGN=0` 是同一时期的配套机制，
  后者回到「当前帧 + 旧掩码」（有拖影但零延迟），专供 A/B 用。
- `BEAUTY_MASK_EVERY` 改异步提交周期；源码注释保留了退回老节奏的取值，
  便于真机当场对比多档而**无需改代码重编译**。

### 8.2 一个必须写清的副作用

异步开启且磨皮线程数未显式指定时，源码会把线程数**自动降为 `hardware_concurrency()-1`**
（核数多时上限 8），留一核给检测 worker。这不是「优化」，是**把尖峰换了个形状**：
不加这一条，检测帧会抢核、把磨皮那一帧拖慢。做性能对比时必须把该副作用计入口径。

### 8.3 确定性与盲区（坑）

- ⚠️ **异步会破坏逐字节确定性**：`core_probe.cpp` 在未显式设置时强制 `BEAUTY_ASYNC_DETECT=0`，
  注释写明「逐字节哈希会飘」。任何 golden A/B / 回归对拍都要显式关闭异步；
  另一处确定性要求是 `BEAUTY_SKIN_EMA`，见 `docs/design/design-face-mask.md`。
- `c10` §8 登记的两个盲区仍成立：**真机 60fps 端到端未验证**；插件层
  `gs_stagesurface_map` 下载 / `gs_texture_set_image` 上传（1080p RGBA 各 8 MB）**未计入引擎层计时**。
  这与 §7「未验证」清单是同一盲区，`BEAUTY_PROFILE=1` 埋点在当前源码仍存在，
  但**尚未在 CPU `1.0.0.0` 上取数**（待人工确认）。
