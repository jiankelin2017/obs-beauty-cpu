## 1. 为什么先采 SDK 再动手

这五项在 `goldens/` 里**一条基线都没有**（78 组只覆盖磨皮 / 美白 / 红润 / 锐化 / 清晰）。
没有参照就写算法，等于凭想象调参，"不降低画质"这条底线无从验证。

所以先用还能跑的 SDK（`ref_golden.dll`）现场采一遍：固定磨皮 50，逐项把参数拉到
100，与"该项为 0"的输出相减，差值图就是这一项的**真实作用域**。再对差值图做连通域
分析，取出每个作用域的中心、σ、方向、峰值 —— 几何参数是这样反解出来的，不是估的。

差分图：`06_离线验证/goldens/_probe/diff_view.png`（3×2 拼接，蓝=变亮，红=变暗）。

### 1.1 一条被实测推翻的假设

**"五官立体 = 大尺度 unsharp"是错的。** 拿 `Y − box(Y, r)` 去拟合 SDK 的立体差分图，
r 从 12 扫到 56，相关系数最高只有 **0.24**（r=56），残差 σ 基本没降。
它真是**按人脸几何画出来的 dodge & burn**：额头 / 鼻梁 / 双颊 / 下巴提亮，眼窝压暗。
所以实现走"关键点 → 软边椭圆 → 局部加减亮度"，不是滤波器。

## 2. 几何参数（全部归一化到人脸框）

坐标系：椭圆的 `cx/cy/rx/ry` 都是**相对脸框的比例**。`(0.5, 0.5)` 永远是脸框正中，
`0.1` 永远是"十分之一个脸宽"。这样同一套系数在 640×394 和 1080p 上落在同一个解剖点。

素材实测脸框 `x=277.2 y=89.5 w=107.4 h=133.7`（YuNet），5 个关键点归一化后：
右眼 `(0.377, 0.373)`、左眼 `(0.813, 0.409)`、鼻尖 `(0.614, 0.613)`、
右嘴角 `(0.367, 0.744)`、左嘴角 `(0.707, 0.774)`。

| 项 | 椭圆 | 中心 (cx, cy) | rx / ry | rot | 增益 | shade | feather |
|---|---|---|---|---|---|---|---|
| 五官立体 | 额头 | (0.568, 0.200) | 0.26 / 0.24 | 0 | +g | 0.30 | 0.50 |
| | 鼻梁 | (nsx, (e0y+nsy)/2) | 0.06 / 0.18 | 0 | +0.75g | 0.30 | 0.55 |
| | 双颊 ×2 | (0.273, 0.546) / (0.759, 0.526) | 0.20 / 0.11 · 0.11 / 0.10 | 0 | +0.80g / +0.70g | 0.20 | 0.55 |
| | 下巴 | (0.535, 0.905) | 0.08 / 0.05 | 0 | +0.70g | 0.20 | 0.55 |
| | 眼窝 ×2（**压暗**） | 眼心 +0.10 | 0.10 / 0.09 | 0 | **−0.55g** | 0 | 0.60 |
| 亮眼 | 双眼 ×2 | 眼心 | 0.10 / 0.055 | 0 | +g | 0.35 | 0.35 |
| 去黑眼圈 | 眼下 ×2 | 眼心 +0.075 | 0.095 / 0.045 | 0 | +g | 0.55 | 0.45 |
| 去法令纹 | 鼻翼→嘴角 ×2 | 连线中点 | max(0.55·len/fw, **0.13**) / 0.045 | atan2(Δy, Δx) | +g | 0.45 | 0.50 |

- `shade`：按 `(1 − shade·Y/255)` 加权，越大越只提亮暗部。眼白、高光不该继续被推。
- `feather`：`d < feather` 处满强度，`d = 1` 处 smoothstep 归零，避免硬边台阶。
- 增益（`regXxxGain`）见 §4。
- **关键点不可信时整组跳过**（`kpsSane()`：五点必须落在脸框外扩 50% 内），
  只保留不需要位置的祛斑痘。位置错了会把亮度糊到脸颊上，比不做更糟。

### 2.1 法令纹的旋转必须在像素空间算

脸框不是正方形（实测 107×141）。在归一化空间算 `atan2` 会歪 —— 因为 x 除以脸宽、
y 除以脸高，两个方向的缩放不同。所以 `Δdx = (mx − tipX) * fw` 先还原成像素再取角度。

---

## 3. 祛斑痘：不是模糊，是"拉回局部均值"

判据用**偏离局部均值的幅度落在 [thrLo, thrHi]**，而不是"所有偏离"：

- `|dev| < thrLo`（1.4）→ 皮肤本身的细纹理，动了就是糊
- `|dev| > thrHi`（30） → 真结构边缘（睫毛、鼻孔、唇线），动了出光晕
- 中间这一段才是斑 / 痘印的尺度

拉回量 `pull = −k · mask · dev`，`k = 0.25`。窗口 5×5。

**亮度取自当前 dst（磨皮/美白之后）**，不是原图 —— 用原图算会把已经磨掉的斑再"修"一遍，
等于白做。

**位置**：亮眼 / 黑眼圈 / 法令纹的纵向位置与 SDK 完全一致（质心 y 偏差 ≤ 0.01）。
**脸外改动像素 = 0**（softmax 掩码之外逐字节不变）。

### 4.1 三处未完全对齐，都有原因，不要拿单张图去补

1. **法令纹横向质心偏右 0.22 脸宽**（core 0.56 / SDK 0.34）。SDK 的左边界到 0.12，
   已经贴到脸框左缘，怀疑它的作用域还含嘴角下方的木偶纹。
   **只有一张素材，不做过拟合** —— 换张脸再定。
2. **五官立体 core 面积约为 SDK 的一半，p95 只有 +3.0（SDK +5.1）**。
   SDK 的明暗跨度更大（p5 −2.7 / p95 +5.1）。继续加 gain 会让均值从 +1.58 冲到 +2 以上，
   整脸发灰，所以停在 3.6。
3. **祛斑痘 core 的 dY 均值 −1.14（SDK +0.39）**。core 命中的暗斑（dev<0）比亮斑多，
   所以净效果是"压暗多于提亮"。这是图像本身的属性，不是符号写反了
   （p5 −5 / p95 +3 两侧都在动）。

## 5. 代价

| 分辨率 | 磨皮 50 基线 | + 五项全开 | 增量 |
|---|---|---|---|
| 640×394 | 2.03 ms | 3.48 ms | +1.45 ms |
| 1080p | 6.08 ms | 7.88 ms | **+1.80 ms** |

五项合起来 +1.8 ms，因为椭圆只扫并集包围盒（脸框的几成），祛斑痘只在掩码 ROI 内跑。
1080p 全功能（磨皮 + 美白红润 + 清晰 + 锐化 + 五项）合计约 13 ms，30fps 预算 33 ms 内。

## 6. 这一轮修掉的三个真 bug（都是"不报错、只对拍能看出"的类型）

### 6.1 椭圆整体左移了 308 像素

`applyEllipses` 的写指针从**行首**起算，但循环变量 `x` 从 `x0`（并集包围盒左边界）
起算。漏掉 `x0 * 4` 的偏移 → 整片椭圆画到画面左上角。

表现：亮眼的改动 bbox 是 `x[3,63]`，而眼睛在 `x=317/367`。y 完全正常（因为 y 没有
包围盒偏移问题），所以"看 x 不对、y 对"就是这个 bug 的特征。

```cpp
unsigned char* p = dst + (rowOff + (size_t)x0) * 4;   // 必须加 x0
```

### 6.2 祛斑痘的局部均值大了 5 倍

竖直方向先累加 5 行的列和，横向滑窗再累加 5 列 → `sum` 是 **25 个像素的和**，
却只除了 `win = 5`。结果 `mean ≈ 5 × 真实均值`，`dev` 中位数被撑到 **587**，
全部超过 `thrHi = 30` → **命中数为 0，祛斑痘完全没生效，而且不报错**。

修法是分母按**实际参与的元素数**算（边界 clamp 会重复边缘行/列）：

```cpp
const float invV = 1.0f / (float)(yB - yA + 1);      // 竖直：按实际行数
...
o[x] = sum / (float)cnt;                              // 横向：cnt 随窗口进出增减
```

### 6.3 法令纹的 rx 退化到 0.001

`rx = 0.55 × 连线长度 / 脸宽`。鼻翼与嘴角的 x 几乎相同（实测差 0.003 脸宽），连线
几乎是竖直的 → `rx` 退化成 0.001，右侧那条法令纹等于没画。
改给下限 **0.13 脸宽**：法令纹是**带状**不是线段，宽度得单独给。
