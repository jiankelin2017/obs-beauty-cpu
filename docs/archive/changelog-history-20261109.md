### `1.0.13.7` — 2026-11-09 · 修复：`1.0.13.6` 之后歪头 45° **还闪**

**结论**：`1.0.13.6` 判断对了三件事（丢检窗口、掩码保持、EMA 历史），但「闪」的直接原因
**不是丢检** —— 是**几何在一帧之内整个换掉**，那一条当时被我按「现状保留」放过去了。
用户装完 `1.0.13.6` 反馈「还闪」，这一版补的就是它。

**复现**（异步口径，真机默认；`face_src` 每 3° 一帧从 0° 转到 57°，三项形变拉满，
逐帧量「输出 vs 输入的平均差」`meanD` —— 它跳一下就是肉眼看到的那一下）：

| 帧 | 角度 | `roll` | `phi` | 框 | `meanD` | 单帧耗时 |
|---|---|---|---|---|---|---|
| f16 | 48° | 0 | +0.88° | 108×113 | 0.98 | 30 ms |
| f17 | 51° | 0 | −6.28° | 116×119 | 1.16 | **52.2 ms** |
| f18 | 54° | **−45** | **+45.72°** | 179×179 | **1.61** | 31.8 ms |

一帧之内 `meanD` +39%。两件事同时变：

- `phi` 从「关键点塌成水平」得到的约 0°（**YuNet 对 45° 倾斜脸的五个点会塌成一条水平线**）
  跳到真正倾斜的 45.7° —— 形变方向当场转 45°；
- `fw/fh` 从检测框（`roll == 0` 时是轴对齐外接盒）变成 `rw/rh`（紧框）：108×116 → 107×142。

单独一样都不该在一帧里发生，何况两样一起。

> 顺带确认：异步路径下**一帧都没丢检**。所以 `1.0.13.6` 缩小的丢检窗口没有打中这一枪 ——
> 那条改动本身没错，只是不是这个现象的原因。

**修法**（`01_源码/beauty_core.cpp`，新增「几何过渡」）

- `DetState` 新增 `geoLast` / `geoFrom` / `geoFadeLeft`。`geoLast` = 「上一次真正交给下游的框」，
  由 `buildMaskInto` 在交出前自己写。
  **不能用 `DetState::faces` 代替**：那是异步链路里由渲染线程 `collectAsync` swap 进来的，
  worker 在检测阶段读到的时序不确定 —— 第一版就是这么写的，实测首次 roll 锁定时它为空，
  过渡根本没起来（`from=0`，`left=0`，一帧都没插）。
- roll 从 0 切到 ±45（roll 探测命中）、以及从 ±45 退回 0（按方向角重检成功）时调
  `startGeoFade()`：记下切换前的框，置 `geoFadeLeft = 6`。
- `applyGeoFade()` 在随后 6 帧里按 `t` 线性混合**全部几何量**（中心、`rw/rh`、`roll`、
  5 个关键点）。`roll != 0` 的中间帧，盒的 `w/h` 由 `rw/rh` 与 `roll` 重算外接矩形 ——
  掩码是按 `rw/rh` + `roll` 画倾斜矩形的，ROI 与 `fw/fh` 却读 `w/h`，两边不一致就会错位。
- 过渡期间 `smoothFaceBoxes` 整体跳过：这 N 帧本来就在按设计轨迹挪动，再叠一层迟滞只会
  拽住它；EMA 还会把插值结果写进 `faceEmaPrev`，过渡一结束又往回拉。平滑改由
  `applyGeoFade` 负责，它在结束时把 `faceEmaPrev` 对齐。
- 只在「一对一」时插值：脸数变了（人走进来 / 第二张脸出现）两批框无法配对，硬切更安全 ——
  硬把 A 的几何拉到 B 上会得到一张不属于任何人的脸。

**验证**（同一序列）

| 项 | `1.0.13.6` | `1.0.13.7` |
|---|---|---|
| roll 锁定那段 `meanD` | 1.16 → **1.61（一帧 +0.46）** | 0.93 → 1.13 → 1.25 → 1.38 → 1.48 → 1.63（每帧 1/5） |
| 最大相邻帧跳变 | +0.46 | **+0.19**（与 0–45° 区间的自然漂移同量级） |
| 正立 8 种面板组合 | 基线 | **8/8 逐字节相同**（`000` 组合 MD5 仍 `0efa47d9cf6a5505848410dd6f5e35af`） |
| 270° 同组 | 7/8 DIFF | **仍 7/8 DIFF**（`1.0.13.5` 的美形修复不受影响） |

- **代价**：过渡的 6 帧内形变强度未到满值（几何还在追，末帧归位）；正立一分钱不付
  （`geoFadeLeft` 恒 0，`applyGeoFade` 直接返回，与旧版逐字节一致）。`roll` 探测那一帧的
  52 ms（±45 各一次 640×640 推理）本版没动，仍是「卡一下」的来源。
- **回退**：无开关（属缺陷修复）。要复现旧行为用 `02_构建\build_1.0.13.6\`。

### `1.0.13.6` — 2026-11-09 · 修复：歪头 45° 时画面闪一下 / 卡一下

**结论**：用户报「头立正没问题，歪到左右 45° 时画面过渡会轻微闪一下、卡一下」。这是**四件事叠在一起**，
只有最后一件是 `1.0.13.5` 留下的：

| # | 现象 | 机制 | 归属 |
|---|---|---|---|
| 1 | 闪一下 | YuNet 对 ≥40° 的倾斜脸直接检不出，要等 roll 探测接手；而 `kMaskHold = 6` 撑不住那段空窗（它是「丢检**次数**」不是帧数），第 7、8 帧掩码被清空 → 磨皮和三项形变整块停用 | `1.0.5.0` 既有 |
| 2 | 卡一下 | 接上那帧在 ±45° 各跑一次 640×640 推理，开销约 3 倍 | `1.0.5.0` 既有 |
| 3 | 闪第二下 | 框从外接盒 176.6×176.6 塌成紧框 107.5×142.2（面积差 2.04 倍），且 `resetFaceEmaState()` 清掉 EMA → 新框被「直接采纳」，没有任何过渡 | `1.0.5.0` 既有 |
| 4 | 频繁闪 | `\|cos(phi)\| >= \|sin(phi)\|` 判 `fw/fh` 要不要互换：45° 时 0.7085 vs 0.7057，**只差 0.4%**，关键点抖 0.2° 就判反（`fw` 107.5 ↔ 142.2，32% 尺度跳变） | **`1.0.13.5` 引入** |

第 4 条的根因是判据本身错：互换的物理原因是 `invRotateFace()` 在 `qi == 90 / 270` 时对调了盒宽高
（`beauty_core.cpp`），这是个**离散事实**。拿连续量 `phi` 去猜它，45° 处必然站在悬崖边上；
正立和 90/270 只是恰好猜对，所以只有歪头才暴露。

**逐帧实测**（`face_src` 旋转 45°，同步检测，逐帧喂）：

```
f00 无脸
...
f07 无脸          <- 连续 8 帧；kMaskHold=6 扛不住，第 7、8 帧掩码清空
f08 phi=44.92 roll=-45.0 w=176.6 h=176.6 rw=107.5 rh=142.2   <- roll 探测接上
```

那个 `8` 正好等于 `g_cfg.rollMiss` 的旧默认值。

**修法**

- `FaceBox` 新增 `int srcRot`（0 / 90 / 270），在 `invRotateFace()` 真正交换 `w/h` 的**同一处**置位。
- `beauty_warp.cpp` 改判据：有 `rw/rh` 直接用（它本身就是脸的宽高，**绝不互换**）→ `srcRot` 是
  90/270 才互换 → 否则原样。正立与 90/270 逐位不变，45° 的悬崖消失。
- `g_cfg.rollMiss` 8 → 4：丢检窗口砍一半。
- `kMaskHold` 6 → 8：盖住「歪头时连续 8 帧无脸」这个窗口，掩码不再断。
- `smoothFaceBoxes()`：丢检不再当场作废 EMA 历史（上限 `kEmaResyncMiss = 15` 帧），恢复首帧不吃
  hold、直接按 EMA 收敛 —— 短暂丢检（遮挡、运动模糊）之后框不再瞬跳。

**验证**

| 项 | `1.0.13.5` | `1.0.13.6` |
|---|---|---|
| 45° 素材的丢检窗口 | 8 帧（f00–f07） | **4 帧（f00–f03）** |
| 45° 时的 `fw/fh` | 卡在 `\|cp\| >= \|sp\|` 临界，抖 0.2° 就翻转 | 恒取 `rw/rh`，与「应然」值完全一致 |
| 正立 8 种面板组合 | 基线 | **8/8 逐字节相同**（`000` 组合 MD5 仍 `0efa47d9cf6a5505848410dd6f5e35af`） |
| 270° 同组 | 7/8 DIFF | **仍 7/8 DIFF**（`1.0.13.5` 的修复不受影响） |
| `_warp_seam.py` 接缝 | 旋转 6 行全在正立基线内 | **完全相同** |
| `diff` / `ema_cmp` / `mt_cmp` | 30/30 · 0/16 · 40/40 | **30/30 · 0/16 · 40/40** |

**产物**：`02_构建\build_1.0.13.6\`（`obs-beauty.dll` 503,808 B / `d2695c95…`、
`obs-beauty-ui.dll` 218,624 B / `f73ae176…`）；`03_装机\install_1.0.13.6.bat`；
`06_安装包\OBS美颜_CPU_v1.0.13.6.exe`（3,659,389 B / `3d5c1913447379cb2fb90904a15189ed`）。
PE 链接时间戳每次都不同，复验请用 `certutil -hashfile` 现场核对。

- **代价**：`rollMiss` 8→4 让人真离开画面时多跑两次推理（每次 ≈ 一次 YuNet 前向）；`kMaskHold`
  6→8 让「人走了」多糊 2 次检测（异步下约 33 ms）。`rot` 路径的逐像素开销没变。
- **回退**：无开关（属缺陷修复）。要复现旧行为用 `02_构建\build_1.0.13.5\`。
- **仍未解决（本版范围外）—— roll 锁死不放**。角度扫描（`0° → 57° → 0°`，每 3° 一帧，同步检测）：

  ```
  帧  角度   roll     phi      maskPx
  17   51°    +0.0    -6.28     17844
  18   54°   -45.0   +45.72     20982   <- 锁定，形变场整体转 ~50°
  ...
  40    0°   -45.0   +42.59     23097   <- 头已回正，roll 还是 -45
  ```

  回到 0° 时掩码 23097 px（正常 17805，多 30%），意味着磨皮糊到脸外、形变方向错约 42°。
  原因：`rollBoxPlausible()` 在**旋转后坐标系**里判断，两个角度下检出的都是「正立脸」，
  天然分不出 roll 是对是错；而释放条件只写了「按当前 roll 检不到才算失效」，YuNet 对 ±45°
  硬检是给得出框的，于是永远走不到那条路。要修得加「周期性 0° 对照」，
  属于 `1.0.5.0` 头歪补偿的设计改动，单独一版。

### `1.0.13.5` — 2026-11-09 · 修复：瘦脸/下巴的形变落错了位置

**结论**：用户报「美形的瘦脸和下巴形变位置不对」。根因是三个位移场全部建在**画面轴**上，
而方向补偿之后的框已经被 `invRotatePoint()` 反变换过 —— 源转过 90/270 时 `f.w` 是脸的
**高**、`f.h` 是脸的**宽**。三项一起错：

| 面板项 | 建场用的轴 | 实际压到的方向 |
|---|---|---|
| 瘦脸「向面中线水平压缩」 | 画面 x | 脸的长轴（把脸压短了，不是压窄） |
| 下巴「嘴线以下纵向压缩」 | 画面 y | 脸的横向（落到耳朵那一侧） |
| ROI 外扩 `f.x ± 0.30 f.w` | 画面轴 | 矩形切在脸外面，位移场贴着边界被截断 |

摄像头摆正的用户碰不到这条路径（`phi` 落在死区），所以此前一直没暴露。

**修法**（`01_源码/beauty_warp.cpp`）

- 新增 `Geom::cp/sp/rot`（画面 → 脸坐标系）。`phi` 取眼线角 `atan2`；嘴角只用来定
  ±180° 歧义（头朝下时眼线同样是「水平」的，单看它分不出正反）。
- **8° 死区**：既挡关键点噪声，也保证**正立素材走原封不动的老算式**
  （`face_src` 的眼线角是 5.8°，落在死区里）。
- 脸自身宽高 `fw/fh`：盒宽高（头歪时优先 `rw/rh`）按 `|cos| >= |sin|` 决定是否互换。
- 内层循环改成 `ox,oy → ax,ay`（脸坐标）→ 三个场 → 转回 `(sx,sy)` 采样；
  大眼 / 下巴的算式一个字没改，瘦脸的垂直权重由 `oy` 改 `ay`（正立时 `ay ≡ oy`）。
- ROI 在 `rot` 时取「脸坐标系里那个 `0.80fw × 0.68fh` 矩形」的外接盒；正立分支逐字保留。

**判据**（`05_验证/_warp_seam.py`，新增）

不看「改动区外接盒」—— 那玩意儿本来就会超出 ROI，测出来全是假阳性。只看**代码里真实算出的
那个 ROI** 的最内 2 px，并且只测没被画面边界裁掉的边。对照件是
`05_验证/beauty_core_test_norot.dll`（源码只差一行：把 `phi` 强制归零，等价于 `1.0.13.4`
的路径），用 `BEAUTY_TEST_DLL` 指过去跑同一套脚本。

脚本现在每次启动都自检「**本进程实际加载的是哪一份 `onnxruntime.dll`**」并把路径打出来。
起因是上一轮偶发过一条 `ORT: requested API version [20] not available, only [1, 17]` ——
系统里另有一份 `C://Windows//System32//onnxruntime.dll`（1.17.x，只有 API 17），而源码按 API 20
编译；一旦加载到系统那份，`GetApi(20)` 返回空、人脸检测整条死掉，后面所有数字都无意义。
实测枚举进程模块确认：正常跑在本目录时加载的是自带的 1.20.x（`1.20.20241119.10.5c1b7cc`），
那条告警来自之前一个 cwd 不对的临时脚本，既有台架结论不受影响。自检不是「加载错就崩」，
而是把它变成一行可见的输出，省得下次再靠猜。

改动落点改用**脸坐标系**描述（x 正 = 脸右半，y 正 = 脸下半；脸框内 `|x|<=54 |y|<=67`）：

| 项 | 朝向 | `1.0.13.4`（对照件） | `1.0.13.5` |
|---|---|---|---|
| 下巴 | 0° | `x[-86.9,85.1] y[39.7,68.7]`，2801 px | **逐位相同** |
| 下巴 | 90° | `x[20.7,65.8] y[-111.3,103.7]`，3382 px | `x[-89.0,101.6] y[39.7,69.4]`，3046 px |
| 下巴 | 270° | `x[-68.3,4.9] y[-105.9,111.8]`，7521 px | `x[-88.2,102.5] y[39.7,69.4]`，3057 px |
| 瘦脸 | 0° | `x[-80.9,82.1] y[-82.3,90.7]`，14340 px | **逐位相同** |
| 瘦脸 | 90° | `x[-55.5,81.7] y[-106.8,100.3]`，14398 px | `x[-81.0,82.2] y[-85.9,105.5]`，14818 px |
| 瘦脸 | 270° | `x[-71.3,81.7] y[-104.3,101.6]`，14996 px | `x[-81.1,82.1] y[-85.9,105.4]`，14782 px |

读法：改前下巴是一条「窄带」横跨整张脸（y 从 −111 到 +104），落在脸的**一侧**；改后与正立
同形（下半脸 `39.7~69.x`、整幅宽度）。瘦脸改前左右不对称（−55.5 vs +81.7，有一侧根本没压到），
改后 x 范围与正立重合（±81）。

- **正立逐字节不变**：8 种面板组合（瘦/大眼/下巴的单开、两两组合、全开）与对照件全部 SAME，
  `000` 组合的输出 MD5 仍是历史 golden `0efa47d9cf6a5505848410dd6f5e35af`；
  同一组跑到 270° 竖屏上 **7/8 DIFF**（唯一 SAME 的是全 0 组合，本来就不该变）。
- **回归**：`diff` 30/30、`ema_cmp` 0/16 帧不同、`mt_cmp` 40/40 逐次相同。
- **产物**：`02_构建\build_1.0.13.5\`（`obs-beauty.dll` 503,296 B / `14b2a624…`、
  `obs-beauty-ui.dll` 218,624 B / `46caab70…`）；装机脚本 `03_装机\install_1.0.13.5.bat`；
  安装包 `06_安装包\OBS美颜_CPU_v1.0.13.5.exe`（3,659,220 B / `001a9059214f0670ca3d382848eec531`）。
  同样注意：PE 链接时间戳每次都不同，复验请用 `certutil -hashfile` 现场核对。
- **代价**：`rot` 路径每像素多两次旋转（4 乘 4 加），只有 `phi > 8°` 才走 —— 摄像头摆正的

### `1.0.13.4` — 2026-11-09 · 修复：共用的那个人脸检测器没加锁

**结论**：`1.0.13.2` 把「检测态」按 slot 切开了，`1.0.13.3` 把「有记忆的状态」也切开了，
但**检测器本身**（`beautycore::FaceDetector`，进程里只有一份）始终没加锁。`detect()` 会把
640×640×3 的中间图写进成员缓冲（`resized_` / `input_`），再把指针交给 ONNX Runtime 推理。
两个 slot 同时进来时这不是「结果不准」，是**内存安全问题**：

| 情形 | 实际发生的事 |
|---|---|
| 渲染线程走同步检测，异步 worker 同时也在检测 | 一方 `resized_.resize()` 重新分配，另一方还握着旧指针往里写 —— use-after-free，轻则掩码全黑，重则堆破坏 |
| 两个 slot 都正常但交替很快 | 掩码偶发错几帧（实测 40 次里错 4~9 次），不崩、不自知 |
| 检不出脸时读 `lastBestScore()` 写进日志 | 读到的是**另一路**刚刚留下的分数，调阈值时被它带偏 |

**修法**

- `FaceDetector` 加 `std::mutex`，`detect` / `load` / `release` / `setInputSize` 全部串行；
  `load()` 内部改调新增的 `releaseLocked()`，不再调 `release()`（非递归锁，套一层就自死锁）。
- 置信度改由 `detect(…, DetMeta* out)` 交回，落进 `DetState.detBest`（按 slot 存），
  失败日志读它。`lastBestScore()` / `lastMs()` 保留，只给单线程探针用（`face_probe.cpp`）。
- `CoreEngine::ensureReady()` 也串行：`preheat()`（模块加载）与 `acquireSlot()`（宿主建滤镜）
  可能在两条线程上进来，而 `faceTried_` 这个「只试一次」的闸门不是原子的 —— 两边同时看到
  false 就会各加载一次模型（多付 100~300 ms，后一个还会把前一个的会话拆掉重建）。

**实测**（`05_验证/dual_instance_check.py` 新增 `mt_solo` / `mt_dual` / `mt_cmp`）

前面几种模式（`solo` / `same` / `diff`）都是**同一线程里 A、B 交替**，检测器任何时刻只有一条
线程在用，「串行」是白送的 —— 所以这条路径此前一次都没被测到。`mt_dual` 改成两条线程**同时**
跑：A 一次、B 一次，各 40 次，比 A 的掩码 MD5。

| 构建 | 不一致次数 | 说明 |
|---|---|---|
| 摘掉锁的对照件（源码只差这一行） | **4 / 40**、**9 / 40**（3 次里中 2 次） | 竞态是概率性的，跑一次可能侥幸全对 |
| `1.0.13.4` | **0 / 40**（3 次全对） | 逐次相同 |

- **判据有牙**：对照件是同一份源码只摘掉 `std::lock_guard` 编出来的 `beauty_core_test_nolock.dll`，
  用 `BEAUTY_TEST_DLL` 环境变量指过去跑同一套脚本。
- **回归**：`diff` 模式 A 命中仍是 30/30；`ema_cmp` 仍是 0/16 帧不同；单实例逐字节不变
  （同一帧输出 MD5 仍为 `0efa47d9cf6a5505848410dd6f5e35af`）。
- **产物**：`02_构建\build_1.0.13.4\`（`obs-beauty.dll` 495,616 B / `6e9f5c1e…`、
  `obs-beauty-ui.dll` 218,624 B / `e68cd64f…`）；装机脚本 `03_装机\install_1.0.13.4.bat`；
  安装包 `06_安装包\OBS美颜_CPU_v1.0.13.4.exe`（3,654,548 B / `9980bd64702b89642d6c1f725ecda02b`）。
  注意：PE 链接时间戳每次都不同，**同一份源码重编一次 MD5 就会变** —— 上面这几个数只对应本次构建，
  复验时请用 `certutil -hashfile` 现场核对，不要拿旧数字当判据。

### `1.0.13.0` — 2026-11-09 · 优化：磨皮盒式三通道融合 + 垂直趟 SSE（画面逐字节不变）

**先纠正一条结论：磨皮不是 `boxRgbRoi` 在跑。** `1.0.12.0` 的真机 S 组把磨皮推到
全链 44%（归一后 5.34 / 12.07），按代码读出来是「路线 C 盒式迭代 12 趟」，于是先改了
`boxRgbRoi`。改完逐字节相同、**台架一点没快**。查敏感性：`BEAUTY_BOX_ITERS=1/2/4`
三档磨皮耗时一样（7.78 / 7.85 / 7.66）—— 迭代次数直接翻倍趟数却零影响，说明那段
没跑。加 `BEAUTY_BOX_TRACE=1` 打印入口，确认一次都没进。

根因：**3.1.17 起 `surface3=1` / `s3Band=1` 是默认**，生产走 `surface3RgbBand`；
`boxRgbRoi` 只在 `lowPath=3` 且 surface3 关掉时才用。真正的盒式在
`bandBoxH / bandBoxV`（b1 三平面 + b2 三平面 + amp 单平面，各 nPass 轮 × H/V 两趟）。

| 项 | 做法 | 默认 |
|---|---|---|

### `1.0.7.0` — 2026-11-09 · 修复：脖子通道在旋转源上画错了方向（真修，前版）

**现象**：源需要转 90°/270° 才立正时（本机摄像头正是 270° 这一档），从下巴横着出去
一条磨过的带子，穿过肩膀落到窗帘上；真正的脖子一点没磨。

**成因**：脖子通道全部在**源坐标**里做，从脸框下沿按 `+y` 往下推进。源要转 270° 才
立正时，源坐标的 `+y` 在立正画面里是**横向**的。自 `1.0.3.0`（第一次让这台摄像头检出
脸的那版）起就错着 —— 带子落在窗帘上，不盯着看不出来。

**改法**：把「正下方」写成源坐标里的单位向量 `(dx,dy)`，几何全部参数化成 `(u,v)`：
`u` 沿正下方、`v` 为横向。三种形状分支（跟随肤色 / 椭圆 / 矩形）与脖子羽化都只跟
`u`、`v` 走，与源朝向无关。顺带修掉两个换算错误：

1. **旋转源的宽高是交换过的**。270° 时检测框在源坐标里是 356×259，`bw=356` 是脸的
   纵向尺寸（脸高）、`bh=259` 才是脸宽。旧口径一律拿 `bw` 当脸宽，脖子会按脸的长边
   铺开（宽 1.4 倍）。现在按 `(dx,dy)` / `(lx,ly)` 投影算两个半跨度。
2. **脖子起点**改用「脸框沿正下方的下沿」（倾斜时按投影算，且含 `kFaceBoxGrow`），
   倾斜脸的下巴不再和脖子之间留一条 7.5% 的缝。

**实测**（`up10.raw`，源 1920×1080 / 270°，统计在立正坐标系）：

|---|---|---|---|
| `1.0.5.0` | 145010 px | 26154 px（18.0%） | 下巴下 25 px |
| `1.0.6.0`（止血） | 101142 px | 0 px | 下巴下 25 px（脖子没磨） |
| **`1.0.7.0`** | 114684 px | 0 px | **下巴下 92 px** |

全开 22.18 ms。脖子沿立正方向落在脸框正下方，没有把 ROI 拖回去。

**逐字节承诺**：`(dx,dy)=(0,1)` 且 `roll==0` 时所有式子退化成旧式 —— `t5_a0.raw`
（1080×1920）掩码 303927 px，PGM 与 `1.0.5.0` **逐字节相同**。横向基向量必须取 `+x`：

### `1.0.5.0` — 2026-11-09 · 修复：头歪 45° 时「美颜整体失效」

**症状**（用户 2026-11-09 报）：人物**身体立正**、只有**头歪 45° 左右**时，美颜明显失效。

**根因**（两层，缺一不可）：

1. **YuNet 的平面内倾斜容忍边界在 30~40° 之间**。同一帧实测：倾斜 30° 时 `score 0.773`
   仍能出框，45° 时**一个框都出不来** → 掩码为空 → 磨皮 / 美白 / 红润全乘 0。
2. 即使 YuNet 勉强出框，框也是**错的**。真机方向（源需转 270°）下 45° 歪头实测
   `score 0.759`、**双眼间距只有框宽的 28%**（正立脸是 43~47%）—— 框撑大了、位置也偏，
   掩码照样糊到脸外面。这种帧 `detOk` 为真，既不会触发方向兜底，也永远轮不到倾斜探测。

**改法**：

- **检测侧**：连续 `BEAUTY_AUTO_ROLL_MISS`（默认 8）次「检不到脸 **或** 框明显不像人脸」
  后，在合成角（方向 + 倾斜）上各试一次 `+45° / -45°`；命中就记住倾角，之后每帧按
  `方向 + 倾角` 检测。`BEAUTY_AUTO_ROLL=0` 整段关闭（逐字节回到 `1.0.4.0`）。
- **假框门槛**（`rollBoxPlausible`）：这一步是必须的，不是保险。反方向那个候选会把倾斜
  累加到接近 90°（侧躺），YuNet 在那里吐的是画面里某块像脸的纹理：实测假框
  `score 0.66~0.69` / 双眼间距 7.8~10.3%，真框 `0.89~0.92` / 33~37%。没有门槛时
  「取分数最高的那个」会把假框**锁死**，之后每帧都检不到脸，而且因为一直「有框」，
  方向兜底也不会来救。门槛三条：`score ≥ 0.75`、双眼间距/框长边 ∈ `[0.25, 0.62]`、
  眼睛在嘴上面。
- **掩码侧**：反变换回源坐标时，倾斜的框只能退化成**轴对齐外接矩形**，45° 时面积是脸
  本身的 2.8 倍。为此 `FaceBox` 多带 `roll`（倾角）与 `rw/rh`（脸自身宽高），掩码按
  **倾斜矩形 / 倾斜椭圆**画。不这么做的话，磨皮会糊到脸外面，ROI 也白涨一倍。
  脖子通道**保持竖直**（用户报的是「身体立正、只有头歪」，脖子本来没歪）。

**实测（离线台架，帧取自 `2026-11-09 01-35-26.mp4`，机械旋转出 45° 歪头）**：

| 45° 歪头 | `faces=0`，掩码 **0%** | `faces=1`，掩码 18.35%，形状与理论斜框重合 |
| 45° 歪头、磨皮 ROI | —（无掩码） | 17.6 ms（正立 10.6 ms） |
| 真机方向 270° + 45° 歪头 | 锁在 `score 0.759` 的敷衍框 | 先命中 270°，再命中 `-45°（score 0.906）` |

**真机验证（2026-11-09 上午，装机路径 + 真摄像头 + 真录制）**：

### `1.0.3.0` — 2026-11-08 · 修复：竖屏摄像头「美颜完全没效果」（对齐 GPU 版口径）

**症状**：采集设备是**竖着**的（手机竖拍 / 竖屏采集卡）时，美颜一点效果都没有；同一台机器
换成默认横屏机位、人正立，就一切正常。

**根因**：OBS 场景项的旋转只作用于**显示合成**，滤镜拿到的 `in_tex` 仍是躺着的原始帧
（例如 1920×1080 里人横躺着）。YuNet 在 ±90° 的脸上检不出框 → 掩码为空 → 磨皮 / 美白 /
红润全乘 0。日志表现是 `faces=0`、`px=-1`，看起来像「模型没加载」，实际是「方向不对」。

**改法**（从 GPU 版 3.2.0「自动输入方向探测」移植）：连续 `BEAUTY_AUTO_ROT_MISS`（默认 20）
次检测都检不到脸时，在同一张输入图上各跑一次 90°/270° 的重采样检测；认定方向后按该方向检测，
再用 `invRotateFace` 把框与五点反变换回源坐标。旋转做进 letterbox 的重采样，**不额外分配
旋转缓冲**（4K 一帧 33 MB）。

### `1.0.2.0` — 2026-11-08 · 修复：手遮脸时「美白遮罩叠到手部」（对齐 GPU 版口径）

**症状**：手往脸上一搭，手背上出现一块**边界清晰的美白区域**，形状跟着脸的椭圆/脸框走。

**根因**：清晰 / 美白 / 红润三段是**纯逐像素颜色表**，与空间位置无关（实测箱内 σ 只有
零点几灰阶）。可是 `toneColor()` 原来是「LUT 结果 × 皮肤掩码」，于是掩码的边界
（椭圆 / 脸框裁切 / 脖子矩形）在画面上变成一条**可见色界**。手背是肤色，YCbCr 判据必然
放行，掩码罩得住手 → 那条色界正好切在手背上，就是用户看到的「遮罩」。

**改法**（与 GPU 版 `BEAUTY_TONE_GLOBAL=1` 同一口径、同一实现）：色彩三段改为**整帧施加、
不乘掩码、不看 ROI**；磨皮 / 锐化 / 五官五项不动，仍按皮肤掩码走。
`BEAUTY_TONE_GLOBAL=0` 恢复 `1.0.1.0` 行为（**逐字节相同**，见下）。
