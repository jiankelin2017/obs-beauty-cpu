### `1.0.12.0` — 2026-11-09 · 优化：A 通道并进色调写 + 跳过用不到的中频盒式（画面逐字节不变）

`1.0.11.0` 的真机 P/Q/R 三组给出了两条结论：A3 有效（色调 4.56 → 0.84，全链
18.35 → 13.47），A5 证伪（下载省 0.58 但引擎 +0.41、上传 +0.19，净亏 0.28）。
本版在 13.47 的基础上再砍两处，都属「本来就在读写同一片内存，顺手做掉」：

| 项 | 做法 | 台架实测（你的真实配置） | 默认 |
|---|---|---|---|
| **A6 A 通道并进色调写** | 色调整帧整数表分支本来就逐像素写 R/G/B，改成一次 32 位存（高字节 0xFF 拼上 B<<16、G<<8、R），顺手把 A 置 255；`toneColor` 返回 `bool` 告诉调用方「A 已办妥」，末尾的 `forceOpaque` 跳过 | 见下方合计 | 开（无开关） |
| **A7 跳过用不到的中频盒式** | `detailRefill` 里 `hf` 用 3×3、`hm` 用 7×7，而 `hm` 只在 `p.mid / p.globalMid` 非 0 时才被读。生产的基准回填把 `mid` 固定为 0、全局锐化关时 `globalMid` 也是 0 —— 此时 7×7 那两趟纯属白算（整片 ROI 再扫两遍 + 写满一个 float 平面） | 同上 | 开（无开关） |

**合计（`f1.raw` 1920×1080，`BENCH_PROFILE` 复刻你的实际面板：磨皮 100 / 美白 45 /
下巴 7，锐化与全局锐化都 0）**：全开 16.13 → **14.44 ms（−1.69，−10.5%）**，
五轮交替的区间完全不重叠（旧版最低 15.85 > 新版最高 15.03）。强制全帧 28.71 → 26.04。

**逐字节等价**：三份标准素材（`f1.raw` ROI / `up10.raw` 无脸兜底 / `probe_in.raw`
640×394）与**真实配置（含 `chin=7` 的 warp）**四条路径，输出全部与 `1.0.11.0` 相同，
A 通道全为 255。

两处为什么能保证等价：

- A6 的 255 要活到输出，中间隔着 `applyFaceRegions`、细节回填、`warpFace` 三道。
  前两道对 A 全是 `dst[o+3] = src[o+3]` 的「保持原值」写法；`warpFace` 对四个通道
  一起做双线性插值，而 255 与 255 的插值结果仍是 255。所以「色调写过的 255」不会
  被后面任何一步改掉 —— 台架用真实配置（下巴 7 会真的触发 warp）复验过。
- A7 只是**不计算一个不会被读的平面**，`hm` 的计算也一并挪进了
  `if (mwF != 0.0f || mwG != 0.0f)` 分支里。`needMid == false` 时 `mwF/mwG` 双双
  为 0，那个分支根本进不去，所以绝不会解引用未填充的 `b7`。

**原计划的「`blurRefill` 隔帧跑」被否决。** 原因：`blurRefill` 不是独立的一遍，
它和「脸内锐化」「全局锐化」共用同一次 `detailRefill` 调用，只靠 `dp.fine` /
`dp.mid` / `dp.globalFine` / `dp.globalMid` 四个权重区分。隔帧就等于整段细节回填
隔帧，连锐化一起变成 30 Hz —— 会有可见抖动。真正的省法是 A7 这条「少算一个用不到
的频带」，而不是「少跑一帧」。

**A7 的生效条件要说清楚**：只有当「脸内锐化」与「全局锐化」都关时才跳得掉
（`detailMidGain` 默认 3.30，只要 `sharpen > 0`，`dp.mid` 就非 0，7×7 必须算）。
你当前的面板（`sharpen=0`、`global_sharpen=0`、`color_level=45`）正好落在生效区间，
所以 A6 与 A7 两条都在跑。

**真机 S 组（2026-11-09 13:14，5 个干净窗口中位）**：`13.25 ms`（下载 1.93 + 引擎
10.62 + 上传 0.70；检测 0.71 / 磨皮 6.12 / 色调 0.71 / 细节 1.45 / 美形+alpha 1.61）。
**这个数不能与 `1.0.11.0` 的 13.47 直接相减** —— 这一轮 ROI 是 540×292（157680 px），
比 P 组的 450×306（137700 px）大 14.5%，磨皮因此从 5.24 涨到 6.12（磨皮路径本版
未改动，线性外推 5.98，实测在抖动内）。**按 ROI 面积对齐后全链 ≈12.07 ms（−1.40，
−10.4%）**，与台架 −1.69 同量级。

> ⚠️ **2026-11-09 13:44 复查：上面这一段的绝对数作废。** 13:14 那次录制期间后台有
> 进程抢核，所有多线程段被拉慢约 1.8 倍（单线程的人脸检测 0.72 → 0.75 不变），
> 同一份盒式代码在正常状态下磨皮只有 3.1 而不是 6.12。`13.25` / `12.07` / `−1.40`
> 今后不再引用；本节内部「细节与美形两段区间不重叠」的相对结论仍然成立。取证见
> `05_验证/ab20261109_engine_stage.md` §11.4(a)。

不受 ROI 影响的两段区间完全不重叠，是收益的硬证据：细节 1.53~1.74 → 1.38~1.51；
美形+alpha 2.02~2.37 → 1.36~1.69。取证见 `05_验证/ab20261109_engine_stage.md` §9。

### `1.0.11.0` — 2026-11-09 · 优化：色调整数复合表 + 下载零拷贝（可关，画面逐字节不变）

**先纠正一条错误结论。** `1.0.10.0` 的 E/F/G/H 四组真机对照证明「`1.0.8.0` 比
`1.0.7.0` 慢 4 ms」不成立：完全按 `1.0.7.0` 分工与并行参数配置的 H 组反而是四组
里最慢的（引擎 19.02 ms）。那条 10.41 ms 的旧基线是在别的场景下测的，原日志已被
OBS 轮转删除、无法复查，**从此作废、不再作为优化目标**。按 ROI 面积对齐后的真实
归因是：A1 省 2.5 ms、A2 省 0.3 ms、A4 省 0.2 ms，三项都保留。

本版两处提速：

| 项 | 做法 | 台架实测 | 真机实测 | 默认 |
|---|---|---|---|---|
| **A3 色调整数复合表** | 整帧模式下 `sk ≡ 1.0`，清晰→美白→红润对整数输入是纯函数，预计算 3 张 256 项 `uint8` 表；每像素从「3~9 次浮点插值 + 9 个分支 + 6 次 byte↔float 往返」变成 3 查表 3 存 | 全开 **36.85 → 31.05 ms（−5.79）** | 色调 **4.56 → 0.84（−3.72）**，全链 18.35 → 13.47（**−4.88，−27%**） | 开 |
| **A5 下载零拷贝** | `linesize == cx*4` 时把 `gs_stagesurface_map` 的指针直接交给引擎，省一次 8.3 MB memcpy | — | 下载 **2.04 → 1.46（−0.58）**，但引擎 +0.41、上传 +0.19，合计 **13.47 → 13.75（净亏 0.28）** | **关** |

A3 的逐字节等价性：表内算式与原逐像素版**逐字相同**，连 `* 1.0f` 都保留 ——
`r += (tab - r) * 1.0f` 与 `r += (tab - r) * sk`（sk=1.0f）在 IEEE-754 下同一结果，
所以不能手写成 `r = tab`（那是代数等价、不是浮点等价）。

A5 已由真机三组判定（P/Q/R，各录 28 秒，只看 `无脸跳过 = 0` 的窗口）：
下载段确实干净地省了 0.58 ms（P 组 5 个窗口 1.91~2.13、R 组 1.40~1.56，组内抖动
仅 ±0.13），但引擎多花 0.41、上传多花 0.19，合计反而慢 0.28。两组 ROI 面积几乎
相同（掩码 111k vs 102k），所以引擎那 0.41 不是 ROI 差异。原因是预判的那条：
`gs_stagesurface_map` 的内存是写合并/非缓存的，而引擎在掩码、磨皮、色调、细节
四个 pass 里**反复读**同一片输入，省下的一次顺序 memcpy 被加倍的随机读吃掉。
**结论：默认保持关**；代码留作开关不删（换驱动/换 GPU 后结论可能不同，成本只是一个 if）。

开关：`BEAUTY_TONE_LUT=0`（回到浮点插值）、`BEAUTY_ZERO_COPY=1`（开零拷贝）。
init 日志新增 `zc=on|off, tone_lut=int|float`，跨录制的数字才能证明跑的是哪条路。

### `1.0.10.0` — 2026-11-09 · 诊断：A2/A4 可关 + ROI 尺寸进日志（画面逐字节不变）

**1.0.9.0 的四组真机对照把「并行度」这条线排除了**（同机同相机，只看
「无脸跳过 = 0」的干净窗口）：

| 组 | 块宽 / 阈值 | 干净窗口引擎耗时（ms） |
|---|---|---|
| A | 8 / 8192 | 12.86、15.37、15.95、13.87 |
| B | 32 / 150000 | 12.92、14.20、13.95、13.97、13.96 |
| C | 32 / 8192 | 13.92（仅 1 个干净窗口） |
| D | 16 / 8192 | 12.47、13.89 |

四组是**同一个数**（约 13.9 ms）⇒ `kBlock` 与 `bt` 阈值在真机上对引擎耗时
没有影响，1.0.8.0 的并行度改动是中性的，不是回退来源。

**同时发现统计口径的坑**：第一轮把「人走出画面」的窗口也算进中位数，于是
C 组被 4 个 `无脸跳过 28/56/60/89` 的窗口拉低到 10.31 ms，造出「C 快 3 ms」的
假象。`live_matrix.py` 已改为只统计 `无脸跳过 = 0` 的窗口。

**脸的大小也不是原因**：用同一个 YuNet 量两次录制的脸框，1.0.7.0 那次中位
76,695 px²，1.0.8.0 那次 97,448 px² —— 1.0.7.0 的脸更大反而更快。

**本版改动**（默认值等于 1.0.9.0 行为）：

1. `BEAUTY_PAR_COPY=0`：ROI 外整帧拷贝退回单线程（1.0.7.0 写法）。
2. `BEAUTY_ALPHA_IN_ENGINE=0`：A 通道交回插件层（1.0.7.0 分工），插件在上传段
   补那遍标量循环 —— 少了它会合成出黑画面，所以做开关时必须同时补回。
3. 分段日志加 `ROI %dx%d 掩码 %d`：跨录制的引擎耗时只有 ROI 面积可比时才可比。
4. init 行加 `par_copy=on|off` / `alpha=engine|plugin`。

**验证**：`f1.raw` 在默认配置、以及 `PAR_COPY=0 + ALPHA_IN_ENGINE=0` 两种配置下，
输出与 1.0.9.0 **逐字节相同**（A 通道全 255）。

**待办**：真机跑 E/F/G/H 四组，确认回退是否来自 A2 或 A4。

### `1.0.9.0` — 2026-11-09 · 诊断：引擎分段耗时 + 盒式并行度可调（画面逐字节不变）

**起因**：1.0.8.0 装机后真机**反而变慢**，且离线台架复现不出来。

| 版本 | 下载 | 引擎 | 上传 | 合计 |
|---|---|---|---|---|
| `1.0.7.0`（11:57 日志） | 1.80 | 10.41 | 1.10 | 13.31 |
| `1.0.8.0`（12:21 日志） | 2.27 | 14.61 | 0.73 | 17.44 |

上传 −0.37（A4 如预期生效），但引擎 +4.2、下载 +0.5。带 12 线程抢核的离线台架

（`f1.raw` 1080p，两轮交替）仍是新版更快：磨皮 12.8~15.0 vs 15.9~16.1 ms，全开

33.0 vs 39~42 ms。也就是说「一个整段数字」不足以归因，必须拆到引擎内部。

**改了什么**（只加观测手段，不碰任何像素值）：

1. `ICoreEngine::lastStageMs()`（非纯虚，别的引擎不用改）：每帧回五个分段耗时，
   0=检测+掩码、1=磨皮（含混合）、2=色调+五官、3=细节回填、4=美形+A 通道。
2. 性能日志多一行 `分段：检测+掩码 … | 磨皮 … | 色调 … | 细节 … | 美形+alpha …`，
   与「性能」行走同一个 180 帧窗口。五项之和不等于引擎总时，差值就是公共开销。
3. 盒式两个可调项（默认值 = 1.0.8.0 出厂值，不设变量行为不变）：
   - `BEAUTY_BOX_BLOCK`：列块宽，默认 8；设 32 回到 1.0.7.0 的粒度。
   - `BEAUTY_BOX_MINPX`：低于多少像素退回单线程，默认 8192；设 150000 回到 1.0.7.0。
   - init 行多打 `box_block=` / `box_minpx=`，证明跑的是哪一档。
4. `05_验证/obs_ctl.py up --env K=V`（可重复）+ `05_验证/live_matrix.py`：
   一次装机、同一相机同一光照，跑四组配置并列出分段耗时。

**验证**：离线台架 `f1.raw`（1080p，1 张脸）与 `up10.raw`（1080p，无脸兜底路径）
输出与 1.0.8.0 **逐字节相同**；默认参数下 kBlock/阈值与 1.0.8.0 完全一致。

**结论待定**：真机 14.6 ms 的构成要等四组对照跑完才能归因（见
`05_验证/ab20261109_engine_stage.md`）。

### `1.0.8.0` — 2026-11-09 · 优化：磨皮并行度 + ROI 外拷贝 + A 通道搬进引擎（画面逐字节不变）

**起因**：真机 180 帧平均的分项是「下载 2.25 + 引擎 10.0 + 上传 1.44 = 13.8 ms/帧」。
1080p 30 fps 预算 33 ms 还算宽松，但 60 fps 的 16.7 ms 已经贴边。逐段查下来，
有四处是**纯浪费**（三处已在本版修掉，第四处留作下一版）。本版不加任何功能、
不改任何像素，只把「本来该多核的活交回多核」「本来该少跑一遍的少跑一遍」。

**① 磨皮垂直盒式一直在单线程跑。**

`bandBoxV` / `boxPlaneV` 按列分块，块宽 32 列；而 `runRange` 用「任务数 = 块数」
决定线程数，且「每线程至少 16 行」。半分辨率 ROI 的平面宽只有 384 左右 →
`nblk = 384/32 = 12` → 12 < 32 → **直接判成单线程**。垂直 pass 是磨皮里最重的一段
（13 个平面 × 3 趟 × 3 组），自双尺度带通上线起就只占一个核。

改法：块宽 32 → 8（48 个任务，能开 3~6 线程）。分块方式不影响任何像素的值 ——
每块自己维护列和、`kFlush` 重算点仍按全局 `y`，块与块之间没有依赖。
代价是每块每行只读 32 字节（cache line 64 字节，浪费一半），实测仍是净赚。

**② `surface3RgbBand` 的线程门槛卡在半分辨率 ROI 的临界值上。**

`bt = (np >= 150000) ? threads : 1`。正立 1080p 的人脸 ROI 加 pad 后落在
14.6~18.4 万像素之间，人脸稍小一点就整段退回单线程 —— 而这一段的盒式一趟是
18 次滤波。阈值改成 8192（真正该防的只有「几十像素的缩略图」这种量级）。

**③ ROI 之外的整帧拷贝是单线程的。**

磨皮按 ROI 算，ROI 外的 dst 必须从 src 搬回来（1080p 上 ROI 只占 16%，要搬
6~7 MB），原来是单线程 `for + memcpy`，约 0.5~0.8 ms。改成按行并行（写区与合成段
不重叠）。

**④ A 通道置位从插件层搬进引擎。**

`obs-beauty.cpp` 原来每帧跑一遍「207 万次 32 位读改写」把 A 置 255（1080p 约
0.4 ms），发生在引擎返回之后、数据已凉的时候。改成引擎 `process()` 返回前用 SSE2
做（`forceOpaque`），同一批 cache line 刚被本帧写过。插件层那遍删除；「面板全 0
不调引擎」的分支保留一份标量版（那条路只在上传段，一帧 0.4 ms 不在预算讨论范围内）。

**实测（`cpu_bench`，`f1.raw` 1920×1080，faces=1，3 轮交替取中位数）**：

| 项 | `1.0.7.0` | `1.0.8.0` | 变化 |
|---|---|---|---|
| 只开磨皮（掩码 ROI） | 10.64 ms | **7.04 ms** | **−34%** |
| 全开（掩码 ROI） | 25.45 ms | 23.92 ms | −6% |
| 全开（强制全帧） | — | 30.12 ms | 全帧路径不受 ①② 影响（ROI 为空时的兜底） |

全开只降 6%：清晰 / 全局锐化 / 五官五项没动，它们的成本压在磨皮之上。
本机 CPU 占用从 3.36 核涨到 4.53 核 —— 这就是「把活交回多核」的直接证据。

**逐字节承诺**：三处改动一处都不改像素值，已实测两轮。
- `f1.raw` 1920×1080、faces=1、走 ROI 路径：`dumpOut` 8,294,400 字节**完全相同**。
- `probe_in.raw` 640×394、faces=1：同样**完全相同**。
- `up10.raw` 1920×1080、faces=0（走全帧兜底 + 色调整帧）：同样**完全相同**。

**真机验证**：见本节末「真机」段（装机后补测）。
