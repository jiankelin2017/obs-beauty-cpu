### `1.0.13.10` — 2026-11-09 · 加固：一个潜在空指针 + `BEAUTY_*` 覆盖收口（**画面不变**）

**结论**：本版**不改画面**。三项都出自同一次代码审查（C-1 / C-2 / C-3）：C-1 是
「分配失败才触发」的崩溃路径，C-2 / C-3 是同一个机制的两面。按「用户能不能看出
差别」验收会得到「看不出」—— 那是预期结果，不是没修好。

**C-1：重分配失败后空指针**（`01_源码/obs-beauty.cpp`）

原顺序是「先提交尺寸、再分配」：

```c
f->w = cx;  f->h = cy;              /* 先写进结构体 */
f->buf_in  = malloc(cx*cy*4);       /* 1080p 每份 8 MB，4K 每份 33 MB */
f->buf_out = malloc(cx*cy*4);
if (!f->tr || !f->stage || !f->buf_in || !f->buf_out) { …; return; }
```

任一份失败就带着「`f->w/h` 已更新、缓冲是 NULL」提前返回。下一帧的判据是
`f->w != cx || f->h != cy || !f->tr` —— 三个都不成立（`tr` 那一份已经建好），
重分配被**永久跳过**，控制流直接走进 `memcpy(f->buf_in, …)` 与
`gs_stage_texture(f->stage, …)`。`stagesurface` 失败而 `texrender` 成功，是同一个
结局。OBS 里表现为「切到高分辨率源 / 显存吃紧时整个进程崩」，且崩在渲染线程上。

修法：新增 `beauty_filter_alloc()`，新的一套（两份 malloc + texrender +
stagesurface + `GS_DYNAMIC` 纹理）全部建在局部变量里，**全部成功之后**才释放旧的
并提交 `w/h`；任一失败则释放已建好的局部资源、返回 `false`，结构体一个字段不动
（上一帧那套仍完整可用），本帧直通、下一帧自然会重试。重分配判据同时补齐
`!stage / !out_tex / !buf_in / !buf_out`，不再依赖「要么全好、要么 `tr` 为空」这个
不成立的假设。

**C-2 / C-3：115 处 `BEAUTY_*` 覆盖收口，发布版加锁**

原状态：全库 115 处诊断开关各自直接调 `getenv`，**发布版里全部生效**。最扎眼的是
`BEAUTY_FACE_MODEL`（可让插件加载任意路径的 `.onnx`）；更现实的是支持成本 ——
机器上残留一个 `BEAUTY_ROLL_CHECK=0`，行为就和文档不一致，而日志里没有任何痕迹。

修法：新增 `01_源码/beauty_env.h`，`beauty_env(name)` 成为唯一入口，
`beauty_env_enabled()` 供日志与台架判断；115 处调用**只换函数名、逻辑一行没改**
（原有 `if (e && *e) {…} else {默认值}` 结构天然适配）。发布构建定义
`/DBEAUTY_ENV_LOCK=1` 后 `beauty_env()` 恒返回 `nullptr`，MSVC 把这些分支当常量
折叠掉 —— 滤镜 DLL 506,880 B → 463,872 B（−43 KB），证明分支是真的不可达，
不是「运行时绕一圈再回落到默认值」。

两个构建，源码同一份、只差这一个宏：

| 构建 | 宏 | 输出目录 | 用途 |

| `02_构建\build_1.0.13.10.bat` | `BEAUTY_ENV_LOCK=1` | `02_构建\build_1.0.13.10\` | **发布/打包**，`BEAUTY_*` 一律失效 |

### `1.0.13.9` — 2026-11-09 · 修复：`roll` 锁死不放（歪过 45° 再回正后不归位）

互相抵消。位置对了，**掩码是错的**：

|---|---|---|---|---|---|
| 回正后（锁死） | −45 | +42.59° | 192.4×192.4 | 123.5×148.6 | 23857 px |
| 回正后（正常） | 0 | +5.84° | 107.5×133.7 | — | 18126 px |

**一处自我更正**：外接盒面积差 2.6 倍，但**掩码只差 1.32 倍** —— 掩码取的是
`rw/rh`（脸自身宽高），`w/h` 只决定绘制范围的外接盒。`1.0.13.8` 记录里写的
「面积差约 2.4 倍」指的是外接盒，容易读成掩码也涨 2.4 倍，实际不是。
（本表数值为 640×640 画布、同步口径补测。）

**修法**（`01_源码/beauty_core.cpp`）

- `DetState` 新增 `rollCheck` / `rollReleaseLog`（按 slot 隔离）。
- `roll≠0` 且本帧 `detOk && plausOk` 时，每 `g_cfg.rollCheckFrames`（默认 45 帧
  ≈ 1.5 s @30fps）在同一条路上额外跑一次 **0°（不含倾斜）** 对照检测。
- 判据：对照结果里**通过 `rollBoxPlausible` 的框**最高分 ≥ 当前角度同类最高分
  + `rollReleaseMargin`（0.05）才释放。要求「明显更好」，因为真歪头时 0° 大概率
  也给框 —— 只是个撑大的敷衍框（45° 时 0° 那一路双眼间距比只有 0.216，过不了
  `rollBoxPlausible`）。
- 比较基准用「只统计 plausible 框的最高分」，不用「所有框的最高分」：后者会被
  一个不 plausible 的高分假框顶住，该释放时释放不了。
- 释放走与倾斜切换完全相同的路径（`startGeoFade` + `resetFaceEmaState`），
  由 `applyGeoFade` 6 帧插值过去。
- `!plausOk` 时不做对照 —— 那种情况交给上面的倾斜探测，不重复下注。

| S　固定 20/30/35° 各 120 帧 | 全程不锁（紧框已够，锁了只是多一层切换） |

H 组是关键：真歪头时 0° 那一路的框过不了 `rollBoxPlausible`（45° 时双眼间距比
只有 0.216），永远补不上 0.05 的差距要求。S 组说明小角度本来就不锁 ——
`1.0.5.0` 以来「歪一点也补偿」的抖动风险并不存在。

`06_安装包\OBS美颜_CPU_v1.0.13.9.exe`（3,660,462 B / `7002dd6acb9070bed4dd436a54a5be53`，

- **代价**：`roll` 锁定期间每 45 帧多一次 640×640 推理（同步口径该帧 27.6 → 36.3 ms）。
  异步下落在 worker 上，不阻塞渲染。释放最坏要等满 45 帧（≈1.5 s @30fps）——
  这是有意的：太快会让「歪一下又回」反复切换，而每次切换都要清人脸框 EMA。
  实测第 24 帧就释放，是因为计数在歪头期间已开始累加，回正时并非从零起算。
- **仍未解决**：`roll` 探测帧仍是「一帧内多跑两次推理」（同步口径 51.9 ms vs

  （`1.0.13.5` 记录里那条）未动。

### `1.0.13.8` — 2026-11-09 · 修复：`1.0.13.7` 之后歪头 45° **还是闪**

**结论**：`1.0.13.7` 的几何过渡没白做 —— 关掉掩码对齐做对照，几何那段确实是平的。
让画面跳的是**掩码对齐**（`3.1.10`）在异步链路里的断续：worker 结果到货的那一帧
输出 `heldFrame_`（**上一帧画面**），没到货的帧输出当前帧。worker 一忙一闲，输出就在
「晚一帧」和「当前帧」之间来回切。

歪头过渡期正是 worker 最慢的时候（`roll` 探测要多跑两次 640×640），所以那个切换
在那一段最频繁 —— 这就是用户说的「闪一下 / 卡一下」。

**复现（同一序列，`face_src` 每帧 +1° 从 0° 转到 57° 再转回，三项形变拉满）**

| 口径 | 57°→57° | 57°→56° | 全程 |
|---|---|---|---|
| `BEAUTY_ALIGN_DIFF=0`（= `3.1.10` 旧行为） | 7.09 → **1.67（−5.41）** | 1.67 → 6.89（**+5.22**） | 在 1.67 与 7 之间来回 |
| 默认（本版，`alignDiff=4`） | 1.68 → 1.67 | 1.67 → 1.68 | **1.29…1.68，无 >0.6 的相邻跳变** |
| `BEAUTY_MASK_ALIGN=0`（关掉对齐） | — | — | 恒定 1.3…1.7 |

> **口径提醒（踩过的坑）**：异步路径下的 `meanD` **不是美颜强度**。同步检测跑同一序列，
> `meanD` 恒在 1.2…1.7 —— 那才是美颜量；异步多出来的约 5.4 全部是「上一帧画面 vs
> 当前帧」的整图位移（1°/帧 旋转，半径 320 px 处约 5.6 px）。量强度必须走同步口径，
> 异步 `meanD` 只能用来量「帧有没有对错」。

**修法**（`01_源码/beauty_core.cpp`）

- 新增 `frameNearlySame()`：每 4 行每 4 列取一像素，比 R/G/B 的平均绝对差
  （1080p 约 13 万次比较，实测 < 0.3 ms）。
- `process()` 里对齐的条件从「有新鲜掩码」改成「有新鲜掩码 **且** 画面几乎没动」。
  取舍一句话：**宁可掩码晚一帧，也不要画面重复一帧**。重复帧是硬的；掩码晚一帧在
  皮肤这种大色块里看不出来。静止时照旧对齐（掩码与画面逐像素同源，零代价）。
- `g_cfg.alignDiff` 默认 `4.0`（相机噪声静止时 1~2，1°/帧 旋转 5.4，取中间）；
  `BEAUTY_ALIGN_DIFF` 可覆盖（0~64），**`0` = 关闭这道门，退回 `3.1.10` 行为**，A/B 用。
- 新增诊断计数 `g_alignRejected`（因「在动」而放弃对齐的帧数），与 `g_alignUsed` 成对看。

> 真机这一条是唯一能终止「还闪」争议的判据。前两版（`1.0.13.6` / `1.0.13.7`）

> 证伪，不能证真。

> **装卸回归首跑 6 FAIL，是判据的锅，不是产品的锅**（2026-11-09 17:14）。
> 6 项全部落在 A3「ProgramData 下的文件没删掉」，而同段落的安装目录、两个注册表键、
> 开始菜单全 PASS —— 注册表键是 nsi 卸载段的最后一步，它没了说明删除动作执行过。
> 定性靠三条独立证据：`models` 目录创建时间仍是安装那一刻、复跑时打印的
> `reg ObsDir` 与断言路径一致、放宽窗口后 `filter/ort/models/ui` 四项全部 `True`。
> 真因是**卸载器的文件删除有 1~2 秒延迟**，旧判据「等注册表消失后硬睡 1.2 秒」卡在边界上。
> 改法：`e2e_test.ps1` 新增 `Wait-PathGone()` 轮询（最多 8 秒），并在 A2 打印
> `ObsDir/UIDir/PDir`、在 A3 打印 `gone after wait` 四态。**只放宽时间窗口，
> 不改变「最终有没有删掉」的判定** —— 等满 8 秒仍未消失照样 FAIL。
> 判据口径从此固定：**凡「卸载后应消失」的断言一律轮询 + 超时，不用固定 sleep。**
