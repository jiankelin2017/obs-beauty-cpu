# C13 · 装机链路：把自研引擎的运行时装进去

> 2026-10-28 · 滤镜 3.1.2 / CoreEngine 0.7 / 面板 3.0.20
> 产物：`D:\插件\OBS美颜_Setup_v3.1.2.exe`（65.7 MB）、`D:\插件\OBS美颜_v3.1.2_整合包.zip`（71.1 MB）
> 改动的文件：`04_依赖与SDK/installer-stage/*`、`08_安装包/obs-beauty.nsi`、整合包 `INSTALL.bat`

---

## 1. 为什么做这件事（一个会让功能静默消失的缺陷）

面板 11 项已经在 core 引擎里全部实现（`C12`），但**安装包发出去的东西里没有它们**。

`04_依赖与SDK/installer-stage/obs-beauty.dll` 是 00:15 的旧构建，308,736 B。用功能开关字符串做对照：

| 字符串 | 旧 stage DLL | 3.1.2 构建 |
|---|---|---|
| `BEAUTY_NECK_HALFW`（脖子通道，0.4） | 无 | 有 |
| `BEAUTY_DETAIL_MID`（锐化，C11） | 无 | 有 |
| `BEAUTY_REG_GAIN` / `BEAUTY_REG_SPOT`（五项，C12） | 无 | 有 |

也就是说：谁按当时的 stage 打一版安装包，装出来的是一个**面板有滑块、背后没有实现**的版本。
面板是动态枚举滤镜属性生成的（`build_form()`），所以界面上看不出任何异常。

同时 stage 里没有 `onnxruntime.dll` / `yunet.onnx`。缺这两个不会让滤镜加载失败
（`beauty_onnx` 是动态加载），但人脸检测会静默失效 → 掩码为空 → 磨皮退化成全帧，
连肤色保护都没了。**这是"不报错、只对拍能看出"的那一类问题**，和 `C12 §6` 那三个 bug 同族。

## 2. 运行时路径约定（改之前必须先确认，否则装错位置）

`beauty_core.cpp` 的 `ensureReady()` 里，两个资源都按**自身 DLL 所在目录**解析：

```cpp
const std::string d = selfDir();                  // = obs-plugins\64bit
beautycore::onnxSetRuntimeDir(d.c_str());         // → d\onnxruntime.dll
mp = d + "\\models\\yunet.onnx";                  // 找不到才退回 d\yunet.onnx
```

`selfDir()` 用的是 `GetModuleHandleExA(... &beautyCoreSetSmoothParams ...)`，
所以它永远是 `obs-beauty.dll` 所在目录，不受工作目录影响。

推论（这三条决定了安装位置，别改）：

| 文件 | 必须装到 | 不能装到 |
|---|---|---|
| `onnxruntime.dll` | `obs-plugins\64bit\` | `obs-plugins\64bit\obs-beauty\` |
| `models\yunet.onnx` | `obs-plugins\64bit\models\` | `obs-plugins\64bit\obs-beauty\models\` |

`obs-beauty\` 是 **NamaSDK 的资源根**（`preset.json`、`assets\`、`fuai.dll` 都在那），
core 引擎从来不看那个目录。放错了的表现和"没装"完全一样。

## 3. 改了什么

### 3.1 stage（`04_依赖与SDK/installer-stage/`）

| 文件 | 动作 |
|---|---|
| `obs-beauty.dll` | 308,736 B / `ada7d19c…` → **474,624 B / `fd7ef358…`**（3.1.2） |
| `obs-beauty-ui.dll` | 本来就是 `cb66fef7…`，未变 |
| `onnxruntime.dll` | **新增**，11,569,696 B / `cd5e3b3e…`（1.20.1，API 版本 20） |
| `yunet.onnx` | **新增**，232,589 B / `4ae92eeb…`（MIT，opencv_zoo） |

`install.bat`（整合包版安装逻辑）同步改造：加 `[5/6]` 装 core 运行时，校验清单 9 → **11 项**。

### 3.2 nsi（`08_安装包/obs-beauty.nsi`）

- 版本拆开：`VERSION` 保留为**面板版本** 3.0.20，新增 `PKGVER = 3.1.2` 作为**安装包版本**。
  之前两者共用一个 define，一升滤镜就会把面板版本也带跑，而且产物文件名会和旧包撞车。
- 新增 `Section "自研引擎运行时 (ONNX Runtime + YuNet)" SecCore`：
  - `onnxruntime.dll` 走**和滤镜 DLL 同一套备份规则**（装之前有就备份，卸载还原）；
  - `models` 目录记 `ModelsCreated` 标志，卸载时只删本包建的那个。
- 源文件自检加了 `core\onnxruntime.dll` 与 `core\models\yunet.onnx`，缺了在开始前就报。
- 组件说明加 `DESC_Core`，欢迎页写明"两套运行时"。

### 3.3 包源布局（`D:\_obspkg_src`，纯 ASCII 路径）

nsi 的 `SRCDIR` 指这里。**这个目录就是整合包的内容**，两边同一份：

```
bin\obs-beauty.dll          bin\obs-beauty-ui.dll
core\onnxruntime.dll        core\models\yunet.onnx
sdk\CNamaSDK.dll  fuai.dll  w32-pthreads.dll  api-ms-…dll  auth_package.bin
sdk\assets\model\ai_face_processor_pc.bundle
sdk\assets\model\ai_face_processor_pc_plain.bundle
sdk\assets\graphics\face_beautification.bundle
README.txt   md5.txt   INSTALL.bat
```

`INSTALL.bat` 重写为按 `bin\ core\ sdk\` 取文件，SDK 用 `xcopy /e /i` **保留 assets 树**。

> 顺带修掉一个旧包的隐患：之前 stage 是**平铺**的，`File /r "${SRCDIR}\sdk\*.*"` 会把两个
> bundle 直接倒进 `obs-beauty\` 根目录，而 SDK 是按 `assets\model\` / `assets\graphics\`
> 相对路径找它们的 —— 结果就是 AI 掩码静默不可用（等价于 region=off）。
> 现在 `sdk\` 里带了正确层级，装出来的结构和已装机目录一致。

## 6. 这一轮踩的坑

| # | 症状 | 原因 | 修法 |
|---|---|---|---|
| 1 | 装出来的包功能少一半，界面看不出来 | stage 里的 DLL 是旧构建，没人核对过 | **打包前先核对功能开关字符串**（`grep -a BEAUTY_REG_SPOT`），别只看文件大小 |

## 8. 开发期怎么装（不打包，直接换 DLL）

用户 2026-10-28 定的原则：**安装包只在最终版打**。开发期用 `02_装机/dev_switch/` 三个脚本：

| 脚本 | 要管理员 | 作用 |
|---|---|---|
| `install_core_test.bat` | 是 | 备份 → 旧 DLL 改名 `.disabled` → 拷滤镜 + ORT + 模型 + **面板 DLL** → 校验 |
| `rollback_to_3.0.19.bat` | 是 | 删新文件 → 恢复旧滤镜 DLL 与旧面板 DLL |
| `run_obs_core.bat` | 否 | 设 `NAMA_ENGINE_IMPL=core` 启动 OBS，只影响该进程树 |

两个注意点：

- **路径必须用通配符定位**（`for /d %%d in ("%ROOT%\00_*")`），项目目录名是中文，
  写死进 .bat 会被 cmd 按 GBK 读成乱码（坑 #3 的同一个原因）。
- **`Program Files` 与 `ProgramData\...\bin\64bit` 里的已有文件都需要提权才能覆盖**。
  `ProgramData` 目录本身能新建文件，但**改已存在的文件**一样 Permission denied ——
  这点容易误判，`touch` 一个新文件能成功不代表能覆盖。

### 8.1 第一次真机装，暴露了四个离线测不出的 bug

这四个都不是算法问题，`verify_roi.py` 和所有离线对拍都测不出来（它们直接调引擎，
不经过 OBS 的滤镜列表、面板，而且**离线脚本显式调了 `ensureReady()`**）。

**bug 1：滤镜列表出现两个同名「OBS美颜」**

双注册（`obs_beauty_filter` + `nama_beauty_filter`）共用同一个 `get_name`，
列表里就是两条一模一样的条目，用户没法选。

修法：旧 id 注册时换 `get_name` → `beauty_filter_name_legacy()` 返回
「OBS美颜（旧场景兼容）」。显示名不参与 id 解析，老场景功能不受影响。

**bug 2：面板认不出新 id 的滤镜**

现象：用新 id 加滤镜后，顶层菜单面板报「没有找到美颜滤镜实例」。

根因不在源码——`obs-beauty-ui.cpp` 的 `isBeautyFilterId()` 早就同时认两个 id。
问题在**装机的面板 DLL 是 10-27 的旧构建**，只认 `nama_beauty_filter`；
10-28 的修复构建一直在 `build_output` 里，从没装进机器。

> 教训：改名这类「全局替换 id」的改动，**不能只核对源码，必须核对装机二进制的字符串**。
> 判据：`grep -a obs_beauty_filter <装机DLL>` 应该有。

**顺带修正的版本号问题**：两个 UI DLL 都自称 3.0.20（10-27 旧构建 / 10-28 修复构建，
内容不同）。修复构建升到 **3.0.21**，滤镜升到 **3.1.3**。

**bug 3：自研引擎在 OBS 里从没加载过人脸模型（滤镜 3.1.4 / core 0.7.1）**

现象（用户原话）：「CPU 跑到了 22%」「而且仅个别功能可以使用」。

`CoreEngine::preheat()` 是个空壳 —— 只 `err.clear()` 就 `return true`，而
`ensureReady()`（`beauty_core.cpp:427`）是**唯一**做 `face_.load("models\yunet.onnx")` 的地方，
`obs-beauty.cpp` 又只在 create 时调 `acquireSlot()`、从不调 `ensureReady()`。于是
`faceOk_` 恒 false → `updateMask()` 第一句 `if (!faceOk_) return false;` →
`haveMask == false`：

- 磨皮走**全帧**路径（`beauty_core.cpp:620-635`），背景一起磨 → CPU 22%
- 清晰 / 美白 / 红润 / 五官五项 / 脸内锐化全在 `if (haveMask)` 里 → **11 项只剩 2 项能用**

修法：`preheat()` 真正调 `ensureReady()`，`acquireSlot()` 加幂等兜底；
日志加 `engine=%s/%s`，core 的 region 措辞改成 `off(无掩码/全帧)`。

> 教训（比前两个更重要）：**「离线验过」不等于「插件里验过」。** 离线脚本自己调
> `ensureReady()` 绕过了插件层，而插件层的初始化路径从没被任何测试覆盖过。
> 以后凡是新增引擎实现，第一件事是核对「宿主里谁负责调 ensureReady」，
> 而不是相信 `preheat` 这个名字。

**复测判据**（缺一条就是没修好）：

1. `init OK (v3.1.4, engine=core/0.7.1, …, region=on, …)`
2. `frame#0 drawn 1280x720 faces=1 engine=core region=on`
3. CPU 从 22% 降到个位数；面板清晰/美白/红润/五官五项都有效果

**守门探针**：`06_离线验证/preheat_probe.cpp`（构建脚本 `build_preheat_probe.bat`）。
它不经过 OBS，直接断言「`preheat()` 之后 `regionActive()==1`」，并带一条反向对照
（模型路径故意给错时必须 FAIL，否则说明断言是空转）。修前恒 0、修后 94 ms 加载成功。
**以后新增引擎实现，先跑这条，再谈真机。**

**bug 4：3.1.4 的修复本身有效，但它把 OBS 崩了两次（滤镜 3.1.5）**

真机日志（崩溃前那次）：
```
[obs-beauty] init OK (v3.1.4, engine=core/0.7.1, sdk=on, region=, item=21328, ...)
```
`engine=core/0.7.1` ✅ —— 3.1.4 的 preheat 修复成立。
但 `sdk=on` 这一格本该是 `sdk=<版本>`，现在却是 `region_state()` 的返回值；
`region=` 后面空着。**格式串错位了**。

根因：加 `engine=%s/%s` 时忘了删掉后面的 `sdk=%s`，7 个占位符配 6 个参数，
`region=%s` 拿到 `e.itemId()`（整数 21328）当指针，`ucrtbase` 解引用即崩。
崩溃栈：`ucrtbase` ← `do_log` ← `blog` ← `obs-beauty.dll` ← `obs_init_module`，
与「模块加载阶段连崩两次」完全吻合（`Crash 2026-10-28 15-03-27/34.txt`）。

> 教训：`blog()` 在 libobs 里**没有** printf 格式标注，`/W3` 不检查格式串 ——
> 这类错误编译器一个字都不会提示。3.1.5 把这一行改成 `std::string` 拼接，
> 结构上不可能再错位；文件头也加了警告。
> **「改日志」不是零风险动作，它能崩宿主。**
