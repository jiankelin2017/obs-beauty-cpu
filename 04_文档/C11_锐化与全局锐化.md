## 1. 结论先行

| 项 | 结果 |
|---|---|
| 实现方式 | 频率分离式回填，高频层从**原图**取，不是对磨完的图做 unsharp |
| 与 SDK 路线的曲线吻合度 | 锐化 50：细频带 142.5%（SDK 138.9%）/ 中频带 155.0%（SDK 149.8%）；锐化 100：187.3% / 206.9%（SDK 193.1% / 209.0%） |
| 背景零改动 | 全局锐化 = 0 时，掩码外**逐字节不变**（0 像素差异，脸外细频带恒 100.0%） |
| 成本 | 1080p：脸内锐化 +1.68 ms，全局锐化 +4.47 ms（基准 5.87 ms） |
| 门控与 SDK 一致 | 磨皮 = 0 时「锐化」无效、「全局锐化」仍生效 |

实测主表（`detail_test.py`，640×394，磨皮固定 50 档；百分比相对**原图**）：

| 配置 | 脸内细% | 脸内中% | 脸外细% | 背景改动像素 | ms |
|---|---|---|---|---|---|
| 磨皮50 锐化0 | 97.1 | 97.0 | 100.0 | 0 | 1.81 |
| 磨皮50 锐化25 | 118.3 | 124.8 | 100.0 | 0 | 3.20 |
| 磨皮50 锐化50 | 142.5 | 155.0 | 100.0 | 0 | 3.32 |
| 磨皮50 锐化100 | 187.3 | 206.9 | 100.1 | 0 | 3.13 |
| 磨皮50 全局50 | 108.9 | 108.3 | 144.6 | 90,219 | 3.47 |
| 磨皮50 全局100 | 117.5 | 113.9 | 183.4 | 93,192 | 3.41 |

**已知取舍（重要）**：core 版**没有做时序 EMA**。SDK 路径用跨帧指数平滑压相机噪点
（3.0.1 修「脸部屏闪」那次），core 引擎目前无跨帧状态，改用**空间软阈值**
（细频带幅值 < 3 灰阶不回填）近似。这只能削掉最细的一段噪点，**不能替代 EMA**。
真机若出现脸部噪点闪动，处置顺序见 §6。

## 2. 为什么不能沿用「对磨完的图做 unsharp」

SDK 2.1.0~2.2.1 就是那么做的，实测磨皮 75 时锐化从 0 推到 100 只能把细节能量拉回
**+0.46**，观感是「糊」——因为双边已经把高频抹掉了，再对磨完的图取高通**没有输入可放大**。

所以高频层必须从 `src`（原图）取：

```
hFine = Y(src) − box3(Y(src))        1~2px：毛孔、睫毛、发丝、相机噪点
hMid  = box3(Y(src)) − box7(Y(src))  3~7px：轮廓过渡、皮肤结构
dst  += w · (fine·hFine + mid·hMid)
```

这样两个滑块彻底解耦：磨皮决定「大尺度抹掉多少」，锐化决定「最细两段放回多少」。
磨皮 50 + 锐化 50 = 皮肤仍然光滑，但毛孔与边缘细节回来。

## 3. 三条与 SDK 版的刻意差别

| 项 | SDK 版（`nama_engine.cpp` 的 `applySharpen`） | core 版（`beauty_smooth.cpp` 的 `detailRefill`） | 为什么 |
|---|---|---|---|
| 频带取自 | 三通道各自取高通（7-tap 滑窗 + 定点） | **只在亮度上取**，增量等量加到 RGB | 省 2/3 成本；三通道独立增益会产生彩边 |
| 噪点抑制 | 跨帧 EMA（`kDetailBetaStill=0.20` + 速度自适应） | **空间软阈值** `thrFine=3` | core 无跨帧状态；EMA 要等「core 有持久状态」再补 |
| 中频带精度 | 1/64 级定点 | float | core 侧本来就是 float 平面，不额外引入量化 |

**软阈值不是随便给的数**：相机噪点与毛孔在幅值上重叠（±2~6 vs 2~8），幅值分不开；
`thr=3` 是从最细的一端切掉噪点、保留毛孔的折中。实测代价很小：

| `BEAUTY_DETAIL_THR` | 锐化 100 时的细频带 | 背景（全局 100）细频带 |
|---|---|---|
| 0（不削） | 213.8% | 191.9%（中调区） |
| **3（默认）** | **187.3%** | **191.9%（中调区）** |

注意第二个数字在两种设置下相同 —— 说明**背景增益弱不是软阈值造成的**（见 §5）。

## 4. 权重与门控（与 SDK 逐条对齐）

```
m = mask/255
fine_eff = m·fine + (1−m)·globalFine
mid_eff  = m·mid  + (1−m)·globalMid
```

| 面板组合 | 脸内 | 脸外 |
|---|---|---|
| 磨皮 > 0、锐化 > 0 | 生效 | **0 字节** |
| 磨皮 > 0、全局锐化 > 0 | 不生效（`fine=0`） | 生效 |
| 磨皮 = 0、锐化 > 0 | **不生效** | 0 字节 |
| 磨皮 = 0、全局锐化 > 0 | 不生效 | 生效 |

「磨皮 = 0 时脸内锐化不生效」不是偷懒，是**对齐 SDK 路线的既有语义**
（`nama_engine.cpp` 的 `wantFaceSharpen = panel[P_BLUR] > 0 && ...`）：
磨皮为 0 时脸内没有细节损失可补，硬要放大只会把噪点放大。

实测验证（`detail_test.py` 尾段）：

| 场景（磨皮 0） | 改动像素 | 期望 |
|---|---|---|
| 面板全 0 | 0 | 0 ✓ |
| 美白 100 | 17,981 | >0 ✓ |
| 红润 100 | 18,162 | >0 ✓ |
| 清晰 100 | 0 | 0 ✓（与 SDK 门控一致） |
| 全局锐化 100 | 109,582 | >0 ✓ |
| 锐化 100 | 0 | 0 ✓ |

> 顺带修掉一个真 bug：旧实现在 `磨皮 = 0` 时**整条链逐字节返回**，导致美白 / 红润 /
> 全局锐化跟着一起失效。这是 CoreEngine 只有 4 项时的历史遗留，与 SDK 路线不一致。

## 5. 实测：三个「看起来不对」的读数，都不是 bug

### 5.1 全局锐化 100 只把背景细频带推到 183%，不是 200%

原因是**亮度截断**：这张素材的背景有 **58.1% 的像素亮度恰好为 0**（纯黑区域），
加正向增量没空间、加负向增量立刻被夹到 0，增益被吃掉一大截。

按区域拆开看：

| 区域 | 细频带比 |
|---|---|
| 背景全部 | 183.3% |
| 背景中调（亮度 20~235） | **191.9%** |

中调区接近理论上的 2.0 倍，说明实现本身是对的，读数差是素材特性。
**这也意味着换一张低对比度素材，同一个滑块会显得更强** —— 标定时不要拿这张图当绝对基准。

### 5.2 「全局锐化」开了，脸内细频带却从 97.1% 涨到 117.5%

不是脸内被锐化了，是**软边掩码**造成的：`m` 在 0~255 之间连续过渡，边缘像素拿到
部分全局权重（`fine_eff = m·0 + (1−m)·1`）。所以脸内涨的是「掩码边缘那一圈」，
不是「整张脸被加锐」。脸内中频带只涨到 113.9，同一原因。

要判断「脸内到底有没有被全局锐化」，看 `fine_eff` 的公式而不是看均值：
`m = 1` 处 `fine_eff` 恒等于 0。这条与 SDK 路线一致（那边掩码内走 `strength=0` 分支）。

> 读表提示：`detail_test.py` 原来把「脸外细%」放在标题为「中%」的列里，两列含义不同，
> 已经改成四列独立（脸内细 / 脸内中 / 脸外细 / 背景改动）。旧的 `detail.md` 若还是
> 三列，重跑一次脚本即可。

---

### 5.3 锐化 100 时「脸外细频带」是 100.1% 而不是 100.0%

掩码外确实一个字节都没改（背景改动像素 = **0**），但指标是 `|Y − box3(Y)|` 的均值，
而 box3 的 3×3 窗口在掩码边界上会**读到脸内的像素**——脸内改了，边界那一圈读数就跟着变。
0.1 个百分点就是这个窗口污染的幅度。判断「背景有没有被改」永远看**改动像素数**，
不看频带读数。

### 6.1 时序 EMA（CoreEngine 0.7.2 / 滤镜 3.1.6）

**问题**：静态纹理帧间相关，传感器噪点帧间独立。高通（本项就是高通）把噪点放大
2~2.5 倍，于是同一张不动的脸逐帧在跳。§6 原来那条「先把 `BEAUTY_DETAIL_THR` 加到 5~6
试试」是治标 —— 阈值抬上去，真纹理也一起被削。

**做法**：对**算高通用的那张亮度平面**做运动自适应 EMA（不是对输出做）。

```
静止（帧间差 ≤ 2.5 灰阶）  β = 0.20   → 白噪声帧间方差压到 1/3
运动（帧间差 ≥ 8.0 灰阶）  β = 1.00   → 完全不平滑
中间线性过渡
```

- 为什么对**输入**而不对**输出**：噪点是被高通放大的，输入先平滑，高通里就没有独立
  噪声了；静态纹理帧间相关，EMA 稳态收敛到自身，纹理 100% 保留。对输出做 EMA 会把
  磨皮结果一起平滑，头一停就出现「由糊转清」的拖影。
- 运动判据：全帧亮度帧间差均值，1/4 分辨率抽样（720p 约 5.7 万次比较）。**没有**复用
  掩码的 `rawChg` —— 无脸时（只有全局锐化）那条路径拿不到它。
- β=1 时**仍然推进历史但不写回亮度平面**，所以那一帧输出与「完全不开 EMA」逐字节相同。
  这一条把「运动时零拖影」变成了可断言的事实。

**验收**（`06_离线验证/diff_ema.py`，1280×720，真机档位 11 项）：

| 判据 | 结果 |
|---|---|
| motion：与 `BEAUTY_EMA=0` 逐帧比 hash | 8/8 帧**完全相同** → 零拖影 |
| static：EMA=1 从第 2 帧起 hash | 恒定 → 历史收敛、无漂移 |
| noise：输出帧间差 | 4.275 → **2.993**（−30.0%） |
| 去掉两档锐化：与 EMA=0 逐帧比 hash | 8/8 帧**逐字节不变** → 只动锐化层 |

把噪声源拆开看「−30%」是谁的功劳：

| 配置 | 输出帧间差 |
|---|---|
| 无锐化（噪声来自磨皮/美白/五官） | 3.013 |
| 有锐化，EMA=0 | 4.275（锐化贡献 **+1.26**） |
| 有锐化，EMA=1 | 2.993（锐化贡献 **≈ −0.02**） |

**锐化带来的那部分闪烁被 100% 消掉**；剩下的 2.99 是磨皮层自身的闪烁，EMA 刻意不碰
（碰它就是拖影）。

**CPU**：隔离锐化层测，300 帧 ×5 次 min-of-5 —— EMA=0 9.24 ms / EMA=1 8.97 ms，
差异落在台架噪声里（符号为负）。额外开销 < 0.5 ms，换算 CPU < 0.6 个百分点。

**环境变量**：`BEAUTY_EMA=0` 关闭；`BEAUTY_EMA_STILL` / `_FULL` 改两个阈值；
`BEAUTY_EMA_BETA` 改静止时的 β。

## 8. 事实 vs 推测

**可验证事实**：§1 / §4 / §5 的全部数字由 `detail_test.py` 复现；`verify_roi.py` 三档
分辨率 ROI 与多线程 `maxdiff=0`；§6.1 的 EMA 数据由 `diff_ema.py` 复现；
当前插件 `obs-beauty.dll` 483,328 B md5 `98ff87f2…`（3.1.7 / core 0.7.2）。

**推测（未实测）**：全局锐化在 4K 上的成本按面积线性外推约 +16 ms；
时序 EMA 的观感收益只有真机开 30fps 才能确认 —— 离线能证明的是「帧间差下降」
与「运动帧逐字节不变」，证明不了「人眼觉得不闪了」。
