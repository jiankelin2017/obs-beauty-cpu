# OBS 美颜插件 —— 一级入口说明

> ⚠️ **本文写于 2026-10-26（当时版本 3.1.6~3.1.8），只讲"顶层菜单 + 面板入口"这一条链路，不是现状快照。**
> 当前已装机 **3.1.26 / core 1.4.0**，权威现状见 `00_先读我.md` 顶部 ◆ 速览。
> 文中涉及的**旧命名 `obs-nama-beauty*` 已于 2026-10-30 全部改为 `obs-beauty*`**（面板现为 `obs-beauty-ui`，
> 装机在 `C:\ProgramData\obs-studio\plugins\obs-beauty-ui\bin\64bit\`），读到旧名字请按此替换。


把 FaceUnity NamaSDK 美颜滤镜的操作入口放到 OBS 的**一级页面**（不用先进滤镜属性页），  
做法对齐商业插件「插件中心」：在 OBS 菜单栏最右侧加一个自己的顶层菜单。

---

## 一、两个入口

| # | 入口                    | 位置     | 技术实现                                          | 依赖                |
| - | --------------------- | ------ | --------------------------------------------- | ----------------- |
| 1 | **「美颜(\&A)」菜单** ← 主方案 | 菜单栏最右侧 | 原生 Qt6 插件，`QMainWindow::menuBar()->addMenu()` | 无                 |
| 2 | **「美颜面板」Dock** ← 备选   | 右侧停靠区  | 自定义浏览器 Dock + obs-websocket                   | 需启用 websocket 服务器 |

**为什么主推菜单**：它不依赖任何外部通道。Dock 面板要走 websocket，  
而 websocket 服务器默认是关的，多一个可能失效的环节。

两个入口可以同时存在，互不冲突。

### 菜单入口长什么样

```
菜单栏:  文件(F)  编辑(E)  视图(V)  场景集合  配置文件  工具(T)  帮助(H)   美颜(&A) ← 这里
                                                                              ├ 参数面板...
                                                                              └ 关于
```

点「参数面板...」弹出一个独立窗口：

- 顶部下拉框列出**当前场景里所有**「OBS美颜」滤镜实例（源名 → 滤镜名）
- 下面按「美颜 / 美型 / 全局」分组显示全部参数
- **面板不硬编码参数表**，而是遍历滤镜自己的 `obs_properties` 动态生成  
  → 滤镜那边改参数名/范围/新增参数，面板自动跟随，不用改两处
- 滑块拖动即时生效；双击滑块回到默认值；底部有「恢复默认」

## 二、安装

### 步骤 1：滤镜插件（已在位）

```
C:\Program Files\obs-studio\obs-plugins\64bit\obs-nama-beauty.dll
```

### 步骤 2：菜单插件（已在位）

```
C:\ProgramData\obs-studio\plugins\obs-nama-beauty-ui\bin\64bit\obs-nama-beauty-ui.dll
C:\ProgramData\obs-studio\plugins\obs-nama-beauty-ui\data\locale\en-US.ini
```

> 放在 `ProgramData` 的全局插件目录，**不需要管理员权限**，与 obsplus 同级。

> ⚠️ **目录名必须与 DLL 文件名完全一致**（`obs-nama-beauty-ui` / `obs-nama-beauty-ui.dll`）。  
> OBS 的 ProgramData 插件扫描规则是找 `<插件目录名>/bin/64bit/<插件目录名>.dll`，  
> 名字对不上会**静默跳过，且不写任何日志**——表现就是"插件像没装一样"，  
> 极难排查。改名前请先用 `check_e2e.py` 确认。

### 步骤 3：配置收口（需要 OBS 关闭）

双击运行：

```
beauty_panel\enable_entry.bat
```

它会等 OBS 退出（最多 1 小时）后自动完成三件事：

1. 启用 obs-websocket 服务器（端口 4455）
2. 把「美颜面板」注册进 `user.ini [BasicWindow] ExtraBrowserDocks`
3. 清掉此前误写在 `global.ini [Basic]` 里的同名键

> **为什么必须等 OBS 关闭**：OBS 退出时会把自己内存里的设置写回配置文件，  
> obs-websocket 退出时也会重写自己的 `config.json`。运行中改的会在退出瞬间被冲掉。

只想用菜单入口的话，这一步可以跳过——菜单不依赖它。

### 步骤 4：启动 OBS

菜单栏最右侧出现「美颜(\&A)」即为成功。

## 七、验证指标的重要说明（别被「0%」误导）

`plugin_verify2.py` 读的是插件自检里的**细节能量**（mean |Laplacian|）。这个指标对  
**纹理锐度**敏感，但对**几何位移不敏感** —— 所以「美型/立体」类参数会显示成 0.0%，  
看起来像无效，其实只是指标看不见。

实测对比（`blur_test/probe_threed.py`，同一张静态图，两个指标同时算）：

| 参数                     | mad（平均绝对像素差） | max | 细节能量变化      | 性质    |
| ---------------------- | ------------ | --- | ----------- | ----- |
| `face_threed`（五官立体）    | **1.1115**   | 17  | **+0.09%**  | 几何变形  |
| `blur_level`（磨皮 70）    | 1.7714       | 36  | **−31.18%** | 纹理变化  |
| `clarity`（清晰 100）      | 4.9040       | 12  | **+8.08%**  | 纹理变化  |
| `cheek_narrow`（窄脸 100） | 5.7579       | 186 | **−6.56%**  | 几何+纹理 |

`face_threed` 的 mad=1.11 远超历史报告「有效」阈值 0.5，差异图（`cmp/threed_face_threed_diff.png`，  
放大 10 倍）显示变化**精确集中在人脸五官区域** —— 它是有效的几何变形参数。

> **结论**：`face_threed`（五官立体）**有效**，此前"疑似无效"的判断是**指标选错**导致的误判。  
> 判断美型类参数必须用 mad / 差异图，不能只看细节能量。
>
> 已确认真正无效的参数只有两个：`tooth_whiten`（美牙）、`delspot_level`（祛斑痘）。

## 八、内存泄漏排查：与本插件无关

OBS 日志末尾的 `Number of memory leaks` 从历史稳定值 **15** 一度涨到 347 / 3889 / 224。  
逐项取证后确认，**泄漏源是第三方插件 `obs-cam-beauty`（由 obsplus「插件中心」加载），  
不是本插件**。

**证据 1 — 模块级 diff**：把 15 泄漏的会话与 224 泄漏的会话做模块列表差分，  
后者只多出三个模块：

```
obs-cam-beauty.dll
obs-cam-beauty_qt6.dll
websocket.dll
```

**证据 2 — 全量相关性表**（`cam-beauty` 是否为泄漏的唯一自变量）：

| cam-beauty 加载 | 本插件 UI 模块 | 泄漏数                     |
| ------------- | --------- | ----------------------- |
| 否             | 否         | 15                      |
| 否             | **是**     | **15** ← 只加载本插件，与基线完全相同 |
| 是             | 是         | 347 / 3889 / 224        |

**反证**：20:20 那次会话本插件的滤镜真的挂在了「视频采集设备」上并渲染了帧，  
64 秒只有 **15** 泄漏；而 21:41 那次 13 秒空转、本插件一次都没渲染，却泄漏 **224**。  
泄漏量与本插件的活动量无正相关。

> **方法学提醒**：`Number of memory leaks` 是全局计数。看到它上涨时，不能因为  
> "最近改的是哪个插件" 就直接归因——必须做模块级 diff + 多会话相关性表。

## 十一、美颜参数 BUG：根因、修复与验证（2026-10-13 23:xx）

### 现象

> 「打开美颜功能画面直接有问题，点击恢复默认直接卡死。」

### 结论速览

| 症状                        | 状态                                                                      |
| ------------------------- | ----------------------------------------------------------------------- |
| 打开美颜 → **画面直接有问题**        | ✅ **已定位并修复**：`filter_level` 缺单位换算，默认参数下 85~87% 像素被推到纯白。修复方式见「根因 A」与第十二节 |
| 点击恢复默认 → **卡死**           | ⚠️ **尚未复现**。原先的跨线程 GL 假设已被 A/B 实验**证伪**（见下）。已埋好分步诊断日志（第十二节 ①），下次复现能直接定位 |
| 渲染线程之外调用 `wglMakeCurrent` | ✅ 仍然修掉了（防御性正确性），但**不是**上面症状的成因                                          |

### 根因 A（已证实）：filter_level 缺单位换算

`nama_apply_params()` 里，31 个滑块参数都做了面板→SDK 换算，唯独 `filter_level` 漏了：

```c
for (int i = 0; i < NAMA_NPARAM; i++)
	g_fuItemSetParamd(g_item, g_params[i].key, f->v[i] / 100.0 * g_params[i].sdk_max);
...
g_fuItemSetParamd(g_item, "filter_level", f->filter_level);   // ← 少了 /100
```

面板刻度 0..100（属性页滑块，默认 **40.0**），而 SDK 的 `filter_level` 是 **0..1** 的  
混合强度。原样传 40.0，SDK 就按「40」处理（内部截断 = 满强度）。

实测（静态图，`blur_test/probe_filter_level.py`；过曝 = 像素值 > 250 的占比）：

| 面板 filter_level | 修复前 亮度 / 过曝       | 修复后 亮度 / 过曝      |
| --------------- | ----------------- | ---------------- |
| 0               | 130.9 / 0.6%      | 130.9 / 0.6%     |
| 5               | 244.4 / **69.7%** | 132.3 / 0.6%     |
| 10              | 252.2 / **86.4%** | 133.7 / 0.6%     |
| **40（默认值）**     | 247.4 / **87.5%** | **142.2 / 0.6%** |
| 100             | 245.2 / **87.5%** | 159.2 / 0.0%     |

隔离测试：默认参数下滤镜 `ziran2@40` → 修复前 **过曝 85.0%**，修复后 **过曝 0.0%**。

**这就是「打开美颜画面直接有问题」**：滤镜一启用，画面接近全白。

旁证（三处互相矛盾）：`nama_init()` 模块级默认写的是 `0.4`（正确的 SDK 单位）；  
`nama_migrate()` 把 legacy 值按 `sdk_max=1.0` 迁移 —— 都说明这一项本该 `/100`。

**第一版修复**（只补一个 `/100`）：

```c
g_fuItemSetParamd(g_item, "filter_level", f->filter_level / 100.0);
```

能解决问题，但**没有解决「为什么会漏」**。`filter_level` 是唯一一个不在  
`g_params[]` 里的参数，于是它天然逃出了那条统一循环，也就天然容易被漏掉。  
第十二节 ② 把它收进表里，从结构上消除了这类遗漏。

### 已证伪的假设：跨线程 GL 上下文冲突

最初怀疑 `nama_enter()` 的 `g_saved_dc / g_saved_ctx` 是全局变量，UI 线程与渲染线程  
互相覆盖，导致画面异常 / 卡死。为此专门做了 A/B 对照：把修复前后的两个二进制  
都跑同一套压测。


**结果：未修复的旧版也通过了压测** —— 该假设不成立。原因是：

> 本机 OBS 跑的是 **D3D11**（日志 `Initializing D3D11...` /  
> `Loading up D3D11 on adapter NVIDIA GeForce RTX 5060 Laptop GPU`）。  
> D3D11 下渲染线程**本来就没有 GL 上下文**，`wglGetCurrentContext()` 在两个线程上  
> 都返回 NULL —— 全局变量被覆盖成 NULL，和原本的值一样，**不产生任何破坏**。

跨线程 GL 的问题只在 **OpenGL 渲染器**下才成立。修掉它仍然是正确的（消除潜在风险），  
但**不能**拿它解释用户报的现象。

> 教训：**假设必须用对照实验证伪。** 「自洽」和「正确」是两件事 —— 这个假设读起来  
> 完全说得通，还配上了源码证据，但一次 A/B 就推翻了它。如果不做 A/B，  
> 就会把一个错误根因当成结论交出去。

### 修复 2（防御性）：SDK/GL 调用收敛到渲染线程

虽然 A/B 已证明它不是本次症状的成因，但「渲染线程之外调用 `wglMakeCurrent`」  
本身仍是真实隐患（换 OpenGL 渲染器就会发作），所以保留这组改动：  
把 SDK/GL 调用**全部收敛到渲染线程**。

1. `struct nama_filter` 增加 `bool dirty`；
2. `nama_filter_create` / `nama_filter_update` 只做 `f->dirty = true`  
   （`nama_filter_read` / `nama_migrate` 只读写 `obs_data`，UI 线程安全）；
3. `nama_filter_render` 在 `!g_ready / !enabled / !target` **早退之前** flush：
   ```c
   if (f->dirty && g_ready && g_item > 0) { f->dirty = false; nama_apply_params(f); }
   ```
   （放在早退前，这样「停用美颜」的改动也能在当帧同步 `is_beauty_on`）
4. `g_saved_dc` / `g_saved_ctx` 改成 `__declspec(thread)` 线程局部，彻底杜绝这一类 bug。

**附带修**：UI 插件原来每点一次「参数面板」就 `new` 一个新对话框，会叠出一堆；  
改为单例（已有面板则提到前台，`destroyed` 信号里置空指针）。

### 旧测试为什么没抓到

`blur_test/plugin_verify2.py` 是「改场景集 JSON + **重启 OBS**」式的，每个用例重新启动一次。  
它走的是滤镜的 **create 路径**，**从头到尾没有调用过 `obs_source_update`** ——  
而 BUG 只存在于「运行时改参数」路径上。所以它 10/10 通过，面板照样卡死。

> 教训：**"旧测试全绿"不等于覆盖到了新路径。** 必须按代码路径设计测试，不能只看通过率。

## 十二、根因修复的工程化收口（2026-10-13 23:4x）

第十一节的结论是「补一个 `/100` 就修好了」。但**补漏不等于收口** ——  
真正要解决的是「为什么偏偏这一项会被漏掉」。以下四件事按顺序做完。

### ① 给「恢复默认」埋分步诊断日志

「点击恢复默认卡死」一直没复现，而它可能卡在三处，靠猜没有意义：

| 可能的卡点                                       | 特征                                                    |
| ------------------------------------------- | ----------------------------------------------------- |
| `nama_filter_get_defaults` / `nama_migrate` | 纯内存操作，几乎不可能卡                                          |
| `obs_source_update`                         | 它会**同步**回调滤镜的 `update`，而 `update` 要拿源上的锁 —— 可能和其它线程互等 |
| 渲染线程的 `nama_apply_params`                   | `wglMakeCurrent` + 调 SDK，驱动/SDK 卡住时画面停住               |

于是两个「恢复默认」入口（滤镜属性页的 `nama_btn_reset`、顶层面板的 `reset_defaults`）  
在关键步骤前后各打一行**带线程号**的日志。复现时看日志停在哪一行即可定位：

```
[nama-beauty] reset-trace: enter (filter properties page) (thread 23184)
[nama-beauty] reset-trace: defaults filled (thread 23184)
[nama-beauty] reset-trace: migrate done -> calling obs_source_update (thread 23184)
[nama-beauty] reset-trace: update: enter (thread 23184)
[nama-beauty] reset-trace: update: settings read (thread 23184)
[nama-beauty] reset-trace: update: return (thread 23184)
[nama-beauty] reset-trace: obs_source_update returned (render thread applies later) (thread 23184)
[nama-beauty] reset-trace: render: applying params to SDK (thread 30012)   ← 另一个线程号
[nama-beauty] reset-trace: render: applied (thread 30012)
```

读法：

- 卡在 `calling obs_source_update` 之后、`update: enter` 之前 → 卡在**拿源锁**上；
- 卡在 `render: applying params to SDK` 之后没有 `render: applied`，且线程号与 UI 线程不同  
  → 卡在**渲染线程的 SDK 调用**里；
- 全部走完 → 与「恢复默认」无关，卡在别处。

顺带：渲染线程那次写入耗时 ≥100ms 会额外打一条 `WARNING`，SDK 偶发变慢也能看见。

> 这两行日志是**临时的**。定位完这个 bug 后可以降成 `LOG_DEBUG` 降噪。
>
> **已执行（降噪收口）**：`nama_filter_update()` 里的 `update: enter/…/return`
> 与渲染线程那两行 `render: applying/applied` 已改为 `LOG_DEBUG`——它们是热路径，
> 拖一次滑块就会触发多次，按 `INFO` 落盘会淹没日志并在 UI/渲染线程上产生无谓写盘。
> 两个「恢复默认」按钮入口仍保留 `LOG_INFO`（低频、用户主动触发），诊断信息不丢。
> 耗时 ≥100ms 的 `WARNING` 保持不变。

### ② `filter_level` 收进参数表（结构上消除这类遗漏）

新增分组 `NAMA_G_FILTER`，并在 `g_params[]` 末尾追加：

```c
#define NAMA_G_BEAUTY 0
#define NAMA_G_SHAPE  1
#define NAMA_G_FILTER 2
...
{"filter_level", "滤镜强度", NAMA_G_FILTER, 40.0, 1.0},
```

**改动清单**（都是「删掉手写、交给统一循环」）：

| 位置                           | 改动                                                                              |
| ---------------------------- | ------------------------------------------------------------------------------- |
| `nama_apply_params()`        | 删掉手写的 `filter_level` 写入 —— 它现在由那条统一循环负责                                         |
| `nama_filter_properties()`   | 删掉手写的 `filter_level` 滑块；新增 `grp_filter` 分组，滑块由统一循环生成                            |
| `struct nama_filter`         | 删掉已成死字段的 `double filter_level` —— 值现在存在 `f->v[]` 里                              |
| `nama_filter_read()`         | 删掉单独读 `filter_level` 的一行                                                        |
| `nama_filter_get_defaults()` | 删掉单独设 `filter_level` 默认值的一行（由循环按 `dflt` 设）                                      |
| `nama_migrate()`             | 表里本来就有 `filter_level`；以前查 `sdk_max` 查不到会落到兜底 `1.0`，现在能查到真正的 `1.0` —— 值相同，但不再是巧合 |

**一个容易踩的坑**：属性页的滑块是「遍历参数表」生成的，所以 `filter_level` 进表后  
会自动多出一个滑块。如果忘了删手写那一行，属性页就会出现**两个「滤镜强度」**，  
而且两个滑块写的是同一个 key —— 拖动时会互相打架。  
`blur_test/probe_param_table.py` 就是专门守这个的。

**顺序**：`filter_name` 必须排在 `filter_level` 之前（SDK 先按名字载入滤镜，再按强度混合）。  
`filter_name` 是字符串、不在表里，仍手写；为让它在属性页里显示在强度上面，  
「滤镜」分组里的 `filter_name` 列表要**先建**，之后才跑统一循环。

### ③ 顶层面板的刷新时机改用 `Show` / `WindowActivate`

面板原本是「读一次 → 建控件」的快照式，也不订阅滤镜信号，所以在滤镜属性页改了参数，  
面板上的滑块不会跟着动（数据是同一份，只是显示不刷新）。

考虑过 `obs_source_add_signal` 订阅参数变化，但**放弃了**：那个回调是从 OBS 的  
工作线程发出来的，在里面直接碰 Qt 控件就是跨线程操作 UI —— 会崩，或者偶发地崩。

改成一个笨但绝对安全的做法：面板每次被**显示**（`QEvent::Show`）或**重新被激活**  
（`QEvent::WindowActivate`，即用户从别的窗口切回来）时，重新读一遍当前设置、重建控件。  
全部发生在 UI 线程里，用户切回来看到的就是最新值。

```cpp
bool event(QEvent *e) override
{
	const QEvent::Type t = e->type();
	if (t == QEvent::Show || t == QEvent::WindowActivate)
		sync_now();
	return QDialog::event(e);
}
```

`sync_now()` 有重入保护（`syncing_`），且**只重建表单、不重新枚举源** ——  
枚举有开销，还会把用户当前选中的那个实例跳掉。若之前没找到滤镜（比如面板先开着、  
之后才加滤镜），则会重新枚举一次，找到就自动接上。

另外挡了两种情况，都不重建：

```cpp
if (QApplication::mouseButtons() != Qt::NoButton) return;   // 正在拖滑块
if (!isVisible()) return;
```

第一条是必须的：`build_form()` 会把旧控件 `deleteLater()`，如果用户**正按着滑块拖动**  
时窗口被别的弹窗抢走焦点、又切回来，那个正在拖的滑块就被删掉了 —— 会崩。  
「拖到一半窗口被激活」很少见，但挡一下成本极低。

### ④ 新增回归：`blur_test/probe_param_table.py`

`filter_level` 进表带来的新风险是「属性页出现两个同名滑块」，而这是纯结构问题，  
不需要启动 OBS 就能查。脚本分两部分：

**第一部分（静态，不启动 OBS）** —— 直接读源码，剥掉注释后检查：

```
[OK]   参数表共 32 条：NAMA_G_BEAUTY 11 / NAMA_G_SHAPE 20 / NAMA_G_FILTER 1
[OK]   参数表内 key 无重复
[OK]   filter_level 在表里且只出现一次
[OK]   filter_level 属于 NAMA_G_FILTER 分组
[OK]   filter_level 面板默认值 == 40.0
[OK]   filter_level sdk_max == 1.0
[OK]   属性页没有手写 filter_level 滑块（滑块应由统一循环生成）
[OK]   nama_apply_params() 里没有手写 filter_level 写入（应由统一循环写入）
[OK]   结构体里没有残留的 f->filter_level 死字段
[OK]   nama_apply_params() 有「遍历 g_params[] 统一写入」的循环
[OK]   默认值没有单独手写 filter_level（应由循环按 dflt 设置）
[OK]   NEUTRAL 里的每个滑块键都在参数表中
[OK]   参数表里没有 NEUTRAL 不知道的滑块
[OK]   NEUTRAL 共 37 键（27 滑块 + 10 其它）

```

两个细节值得记一下：

- **必须先剥注释**。参数表的说明注释里**故意**写着旧写法  
  （`g_fuItemSetParamd(g_item, "filter_level", f->filter_level);`）作为反面教材，  
  不剥注释的话「不许再手写」这一条会被自己的注释判失败。脚本里为此专门写了  
  `strip_comments()`（保留字符串字面量），并加了一条「剥完代码仍然完整」的自检，  
  防止剥过头导致假通过。
- **检查范围要限定在 `nama_apply_params()` 函数体内**。`nama_init()` 里还有一处  
  `g_fuItemSetParamd(g_item, "filter_level", 0.4);` —— 那是**模块级**初始值  
  （此时还没有任何滤镜实例，写的是 SDK 单位 0.4），属于合理存在，不算漏换算。  
  第一版检查没限定范围，把它误判成失败。

**第二部分（`--live`，需要独占 OBS）** —— 起一次 OBS，用 obs-websocket 的  
`GetSourceFilterDefaultSettings` 拿滤镜默认设置，核对：

- 键数正好 **37**（27 滑块 + 10 其它）
- `filter_level` 默认 == **40.0**（面板刻度，不是 SDK 的 0.4）  
  —— 这一条直接验证了「默认值改由循环按 `dflt` 设置」没有改坏
- 键集合与 `plugin_verify2.py` 的 `NEUTRAL` 完全一致（NEUTRAL 是跑测试时喂给滤镜的那份，  
  两边必须对得上）

## 十三、崩溃堆损坏、画面旋转与移除重复滤镜（2026-10-14 11:10 最终验证）

### OBS 最近一次卡死/崩溃：堆损坏证据与代码修复

Windows「应用程序错误」日志记录 OBS 在 **00:31:02、00:32:20、00:32:52** 三次异常退出：

- 进程：`obs64.exe`（OBS 32.1.1）
- 异常码：`0xC0000374`（Windows heap corruption，堆损坏）
- 报错模块：`ntdll.dll`（堆检测器发现损坏的位置；不等于 ntdll 本身是根因）
- OBS 自己的运行日志在退出前还出现 `QFormLayout::takeAt: Invalid index 0`。

**已从 WER 时间点 + OBS 分阶段日志 + C++ 对象所有权代码定位并修复主因：布局清理时把同一个 Qt 布局对象释放了两次。**

`purge_layout()` 对 `QLayoutItem *it = lay->takeAt(0)` 执行：

```cpp
if (QLayout *l = it->layout()) {
    purge_layout(l);
    delete l;
}
delete it;
```

Qt 的子布局对象 `l` **本身就是这个 `QLayoutItem`（`l == it`）**，所以先 `delete l`、  
再 `delete it` 是 double-free。面板每次重建时，`form_` 都包含一个 `main_form` 子布局；  
而面板首次显示 / 激活时会再次 `build_form()`，正好走到这条路径，破坏堆。日志在  
**10:37:16.692 `build_form: done` 后 27ms 的 10:37:16.719 `build_form: begin`** 结束；  
同一秒的 Windows WER 记录 `obs64.exe` 异常 `0xC0000374`（heap corruption）。这次时间和  
崩溃点对上了，且反复重建会稳定再次走到同一段释放逻辑。

**修复主因**：递归清理子布局的内容后，不再单独 `delete l`；最后统一 `delete it` 一次。  
同时 `purge_layout()` 现在先检查 `count()>0` 再 `takeAt(0)`，不再对空布局取下标 0。


**另发现并一并修复一个独立的悬空指针缺陷**：`obs_property_name(p)` 的借用 `const char*`  
曾被滑块/复选框回调长期捕获，而 `build_form()` 末尾销毁了其 `obs_properties_t`。改为复制  
`std::string key_s` 后按值捕获。它本身也可能造成堆损坏，但本次日志精确显示卡在第二次  
`build_form` 开头，因此**主因是前述 double-free，而不是把 UAF 当成结论**。

此次 WER 的 fault module 是 `ntdll.dll`，它报告堆损坏位置，不是根因模块。

### 「镜头画面旋转」下拉无可见效果：原因与修复

旧代码只有 `fuSetDefaultRotationMode(f->rotate)`。这是给 NamaSDK 的**人脸识别方向提示**，  
不会旋转 SDK 返回的 RGBA 像素；旧渲染管线也没有任何像素旋转操作。因此下拉值可能改变  
人脸检测结果，但摄像头预览本身不转——这是界面功能与实现不一致，不是调用线程卡住。

**修复已通过像素回归**：滤镜输出阶段执行 RGBA 旋转：上=0°、右=顺时针 90°、下=180°、左=逆时针 90°；  
90°/270°时保持 OBS 原纹理尺寸，按比例缩放居中，空余区域填黑，避免拉伸/裁切。方向值也继续  
传给 SDK 用于识别方向，镜像在旋转之后应用。属性名现为「镜头画面旋转」，并说明方向角度及留边行为。

`blur_test/probe_rotation_output.py` 实测四个方向：

| --------- | -------------- | -----: |
| 上 0°      | `6baa2ea92bab` |   0.0% |
| 右 顺时针 90° | `53e859045e84` |  62.2% |
| 下 180°    | `aaca7019bcab` |   0.0% |
| 左 逆时针 90° | `76d0011989aa` |  62.2% |

### Q1 导入表原文（`dumpbin /dependents`）

```
滤镜 obs-nama-beauty.dll
    obs.dll          ← OBS 本体
    USER32.dll       ┐
    GDI32.dll        ├ Windows 系统
    OPENGL32.dll     │
    KERNEL32.dll     ┘

UI  obs-nama-beauty-ui.dll
    obs.dll              ← OBS 本体
    obs-frontend-api.dll ← OBS 本体
    Qt6Widgets.dll       ┐
    Qt6Gui.dll           ├ OBS 本体自带（bin/64bit 下）
    Qt6Core.dll          ┘
    KERNEL32.dll         ← Windows 系统
```

**关键点**：`CNamaSDK.dll` **不在**导入表里 —— 它是运行时  
`LoadLibraryExA(<DLL目录>\obs-nama-beauty\CNamaSDK.dll, NULL, LOAD_WITH_ALTERED_SEARCH_PATH)`  
按需加载的。这意味着：

- 不需要用户预装 FaceUnity SDK，也不会和系统里别的 SDK 版本抢；
- `LOAD_WITH_ALTERED_SEARCH_PATH` 让 `fuai.dll` 从 **SDK 自己所在目录**解析，  
  不写进全局 DLL 搜索路径（不会影响别的插件）；
- 少了 SDK 文件时只是滤镜 `init failed` 并**直通**（`obs_module_load` 仍返回 true），  
  不会让 OBS 起不来。

### Q2 唯一备注：UI DLL 里的两条 Qt 头文件路径

`strings` 扫出 UI DLL 里有：

```
C:\Qt\include\QtCore/qbytearrayview.h
C:\Qt\include\QtCore/qobjectdefs_impl.h
```

这不是我们源码写的（`grep '#include'` 确认本工程只 include `<QtWidgets/...>`、`<QtCore/...>`  
形式）。它来自 Qt 头文件里内联的 `Q_ASSERT` / `qFatal` 宏，`__FILE__` 展开成构建机的  
`C:\Qt\include\...`。**影响面仅外观**：只有 Qt 内部断言真的触发时才会把这条路径打进  
日志/崩溃框；不影响加载、不影响功能。若要彻底清掉，可给 `cl.exe` 加 `/d1trimfile:C:\Qt\`  
（本次未做，因为没有实际收益）。

### 18.4 删不动的两个文件：UAC 令牌问题

`obs-nama-beauty.dll` 和 `obs-nama-beauty\` 第一次删不掉，报 `Some operations were aborted`，`mv` 则报 `Permission denied`。查 ACL 后定位：

```
BUILTIN\Users           ReadAndExecute, Synchronize   ← 只有读+执行，没有写
```

而当前会话 `[WindowsPrincipal]::IsInRole(<user>)` = **False** —— 是 UAC **过滤令牌**，<user>s 组被摘掉，只剩 `Users` 权限。同目录下其他文件能删是因为走了环境的 safe-delete 包装层（它会 fallback），这两个没走通。

最终用 `Start-Process -Verb RunAs` 拉起提权批处理删掉（会弹一次 UAC）。UI 插件在 `ProgramData` 下，那个目录 `Users` 有 `Write`，所以无需提权直接删。

**结论**：往 `C:\Program Files` 写/删东西，本环境的普通 Bash 会话做不了，必须显式提权。
