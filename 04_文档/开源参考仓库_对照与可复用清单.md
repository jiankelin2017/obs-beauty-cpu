# 开源参考仓库 · 对照与可复用清单

> 2026-10-28 · 五个仓库已逐个核实。**核心结论：只有 2 个能抄代码，3 个只能读思路。**

## 0. 三条结论

1. **许可证是分水岭**：`lumina-beauty` 的核心 SDK 和 `wuxiwuhen/obs-beauty-filter` 是 **MIT**，
   可以直接借鉴代码；另外三个是 **GPL-2.0**，抄了我们的闭源插件就得跟着开源。

2. **`wuxiwuhen` 的 158 行 effect 是最直接的可用资产** —— 频率分离 + 肤色窗 + Sobel 边缘门控，
   参数全部写死在文件里，已归档到 `09_开源参考/MIT_wuxiwuhen_beauty_filter.effect.txt`。

3. **比算法更值钱的是架构洞察**：三个成熟实现（lumina / wtnl-zhi / wuxiwuhen）**没有一个回读全帧**。
   它们用「椭圆 mask」替代「逐像素肤色分割」，从而让磨皮全程留在 GPU 上。
   我们现在每帧搬 8 MB（1080p RGBA）上下各一次 —— 这笔开销至今没测过，可能比磨皮本身还贵。

## 2. 可直接落地的三项

### 2.1 频率分离替代双边滤波（MIT，代码可直接抄）

`wuxiwuhen` 的做法是 5 个 pass：

```
输入 ──► BlurH1 ──► BlurV1 ──► BlurH2 ──► BlurV2 ──┐
  │            （两轮级联高斯，等效 σ≈12）            ├─► Composite ──► 输出
  └──────────────────────────────────────────────────┘
```

**合成公式**（`PSComposite`）：

```
low   = 两轮高斯后的低频层
high  = orig - low                     // 高频 = 毛孔、痘印、纹理
mask  = SkinMask(orig)                 // YCbCr 肤色窗
edge  = saturate(sobel(luma) * 10.0)   // 梯度大 = 真边缘（眉毛/眼镜/发际线）
atten = mask * (1 - edge) * strength
out   = low + high * (1 - atten)
```

**全部参数**（可直接用）：

| 参数 | 值 | 说明 |
|---|---|---|
| 高斯权重 | 0.40260 / 0.24419 / 0.05449 | 5-tap，归一化的 exp(-k²/2) |
| 高斯偏移 | 0 / 8.8 / 17.6 px | 两轮级联后等效 σ≈12 |
| 肤色窗 Cb | 77 ~ 127（255 制） | 即 0.301961~0.498039 |
| 肤色窗 Cr | 133 ~ 173 | 即 0.521569~0.678431 |
| 窗软化带 | 0.03 | 越大过渡越柔 |
| 边缘灵敏度 | ×10.0 | **越小越保细节** |
| 美白 gamma | `1 + (0.52-1) × strength` | 0.52 是提亮上限 |

**与我们现有双边滤波的对比**：

| | 我们的双边（r=2, 25-tap） | 频率分离（4×5-tap + 1 composite） |
|---|---|---|
| 采样次数 | 25 次/像素，带颜色查表 | 20 次（可分离，单方向） |
| 边缘保护 | **隐式**：颜色差大 → 权重小 | **显式**：Sobel 梯度门控 |
| GPU 化难度 | 高（要用 ping-pong 做 25 次采样，且查表要在 shader 里算 exp） | **低**：4 个可分离模糊 pass，标准做法 |
| 参数语义 | σSpace/σColor 不直观 | 磨皮强度 = 高频衰减量，直观 |
| 美白 | 无 | 同一个 pass 里顺带做完 |

**顺带一个踩坑**（作者写在文件头）：`smoothstep` / `lerp` **不在 OBS effect 的内置函数表里**，
必须手动展开。这个坑我如果自己写 shader 会踩，现在省了。

### 2.2 椭圆 mask + 异步推理：把全帧往返彻底去掉

这是三个仓库的共同做法，也是**我们最大的结构性浪费**。

**我们的现状**（`obs-beauty.cpp` 第 551 行注释就写着 `capture -> CPU roundtrip -> Nama -> draw`）：

```
每帧：gs_texrender 抓帧(1080p 8MB) → gs_stagesurface_map 下载到 CPU
     → CPU 磨皮 4.88ms → gs_texture_set_image 上传 → 画到屏幕
```

**它们三个都不这么做**：

| 项目 | mask 怎么来 | 检测怎么跑 | 结果 |
|---|---|---|---|
| wtnl-zhi | **脸部椭圆轮廓**，保护眼睛/嘴部；"**不是像素级皮肤分割**" | 双 staging + 有界工作线程，**只保留最新帧**，渲染端不等 | 渲染线程永不阻塞 |
| wuxiwuhen | 纯 YCbCr 肤色窗（shader 内算，零检测） | 不检测 | 零 CPU 往返 |
| lumina | 人像分割模型，掩码边缘细化 | MediaPipe ONNX（CPU），独立线程 | 引擎自己管 GL 上下文 |

**关键洞察**：椭圆 mask 只需要**几个 float 参数**（中心、长短轴、旋转角），
从检测结果算出来，然后作为 uniform 传给 shader，在片元里解析判断即可 ——
**完全不需要把 mask 当纹理上传，更不需要下载整帧**。

**我们能照搬的架构**：

```
每 4~10 帧：
    ↓ 只下载 256×256 的缩小帧（数据量 1/36，约 0.2MB）
  CPU 检测 → 人脸框/关键点
    ↓ 算成 4~6 个 float（椭圆参数）
  uniform 上传（几十字节）

每帧：
  GPU: 5 个 pass（磨皮 + 美白），mask 用 uniform 参数在 shader 里算
  零 CPU 往返
```

代价：mask 从「像素级肤色分割」退化成「椭圆近似」，边界不如现在精确
（我们当前的掩码 IoU 0.844）。但 wtnl-zhi 明确选了这条路，并说这就是 v1 的取舍。

> ⚠️ **已实测：纯椭圆在我们的素材上画质不达标，暂不采用。**
> 系数照抄 `radius_x = 脸宽×0.57 / radius_y = 脸高×0.55`，与现有掩码对拍：
> `face_src` IoU **0.562**、精确率 **0.568**（覆盖 11.91% vs 现有 6.91%）——
> 椭圆比真皮肤胖近一倍，多出来的全是眼睛、眉毛、头发。
> crop_a / crop_c 更差（IoU 0.06~0.08）。
> 详见 `C2_边缘门控.md` §4。**只在决定整体改走 GPU 时才值得重估**（那时换来的是
> 去掉全帧往返，性质不同）。

### 2.3 质量分档（思路，值得抄）

wtnl-zhi 给了三档现成数字：

| 档位 | 检测输入 | 检测频率 |
|---|---|---|
| 自动 | 256 px | 10 fps |
| 兼容（低配） | 192 px | 6 fps |
| 高质量 | 384 px | 15 fps |

**注意**：它们能降检测输入，是因为 MediaPipe 模型原生支持动态尺寸。
我们的 YuNet 固定 640（见 `C1_CPU性能优化.md` 第 3 节），**只能降频率，不能降尺寸**。
这一条差异要记住，别照抄了尺寸参数去踩我们踩过的坑。

## 3. 一个被低估的事实

`C1_CPU性能优化.md` 把磨皮压到了 1080p 4.88 ms，但那只算了**引擎层**。
插件层每帧还有一笔没测的开销：

| 动作 | 数据量 | 状态 |
|---|---|---|
| `gs_stagesurface_map` 下载 1080p RGBA | 8 MB | **未测** |
| `gs_texture_set_image` 上传 | 8 MB | **未测** |

D3D11 的 staging map 是**同步**的（要等 GPU 把这一帧画完），1080p 通常 3~6 ms。
如果实测确认这个量级，那么：

- CPU 路线总开销 ≈ 3(下载) + 4.88(磨皮) + 1(上传) ≈ **9 ms**
- GPU 路线（wuxiwuhen 方案）≈ **0.5 ms**，差 **18 倍**

**所以 GPU 化真正的收益不是「省 4.88ms 磨皮」，而是「砍掉每帧 16MB 的往返」。**
这一点在上一轮评估 GPU 时被我漏掉了 —— 当时只比较了磨皮核的耗时。

> 这不代表立刻要改走 GPU。按 C1 的结论，1080p 7.25ms 对 33ms 预算仍有 4.5 倍余量。
> 但如果接下来要加美白、红润、细节回填、锐化（C1 之后的功能项），CPU 成本会翻倍到 12~15ms，
> 而**每加一项，GPU 方案的相对优势就更大**——因为它们全在同一个 pass 里做。

## 5. 建议顺序

| 优先级 | 做什么 | 依据 | 代价 |
|---|---|---|---|
| **P1** | **实测 staging 往返开销** | 决定后面所有路线；只需在 `video_render` 里加两行计时 | 半小时 |
| **P2** | 用频率分离重写保边核（CPU 版先做） | MIT 算法，画质可对拍；比双边便宜且参数直观 | 1~2 天 |
| **P3** | 检测改异步（双 staging + 只保留最新帧） | 去掉「含检测帧 14.34ms」这个尖峰，均摊 7.25 → 4.88 | 2~3 天 |
| **P4** | 若 P1 确认往返 >5ms，再评估整体 GPU 化 | 5 个 pass 的 effect 已经躺在那了 | 视规模 |

**P1 必须先做**，因为：
- 如果往返只要 1~2 ms，GPU 化的收益就是「省 4.88ms」，不值当；
- 如果往返要 5~8 ms，GPU 化立刻变成「省 12ms」，性质完全不同。

现在不做这个测量就讨论 GPU，等于继续在猜。

## 7. 补：他们怎么解决「磨皮太慢」（2026-10-28 追加）

> 起因：我们的引导滤波在 1080p 要 31.9 ms，顶穿 33 ms 预算。回头查这五个仓库是怎么处理的。

### 7.1 一句话答案

**没有一个仓库在 CPU 上做磨皮，也没有一个仓库拿引导滤波当磨皮低频。**
他们的解法是「不在全分辨率上做这件事」，而不是「把同一件事算得更快」。

### 7.2 lumina 的真实分三级分辨率（源码 `LmPipeline.cpp`）

| 步骤 | 运行分辨率 | 核 | 源码位置 |
|---|---|---|---|
| 背景/低频模糊 `kGaussShader` | **1/4** | 7-tap 线性采样（3 次采样覆盖 7 像素） | `Render` 里 `DrawTo(m_quarterA/B)` |
| 磨皮 `kSkinBlurShader` | **1/2** | 单方向 6-tap，两 pass = 12 次采样 | `DrawTo(m_halfA/B)` |
| 合成 `kComposeShader` | 全分辨率 | 读 `m_halfB` + `m_quarterB` | `uSmoothTex` / `uBlurTex` |
| **掩码细化** `RefineMask`（引导滤波） | **1/4 + RGBA16F** | `maskGuideRadius` 按 720p 折算 | `m_guideA/B/C` |

三个关键点：

1. **磨皮在 1/2 分辨率跑**，核只有 6 tap（我们双边是 5×5 = 25 次采样）。因为除了 2，
   等效半径自动翻倍 —— 它在半分辨率用 12 次采样拿到了我们在全分辨率用 25 次采样
   都没拿到的尺度。
2. **低频在 1/4 分辨率跑**，而且只用来做「局部起伏的参照」和背景虚化，不参与最终锐度。
3. **引导滤波只用来细化掩码**，跑在 1/4 分辨率 + 半浮点。全分辨率磨皮低频这件事它根本没干。

→ 我们把引导滤波放在 1080p 全 ROI 上做磨皮低频，是**用错了地方**。

### 7.3 双边颜色差的定义（这条最值钱，可能是零成本修复）

`kSkinBlurShader` 的注释原文：

> 颜色差先减去大半径模糊的差，只看局部起伏：鼻梁侧面这类平缓的明暗过渡差值近似为 0，
> 照常参与平均；直接用颜色差时，过渡带两侧会被各自抹平，中间挤出一条锯齿状的硬边

```glsl
vec3 diff = (tap - center) - (texture(uLow, uv).rgb - lowCenter);
float weight = spatial * exp(-dot(diff, diff) * uEdge);
```

我们的实现是 `diff = tap - center`（绝对差），所以**大幅度但平缓的过渡带会被判成边缘
而跳过平均** → 两侧各自抹平、中间留一条硬边。这与我们实测到的「小幅度高频 106%」
（磨皮反而造出新纹理）在现象上吻合。

另外它是 **RGBA16F** 做中间缓冲，我们迭代路径的 `lowBuf` 是 **uint8**：每轮迭代量化一次，
4 轮下来必然出色带/平台。这也可能是阶梯效应的另一半来源。

### 7.4 wuxiwuhen 的做法：不做大核，级联小核

`PSBlurH/V` 只有 5 个采样点，但同一份 shader 跑两轮（`BlurH1/V1` + `BlurH2/V2`）：

```
权重 0.40260 / 0.24419 / 0.05449，偏移 0 / 8.8 / 17.6 px
两轮级联 σ≈8.8 → 等效 σ≈12
```

级联的等效半径是叠加而不是平方，所以**两轮小核 = 一个大核，但采样数只翻倍**。
纯高斯没有平台效应（输出是连续的加权平均，不是聚类中心），所以阶梯效应天然不存在。

这在 CPU 上同样成立：可分离 5-tap 两轮 = 20 次乘加/像素，比我们双边的 25 次采样
+ 25 次颜色距离计算便宜得多。

### 7.5 wtnl-zhi / iesv：把检测挪出渲染线程

双 staging surface + 工作线程只保留最新帧，渲染端**不等**推理结果。
我们的检测尖峰 14.6 ms（每 4 帧一次）正是靠这个抹平的。

### 7.6 落地顺序（按收益/代价）

| # | 动作 | 预期 | 代价 | 依据 |
|---|---|---|---|---|
| 1 | 双边颜色差改成「减去大半径差」 | 阶梯效应大幅缓解 | 10 行，需加一个低频参照 | 7.3 的源码注释 |
| 2 | 磨皮降到 1/2 分辨率 | 成本 ÷4 | 中（需上/下采样 + 边界处理） | 7.2 |
| 3 | 迭代缓冲 uint8 → float | 消除色带 | 中（内存 ×4，仅 ROI 内） | 7.3 末段 |
| 4 | 引导滤波降到 1/4 分辨率（若还要） | 31.9 ms → 约 2~8 ms（推算） | 小 | 7.2 |
| 5 | 检测异步化 | 尖峰抹平 | 中 | 7.5 |

**事实 vs 推测**：7.2~7.5 的分辨率、核大小、采样次数、权重与源码位置均来自
`/tmp/lumina/LmPipeline.cpp`（1301 行）与 `09_开源参考/MIT_wuxiwuhen_beauty_filter.effect.txt`
（158 行）的实际内容，可复核。第 1、2、4 项的收益是**推算，未实测** —— 尤其第 2 项
（半分辨率磨皮）需要先确认「半分辨率磨出来的皮肤在半分辨率上被放大回全分辨率后
不会出现软边」，这一点所有仓库都是 GPU 双线性上采样，我们 CPU 侧要另写。

### 7.7 实测修正（2026-10-28 13:00，务必先读这段）

§7.6 表里的**第 1 项和第 3 项已经做过，都没有收益，默认已改回原路线**。
详细数据在 `05_文档/C8_低频层对照_浮点与参照.md`，这里只记结论：

| 项 | 预期 | 实测 |
|---|---|---|
| 1 · 双边颜色差减去大半径差 | 阶梯效应大幅缓解 | **更差**：大幅度保留 99.1%→98.8%，脸颊台阶 59.4%→66.8%，成本 +40% |
| 3 · uint8 → float 缓冲 | 消除色带 | **基本无效**：小幅度 106.0%→105.0%，成本 +8~15% |

两条连带修正：

1. **「106% 小幅度高频」不是量化造成的，也不能拿来当阶梯效应的证据。**
   这个指标的分母在平坦区极小，磨皮后 3~12px 尺度整体变化会被放大成 >100%。
   改用「脸颊台阶像素占比」：原图 73.3% → 磨皮后 59.4%（旧路线），
   现有路线本来就在减少平台边。
2. **第 1 项应该排在第 2 项（半分辨率）之后**，而不是之前。§7.3 的推论在
   r=2 的核上不成立 —— 减掉 17px 尺度的参照后，判据被改写而不是被修正，
   保边强度反而下降。lumina 能用是因为它等效半径约 12px。

所以 §7.6 的落地顺序应改成：**2 → 5 → 4 →（再回来评估 1/3）**。

## 8. 掩码的时序行为：拖影 / 羽化 / 跟踪（2026-10-28 补，对应 3.1.9）

§7 全是**空间**口径（核多大、在哪算）。这一节补**时间**口径 —— 我们被「掩码拖影」卡了
两版（3.1.8 压滞后、3.1.9 软化边界），而三个仓库里只有一个真的处理过这件事。

### 8.1 wtnl-zhi 的 `face_tracker.c`：它为什么要 EMA

源码结构（GPL-2.0，**只读思路，未抄代码**）：

```c
struct beauty_face_observation {   // 观测：归一化到 0..1
    center_x, center_y, radius_x, radius_y,
    left_eye_x/y, right_eye_x/y, mouth_x/y, confidence
};
struct beauty_face_track { active, last_seen_ns, state };   // 轨迹 = 上一次的状态
init(tracker, smoothing, stale_after_ns);   // smoothing clamp 0.01 ~ 1.0
```

- **关联**：按中心距离找最近的已有轨迹，距离 > **0.04**（归一化）就不认，另起一条。
- **平滑**：`state = blend(state, obs, alpha)`，`blend(prev,cur,a) = prev + (cur-prev)*a`，
  对 center/radius/双眼/嘴**逐个分量**做。
- **过期**：`now - last_seen > stale_after_ns` 就丢掉这条轨迹。

**关键在它为什么需要这个**：它的检测是**低频**的（`quality_mode` 决定输入边长，
默认档 256px、**10fps** 量级）。10fps 下如果直接用观测，掩码会以 100ms 的粒度**跳**
（不是"拖"，是"蹦"）。EMA 把跳跃抹成滑动，代价是**又加了滞后** —— 但它的滞后本来就
以 100ms 计，多几十毫秒无所谓。

**我们不能照搬**：我们每帧检测（33ms），滞后是 1 帧。再叠一层 EMA 等于把 33ms 变成
50~70ms —— 拿"抖动"换"拖影"，方向完全反了。**这就是 3.1.9 不做人脸框平滑的理由，
不是没想到。**

### 8.2 wtnl-zhi 的 `beauty.effect`：`mask_feather` 怎么用的

```glsl
float feather = clamp(mask_feather, 0.01, 0.30);          // UI 默认 12%
return valid * (1.0 - smoothstep(1.0 - feather,
                                 1.0 + feather,
                                 distance_from_face));     // 椭圆归一化距离
```

三点值得记：

1. **默认 12%**，可调范围 1%~30% —— 这是唯一一个把"边界软到什么程度"当成**用户参数**
   暴露出来的实现，说明它认为这件事得按脸/按场景调，不是一个能一次定死的常量。
2. **带子骑在边界上**（`1-f` 到 `1+f`），内外各一半。我们做不到向外羽化 —— 我们的掩码是
   `肤色 ∩ 矩形框`，框外没有像素可落。所以同样 12% 在我们这里**等于更厚的一条边**。
3. **掩码随眼轴旋转**（`axis` 由双眼连线给出）。我们没做：我们的框是轴对齐矩形，
   歪头时框会变大（外接矩形），羽化边也跟着变大 —— 观感上比旋转椭圆差一点，但不至于
   出硬边。**留着，等真机有歪头场景再说。**

### 8.3 lumina：不跟滞后较劲，让掩码**形状**贴着脸

`LmFace.cpp` 里没有任何时序代码（没有 `prev`、没有 `lerp`、没有时间戳）。它做的是从
MediaPipe 468 点里取下巴/下颌/颧骨/眉毛等关键点，生成一堆**局部椭圆区域**：

```c
AddRegion(regions, center, axis, majorRadius, ...);   // 椭圆 + 主轴 + 半径
```

于是掩码天然是**贴着脸的软形状**：滞后一帧时，整块软椭圆平移一帧的距离 —— 因为边界本来
就是渐变，平移看不出硬边。**它不需要羽化参数，因为它的掩码从来就没有硬边。**

这条对我们的意义：我们之所以要额外做羽化，是因为我们选了「肤色 ∩ 矩形框」这条路
（为了脖子覆盖，IoU 0.844 是这么来的）。**这不是错，是取舍** —— 用矩形换来了脖子精度，
代价就是要自己补一条羽化边。

### 8.4 落地与不落地

| 开源做法 | 我们 | 理由 |
|---|---|---|
| `mask_feather` 12% + smoothstep | ✅ 3.1.9 采用（比例与曲线对齐） | 见 §8.2 |
| 带子骑在边界上（向外也羽化） | ❌ 做不到 | 我们的框是硬裁剪，框外无像素 |
| 掩码随眼轴旋转 | ⏸ 未做 | 歪头时框变大的问题留着，不致命 |
| 人脸框 EMA（`face_tracker`） | ❌ 明确不做 | 每帧检测 + EMA = 白加滞后，见 §8.1 |
| 运动预测 | ❌ 明确不做 | 急停/反向会过冲 |
| 468 点关键点 → 贴脸椭圆 | ❌ 不换路线 | 换掉「肤色 ∩ 框」会丢掉已标定的脖子覆盖 |

**事实 vs 推测**：§8.1/8.2/8.3 的字段名、clamp 范围、公式、默认值均来自
`wtnl-zhi/obs-beauty-filter` 的 `src/face_tracker.c` / `data/beauty.effect` 与
`dinjufen/lumina-beauty` 的 `src/engine/LmFace.cpp` 实际内容（2026-10-28 抓取），可复核。
「它默认档 10fps / 256px」来自它的 `quality_mode` 设置项，**没有实测它的实际帧率**；
「我们叠 EMA 会把 33ms 变成 50~70ms」是按 α 与帧率的推算，**未实测**。
