## 3.1.38 — 控件尺寸统一 28 逻辑 px（2026-10-30 20:07 构建，被 3.1.39 取代）

**用户原话**：「UI大小都不一样，请统一。」

### 一、真值（用户 175% 截图 ÷1.75 实测）

| 控件 | 逻辑高 | 代码里写的 | 差 |
|---|---|---|---|
| 顶栏下拉 | 28.6 | `setFixedHeight(32)` | −3.4 |
| 标签页药丸 | 31 | `padding:3px 12px` | — |
| 行数值框 | 28.6 | `setFixedSize(74, 32)` | −3.4 |
| 底部按钮 | **51** | `setFixedSize(108, 44)` | **+7** |

### 二、根因：OBS 主题按类各算一套（读 `Yami.obt` 得证）

```css
QComboBox   { height: var(--input_height); }
QSpinBox    { height + max-height: var(--input_height); }
QPushButton { height + max-height + padding(--input_padding)
              + margin-top/bottom: var(--spacing_input); }
```

面板 QSS 只写了 `padding`，`height`/`margin` 全留给主题 → 各算各的。
且 QSS 的 `height` 优先级高于 `setFixedHeight`，同一句 `setFixedSize(74,32)` **只生效一半**。

### 三、修法

- `kCtrlH = 26`（内容盒）→ 总高 **28**；`height`/`min-height`/`max-height`/`margin:0`/`padding:0 8px` 五件套写全。
- 代码里删光高度数字，只留宽度（下拉/数值框 74、按钮 74）。
- 复选框无边框，用 `%2 = kCtrlH+2` 对齐。
- 标签页只能靠 padding 调（`QTabBar::tab` 不认 min-height），实测 27。

### 四、探针从此不再说谎

旧探针自造「假主题」，没有 height/margin，永远测不出真机高度 —— 这才是
3.1.26~3.1.37 每轮「探针 OK、装机不对」的根因。现在按 `Yami.obt` 真实写法模拟，
并新增 `reportCtrlHeights()`（一类里 min==max 才算过）与「探针 QSS 必须与面板逐字相同」的校验。

## 面板 3.1.34 / 滤镜 3.1.34 — 2026-10-30 · 窗口尺寸按截图高宽比定稿（536×611 逻辑）

### 一、3.1.32 错在哪

Qt 的 `resize()` / `setFixedSize()` 收的是**逻辑像素**，物理像素 = 逻辑 × DPI 缩放。
用户量到的 670×750 是 **125% 缩放下的物理像素**：

```
670 物理 ÷ 1.25 = 536 逻辑
750 物理 ÷ 1.25 = 600 逻辑
```

3.1.32 直接写 `resize(670, 750)`，真机会渲染成 **838 × 938 物理**（每个方向都大 25%），
视口高从 434 涨到 584，`spread_page()` 只好把行距撑到 **91** —— 这才是「比草图稀疏」的真因，
不是「窗口太高没地方放」，而是**窗口本身比要求的大了一圈**。

### 二、3.1.33 换算对了，但矮了 11 px

3.1.33 改成 536×600 后，用户又给了一张真机截图（810×992，含 OBS 标题栏 69 px）。

```
670 × (923 / 810) = 763.5 → 764 物理
764 ÷ 1.25        = 611 逻辑
```

3.1.33 的 600 比这个矮 11 px，行距只有 63 逻辑（79 物理），比截图实测的 87 物理略紧。

### 二、为什么「文字被截」—— `setMinimumContentsLength` 的本质是猜

3.0.18 起用的是：

```cpp
cb->setMinimumContentsLength(8);   // 按「8 个字宽」猜
cb->setMinimumWidth(76);           // 再兜一个下限
```

「8 个字宽」是**用字体平均宽度乘出来的估值**，真机字体比探针大得多，4 个汉字
（双边滤波）就已经超过 76 px 的框宽，于是 Qt 按省略规则裁掉尾部、只留箭头。

改成：

```cpp
cb->setSizeAdjustPolicy(QComboBox::AdjustToContents);
```

`sizeHint()` 直接等于**最长选项的实测宽度**（`QFontMetrics::horizontalAdvance`
逐个量再取 max）。布局只会给它更多、不会更少，所以：

- 选项文字**永远完整**；
- 换字体 / 换 DPI / 换语言**自动适配**，不需要再调魔数。

探针加了自检，逐个 combo 比较「控件宽」与「最长选项文字宽 + 24（padding + 箭头区）」：

```
combo "高精度"   宽=522 最长文字=33 OK
combo "双边滤波" 宽=418 最长文字=44 OK
combo "人像磨皮" 宽=418 最长文字=44 OK
```

### 三、`spread_page()` 为什么用 `height()` 而不是 `sizeHint()`（四次修正）

第一版：`sp = (avail - rowsH) / (rows - 1)`，上限 34。结果窗口 750 高、5 行只占 246，
底部空出 340 一大片 —— 与草图密度完全不符。

第二版：上限提到 132，行高仍用 `sizeHint()`。探针立刻报出第一页、高级页各冒 10 px 滚动条：

```
page 0 视口=586 内容=596 滚动余量=10 行距=117   <- 超了
page 4 视口=586 内容=597 滚动余量=11 行距=132   <- 超了
```

根因还是 3.1.31 那个老问题：`sizeHint()` 在 polish 前**每行小约 2 px**，5 行就少 10 px，
行距算大 2.5 px，正好把滚动条顶出来。

第三版：行高改读 `widget()->height()`。这个值**不随 `verticalSpacing` 变化**（spacing 只改
间距、不改行高），所以反复调用稳定，不会像 3.1.31 第一版那样自我放大 —— 五页余量全 0。

但和草图并排一比，节奏不对：除以 `rows-1` 把所有空隙塞进了行间，最后一行直接贴页面底边，
紧挨着下面常驻的 2x2 区块（间隔只有 16 px），而行距是 114 —— 上散下挤。

第四版：除数改成 `rows`（不是 `rows-1`），故意多留一份给底部，剩余空间**全部放底部**
（顶部对齐，与草图一致）：

```
page 0 视口=584 内容=584 滚动余量=0 行距=91  行数=5   <- 行距 91，「红润 -> 磨皮算法」间隔 88
page 1 视口=584 内容=584 滚动余量=0 行距=132 行数=2
page 2 视口=584 内容=584 滚动余量=0 行距=91  行数=5
page 3 视口=584 内容=584 滚动余量=0 行距=132 行数=3
page 4 视口=584 内容=584 滚动余量=0 行距=132 行数=3
```

行数少的页（锐化 2 行、美形 3 行）行距被上限 132 卡住，内容仍在顶部、下方留白。

> 踩坑记录：`spread_page()` 会改 `contentsMargins`，所以**不能读当前 margins 当基准**
> —— 否则每切一次页都把上一次的留白算进 `avail`，越切越偏。基准写死 `(2, 8, 2, 8)`，
> 与 `make_tab()` 里的常量一致。

### 四、`ver_` 的生命周期坑

`ver_` 挪进 `sw_row_` 之后，`clear_form()` 里那句 `purge_layout(sw_row_)` 会把它一起
`deleteLater()` —— 第二次 `build_form` 就再也没版本号了。修法：

```cpp
if (sw_row_ && ver_) sw_row_->removeWidget(ver_);   // 先摘出来
purge_layout(sw_row_);
purge_layout(mode_grid_);
```

`build_form()` 末尾再**无条件**重挂（那个 `if` 找不到滤镜时不执行，`ver_` 也得回到行里，不能飘着）。

## 面板 3.1.31 / 滤镜 3.1.31 — 2026-10-30 · 修「选项被裁、冒滚动条」：高度按真实渲染量

> **动机**（用户装机 3.1.30 后的真机截图 + 一句话）：
> 「UI 把高度拉高，直接把隐藏的选项也全部展示出来。」
>

### 一、先量清楚（截图 PIL 逐行扫描，dpr = 1.75）

| 量到的东西 | 实测（物理 px） | 换算（逻辑 px） |
|---|---|---|
| 窗口 | 756 × 602 | **432 × 344**（我们要的是 400 × 320） |
| 参数行行距 | 67 / 66 / 67 | **38.3**（我们按 32 算的） |
| 数值框绘制高 | 46 | **26.3**（代码写死 22） |
| 按钮绘制高 | 53 | **30.3**（代码 min 24） |
| 滚动条滑块 / 轨道 | 195 / 262 | 内容 352、视口 262 → **差 90 物理 = 51 逻辑** |

### 二、根因

构造期 `inner->sizeHint()` **系统性偏小约 20%**：OBS 主题给 `QPushButton` /
`QSpinBox` / `QComboBox` 写的 `min-height` 要等 polish 之后才生效，所以
`apply_adaptive_size()` 在构造函数里量到的行高是 32，真机渲染出来是 38.3。
5 行少算 51 px ⇒ 第 5 行被裁 + 滚动条。

（顺带解释了窗口为什么是 432×344 而不是 400×320：布局最小宽在 show 时把窗口顶大了。）

### 三、修法：不再猜，只用滚动条当证据

新增 `fit_to_content()`，在 `QEvent::Show` + `singleShot(0)` 里跑（首帧布局完成之后）：

```
真实内容高 = 内容 sizeHint
            若有滚动条，则至少需要「视口高 + verticalScrollBar()->maximum()」
```

`maximum()` 就是「被裁掉多少」，与主题、DPI、字号全部无关 —— 这是唯一不依赖假设的量法。
量到之后按 5:4 反推宽度，`chrome = 窗口高 − 标签栏 − 视口高`（顶栏/开关/档位栏/底栏的固定部分）。
切标签页时只走 `fit_to_content()`，不再调 `apply_adaptive_size()`（两者算 chrome 的方式
不同，各算一遍会让窗口在切页时抖 2 px）。

### 四、自测抓到的一个真 bug（探针立功）

第一版写成 `内容 = 视口 + 滚动条余量`。**没有滚动条时这个式子等于视口高**，于是每量一次
窗口就长一点，无限自我放大：

```
[fit pass 0] 465x372  [pass 1] 473x378  [pass 2] 480x384  [pass 3] 488x390  [pass 4] 495x396
```

改成「sizeHint 为基准、滚动条只当佐证」后 2 轮收敛：

```
[构造期]     400x320  page0 sizeHint=160 viewport=164 scrollMax=0
[模拟真机]   400x320  viewport=138 scrollMax=22  <- 滚动条冒出来了
[fit pass 0] 465x372 ratio=1.250 scrollMax=0 changed=1
[fit pass 1] 465x372 ratio=1.250 scrollMax=0 changed=0   <- 收敛
  page 0..4 视口=190 内容=190 滚动余量=0   （五页全部 0）
```

### 五、探针改造

新增 `emulateInflation()`：探针没有 OBS 那套主题，所以用 **per-widget 样式表**
把按钮撑到 30、数值框/下拉撑到 26（per-widget 优先级最高，不会被 kPanelSheet 压回去），
目的不是复刻外观而是**复刻行高**，用来验证 `fit_to_content` 的收敛性。

## 滤镜 3.1.9 / CoreEngine 0.7.4 — 2026-10-28 · 修「33ms 滞后仍可见的硬边拖影」

> 真机反馈（3.1.8 装机后，16:33 日志）：**拖影还在**；CPU 11%（比预估的 14% 还低）。

**为什么 33ms 还看得见**：滞后本身消不掉了（检测跑在 worker 上，最快也要等它算完），
但 3.1.8 的掩码边界是**人脸框矩形的硬裁**（`buildMaskInto` 里 `x0..x1 / y0..y1` 直接
截断，肤色权重只软化框内、不软化框本身）。头部一动，旧框覆盖的那条带子就被全额美颜，

### 三条路，为什么选羽化

| 方案 | 效果 | 代价 / 风险 | 结论 |
|---|---|---|---|
| **边界羽化**（本版） | 硬切变渐变，滞后仍在但边界不可见 | 框边缘约 10% 的掩码能量被削（见下），观感上等于整体强度略降 | ✅ 采用 |
| 运动预测（按速度把框往前推） | 跟得上，滞后可归零 | 急停/反向时框会**冲过脸**，那是另一种更难看的东西（过冲） | ❌ 不做 |
| 人脸框时序平滑（EMA） | 抖动变小 | **增加滞后** —— 我们正要去掉滞后，方向相反 | ❌ 不做 |

## 滤镜 3.1.8 / CoreEngine 0.7.3 — 2026-10-28 · 修「真机掩码拖在脸后面」

> 真机反馈一句话：「脸部遮罩跟不上」。3.1.7 装机后第一次真机跑（15:42 日志）暴露的。

**诊断**：不是推理慢，是**节流节过头了**。

| 量 | 值 | 来源 |
|---|---|---|
| YuNet 单次推理（640×640 固定输入，2 线程） | **14.1 ms** | 离线 `face_probe` 实测 |
| 掩码提交周期 | `kMaskEvery=4` → **5 帧 = 167 ms** | `beauty_core.cpp` |
| 结果采集延迟 | +1 帧（33 ms） | `collectAsync` 在下一帧开头才收 |

于是滞后是个**锯齿**：刚更新时差 1 帧（33 ms），然后一路漂到 **5 帧（167 ms）** 再跳回来。
更糟的是掩码边界是**人脸框矩形的硬切边**（`buildMaskInto` 里 `x0..x1 / y0..y1` 直接硬裁，
肤色权重只软化框内、不软化框本身），所以滞后表现为一条硬边拖在脸后面 —— 非常显眼。

| # | 改动 | 位置 |
|---|---|---|
| 1 | 异步路径的提交周期独立成 `g_cfg.maskEveryAsync`，默认 **0 = 每帧** | `beauty_core.cpp` |
| 2 | 同步路径常量改名 `kMaskEverySync`，仍是 4（**离线口径不变**） | 同上 |
| 3 | `BEAUTY_MASK_EVERY` 环境变量，可当场对比 0/1/2/4 四档 | 同上 |
| 4 | `beautyCoreMaskCadence()` / `beautyCoreMaskSubmits()` 两个诊断出口 | `beauty_core.{h,cpp}` |
| 5 | 日志 `region=on` → `region=on(every=0)`，能看出节奏改没改上 | `obs-beauty.cpp` |
| 6 | **关掉 ONNX Runtime 的线程自旋**（`session.intra_op.allow_spinning=0`） | `beauty_onnx.cpp` |

**为什么两条路要拆开**：同步时检测压在渲染线程上，每帧跑就是每帧 +14 ms（那是掉帧）；
异步时它跑在 worker 上，每帧跑只多烧一个核的一部分。如果偷懒把 `kMaskEvery` 直接改 0，
`cpu_bench` / `verify_roi` / `detail_test` 会一起变成每帧检测，整套离线基线全部作废。

### 改动 6 是怎么被发现的（这一步比改周期更重要）

改完周期先量了一次 CPU，30fps 节流下进程占用从 0.66 核跳到 **2.02 核**。
但单次推理只要 14.1ms、30fps 下多跑 23 次/秒，怎么算也只该多 0.33 核 —— 差了 4 倍。

查下来是 ORT 的 intra-op 线程池**默认开启忙等**（`session.intra_op.allow_spinning`
默认 1）：两次 `Run()` 之间线程不睡，原地自旋等下一次调用，为的是省掉线程唤醒的
几十微秒。检测每 167ms 一次时自旋几乎碰不到；改成每 33ms 一次，2 个推理线程就几乎
全程在自旋，白烧 1.4 个核。

关掉之后：单次推理 10.5~12.7ms（**没有变慢**，比之前测的 14.1ms 还低 —— 那个数是含
首次预热的单次读数），检出正常。

> **教训**：`SetIntraOpNumThreads` 只管「用几个线程」，不管「线程在两次推理之间干什么」。
> 高频小批量推理的场景必须显式关自旋，否则省下的那点延迟会以整核的代价还回去。

### 验收：提交率是唯一直接证据

| `BEAUTY_MASK_EVERY` | 提交次数 / 帧数 | 次/帧 | 渲染线程每帧 | 进程 CPU |
|---|---|---|---|---|
| 4（3.1.7 的老节奏） | 40 / 200 | **0.20** | 11.86 ms | **1.29 核** |
| 0（新默认） | 200 / 200 | **1.00** | 13.61 ms | **1.70 核** |

`1/(周期+1)` 完全对上。**真实代价 = +0.41 核 ≈ 20 核整机 +2.1 个百分点**，

## 滤镜 3.1.6 / CoreEngine 0.7.2 — 2026-10-28 · 细节层时序 EMA（压掉锐化放大的噪点闪烁）

> 动机：真机 3.1.5 跑通之后，观感上「静止时脸有点抖」。查下来不是磨皮在抖，
> 是**锐化把传感器噪点放大了** —— 静态纹理帧间相关，噪点帧间独立，高通一放大，
> 输出就逐帧跳。这是自研引擎相对 SDK 的最后一个已知画质缺口。

**做法**：照 SDK 3.0.1/3.0.2 已经验证过的路子（`legacy_engine.cpp` 的 `srcT` +
`detailBetaFromVel`），对**算高通用的那张亮度平面**做运动自适应 EMA：

- 静止（帧间差 ≤ 2.5 灰阶）→ β=0.20，白噪声的帧间方差压到 1/3；
- 运动（帧间差 ≥ 8.0）→ β=1，**完全不平滑**；
- 中间线性过渡，避免阈值附近抖动导致「时有时无」的观感。

为什么对**输入亮度**做 EMA 而不是对**输出**做：噪点是通过高通被放大的，输入先平滑，
高通里就没有独立噪声了；静态纹理帧间相关，EMA 稳态收敛到自身，纹理 100% 保留。
反过来对输出做 EMA，会把磨皮结果一起平滑，头一停就出现「由糊转清」的拖影。

| # | 改动 | 位置 |
|---|---|---|
| 1 | `DetailEma` 结构（`lumT`/`beta`/`reset`），`detailRefill` 加默认参数 —— 不传就是原路径 | `beauty_smooth.h` |
| 2 | 在「算盒子之前」插一段全帧亮度 EMA；β=1 时**只推进历史、不写回浮点平面** | `beauty_smooth.cpp` |
| 3 | `updateMotion()`（1/4 分辨率亮度快照，`77/151/28` 整数 luma）+ `emaBeta()`（分段线性） | `beauty_core.cpp` |
| 4 | 4 个环境变量：`BEAUTY_EMA` / `_STILL` / `_FULL` / `_BETA` | `beauty_core.cpp` |
| 5 | 历史断帧复位：`detailEmaGen_ + 1 != frameNo_` 就用当前帧重置 | `beauty_core.cpp` |

**为什么 β=1 时也要走一遍循环**：运动那几帧如果不动历史，等头停下来 β 一降，
就会把几帧前的旧亮度混进来 —— 观感是「头停了画面才滑一下」。历史必须每帧推进。
而这一遍**不写回 `lum`**（保持浮点原值），所以 β=1 的帧输出与「完全不开 EMA」
**逐字节相同** —— 这就把「运动时零拖影」变成了可断言的事实，不是靠眼睛看。

**为什么需要断帧复位**：EMA 的历史必须逐帧连续。中间断一帧（面板全 0 提前返回、
这一帧没检出脸导致 `detailRefill` 早退）之后历史就是陈旧的，再拿它混会把几帧前
那个位置的亮度渗进来。用「帧序号」比较而不是布尔标志，是因为提前返回的路径太多，
逐个去置标志一定会漏。

### 验收（`06_离线验证/diff_ema.py`，1280×720，真机档位）

台架 `ema_probe.exe` 用**同一份** `beauty_core.cpp` 编成，不经过 OBS，输入序列由
确定性 PRNG 生成 —— 所以 EMA=0 与 EMA=1 两次运行看到的输入逐字节相同。

| 档位 | 判据 | 结果 |
|---|---|---|
| 真机档位 11 项 | motion：与 EMA=0 逐帧比 hash | **8/8 帧完全相同** → 零拖影 ✅ |
| 真机档位 11 项 | static：EMA=1 从第 2 帧起 hash 是否恒定 | 恒定 → 历史收敛、无漂移 ✅ |
| 真机档位 11 项 | noise：输出帧间差 | 4.275 → **2.993**（−30.0%）✅ |
| 只留磨皮+两档锐化 | noise | 4.357 → **3.084**（−29.2%）✅ |
| **去掉两档锐化** | noise：与 EMA=0 逐帧比 hash | **8/8 帧逐字节不变** ✅ |

最后一行是关键旁证：**锐化关掉时 EMA 一点都不生效**，说明它只动锐化那一层，
不会污染磨皮 / 美白 / 红润 / 五官五项。

### 那 −30% 到底是谁的功劳（把噪声源拆开）

| 配置 | 输出帧间差 |
|---|---|
| 去掉两档锐化（噪声只来自磨皮/美白/五官） | 3.013 |
| 加上两档锐化，EMA=0 | 4.275（**锐化额外贡献 +1.26**） |
| 加上两档锐化，EMA=1 | 2.993（**锐化额外贡献 ≈ −0.02**） |

也就是说：**锐化给画面带来的那部分闪烁被 100% 消掉了**，剩下的 2.99 是磨皮层
自身的闪烁（磨皮不做时序平滑，这是刻意的 —— 对它做时序平滑就是拖影）。
总量「只降 30%」是因为分母里本来就有一大块与锐化无关的闪烁。

### CPU 代价

隔离锐化层（`BENCH_PROFILE=26,0,0,0,59,76,0,0,0,0,0`），300 帧 ×5 次，min-of-5：

```
EMA=0  min 9.24 ms   median 9.63 ms
EMA=1  min 8.97 ms   median 9.54 ms
```

**差异落在台架噪声里（符号都是负的）** —— EMA 那一遍是纯顺序读写的整数运算，
全帧 921,600 px 按 8 线程切，比它贵的 `boxPlaneH/V` 与软膝逐像素运算早把它盖住了。
结论：额外开销 < 0.5 ms，换算 CPU < 0.6 个百分点，实测不出来。

**指纹**：`obs-beauty.dll` 482,816 B · md5 `e1f0ed0d5a1fc06b29a8ffc07dd0a963` · 3.1.6 / core 0.7.2

以后加参数仍然自动跟随 —— 不破坏原来「面板不硬编码参数表」的设计。

按钮用 `obs_property_button_clicked()` 触发。属性表在 `build_form()` 末尾会
销毁，所以回调里**不能**捕获属性指针 —— 改成点击时按 key 重新取一次属性表，
找到同一个属性再触发。按钮执行完用 `QTimer::singleShot(0, ...)` 重建表单，
避免在点击处理里把自己删掉。

**第三个参数必须是 `obs_obj_get_data(filter_)`，不是 `filter_` 本身。**

滤镜那三个回调第一句都是 `struct beauty_filter *f = (struct beauty_filter *)data;`，
然后拿 `f->context` 当 `obs_source_t*` 用 —— 也就是说回调期望收到的是**滤镜的
私有数据指针**。但 OBS 自己传的不是这个：

- `shared/properties-view/properties-view.cpp` 的 ButtonClicked 分支用的是
  `view->GetObject().Get()`，即 `obs_source_t*`；
- `struct obs_source` 的首成员是 `obs_context_data`（首字段 `char *name`），
  跟 `struct beauty_filter` 的 `context` 不是同一个东西。

所以原生「滤镜属性」页点这三个按钮时，`f->context` 实际读到的是 `name` 指针
→ `obs_source_valid()` 判假 → `obs_source_update()` 直接返回。后果是
**原生页那三个按钮点了没反应，但也不会崩**（日志里从来没出现过它们的痕迹，
正好印证这一点）。这是**滤镜侧既有的契约不符缺陷**，本次只改 UI 模块、
不动 3.0.19，所以留着没修。

面板这边因此必须传 `obs_obj_get_data(filter_)`，才能跟回调的期望对上，
三个按钮才真的能用。如果以后把滤镜回调改成符合 OBS 契约（吃 `obs_source_t*`），
这一行要相应改回 `filter_`。

**排查过程（三次假设，两次被证伪）**：

| 中频带（3~7px）增益不足 | **部分成立但性价比差**，见下表 |

**真正的结构事实**：两条频带的回填上限差一个量级。

```
细频 1~2px：am = 204(锐化80) × softKnee(hf, 12) ≤ 24   →  上限 19 级
中频 3~7px：gm = 672(锐化80) × softKnee(hm, 10级) ≤ 20 →  上限 52 级
```

细频带增益被 `if (amt > 1.0) amt = 1.0;` 硬限在 1.0，所以过去想加锐度只能拧
中频带 —— 而放大 3~7px 就是白边的定义。这解释了为什么每次提锐度都伴随光晕。

**解法**：`kTexModes` 里的 `edge` 项本来就是「按局部结构强度 t 抬细频带」，
但模式 0（人像，默认）一直是 0。它的 t 由 `|h_mid|`（3~7px 幅值）算出，
所以只抬**真实边缘**处的 1~2px 细节；毛孔本身就在 1~2px，进不了 t，脸颊照样
干净 —— 正是对方「只在真边缘有高频」的特征。

| 路线 | 边缘对比 | 平坦高频 | 光晕过冲 | 性价比 |

| `kMidKnee` 10→22 + `kMidGain` 4.20 | +13.3% | +4.2% | +44.8% | 0.30 |

### 为什么这么改（离线 sweep 实测依据）

用 `LEGACY_EXTRA_PARAMS_FILE` 诊断通道在测试 DLL 上扫参数，结论：

| 尝试 | 结果 |
|---|---|
| `heavy_blur` = 0..5 / 0..100 | **完全无效**，所有档指标逐位相同 |
| `clear_smooth` / `fine_smooth` / `balance_smooth` / `hazy_smooth`（0/1 与 50） | **完全无效** |
| `blur_type` 扫全档 | 只有已知 4 档（0 高斯 / 1 双边 / 2 弱磨皮 / 其它），无新增 |
| 加载 `ai_human_processor_pc.bundle` 走 HumanProcessor | 道具确实升级成 `face_beautification_v2`（与第三方日志一致），**但上述 key 依然无效** |
| **`clarity`** | **有效**：脸内效果量 2.744 → 5.072（**+85%**），细节 +3.3%，背景零改动，闪动不变 |
| **`delspot_level`** | **有效**：脸内效果量 +9.4%，但帧间闪动 1.626 → 2.533（**+56%**） |
| `blur_level` 2.0 / 6.0 | 与默认值无差异（blur_level 已由「磨皮」滑块按 0..6 线性下发） |

结论：第三方的磨皮模式**不是**这些 SDK 参数（应为它自己做的后处理），但其「清晰（Clarity）」
就是 SDK 的 `clarity` —— 这正好是用户说的「高低频凸显的立体感」的来源。
