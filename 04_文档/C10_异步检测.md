# C10 · 异步检测（S3）

> 2026-10-28 13:35。对应 `05_文档/D1_我们自己的技术线路.md` 的 **S3**。
> 一句话：**把 YuNet 从渲染线程挪到 worker 线程，最慢帧 22.90 → 18.65 ms，
> 超 60fps 预算的帧从 5/24 降到 1/24。**

## 1. 为什么做

1080p 的均值本来就够（均摊 9.5ms / 33ms 预算），问题在**尾帧**：
检测每 4 帧跑一次，那一帧要多吃 11ms。30fps 还扛得住（22.9ms < 33ms），
但 60fps 预算只有 16.7ms —— 每 4 帧掉 1 帧，用户看到的是规律性顿挫。

## 2. 结构

```
渲染线程                               worker 线程
  ├ 收结果（vector::swap，O(1)）        ├ 等输入槽（condvar）
  ├ 到周期就 memcpy 一帧到输入槽  ────►  ├ 跑 buildMaskInto（检测+掩码+保护）
  └ 结果没到就沿用旧掩码（不等）    ◄────  └ 结果放输出槽
```

关键点：

1. **渲染线程永不 `wait`。** 最坏情况只是「掩码晚一帧到位」，而不是掉帧。
2. **单槽位，不排队。** 检测 15ms、提交周期 133ms（4 帧），一个槽位绰绰有余。
   排队保的是「一帧都不丢」，但掩码只需要最新那份 —— 中间结果没有价值
   （wtnl-zhi 的「只保留最新帧」是同一个判断）。
3. **`buildMaskInto` 只读 `src`、不碰任何成员**，所以整段可以安全地在另一个线程跑，
   磨皮链一个锁都不用加。这是这次改造最关键的设计约束。
4. **没检出脸时不换缓冲。** worker 的 mask 内容此时无意义，换进来会把正在用的
   掩码冲掉，C5 的「丢帧保持」就失效了。

## 3. 两处必须调的参数（不调就是白干）

第一版只把检测挪到线程里，结果**尖峰换了个形状**：非检测帧从 8.4ms 涨到 13.7ms
（worker 和 8 个磨皮线程抢核），还有一个 60.8ms 的离群帧。两处修正：

| 措施 | 作用 |
|---|---|
| worker 线程 `THREAD_PRIORITY_BELOW_NORMAL` | 它晚一两帧出结果没关系，渲染线程晚一帧就掉帧 |
| 异步时磨皮线程数 = 核数−1 | 给 ORT 留一个核；代价是每帧 +1.2ms，换掉 11ms 的尖峰，值 |

## 4. 结果（1080p，24 帧 = 6 个检测周期，计时用**引擎自报的 `ms=`**）

| 模式 | 中位 | 均值 | p95 | **最慢帧** | 超 16.7ms（60fps）的帧数 |
|---|---|---|---|---|---|
| 同步 | 9.50 | 11.50 | 20.73 | **22.90** | 5 / 24 |
| **异步** | 9.72 | 10.39 | **12.89** | **18.65** | **1 / 24** |

逐帧（ms）：

```
同步：8.4 8.3 9.1 22.9 8.4 8.3 10.3 8.1 20.9 9.8 9.7 9.5 8.5 20.7 9.5 9.9 10.2 8.1 20.1 7.9 9.7 9.4 7.7 20.5
异步：9.6 8.5 10.4 11.9 8.2 8.3 10.1 10.4 12.9 8.3 8.1 7.7 9.3 18.6 10.5 9.3 9.7 10.2 12.7 8.8 9.5 14.5 9.1 12.9
```

周期性 20~23ms 的尖峰消失了，剩下 12~13ms 的小鼓包（memcpy 8MB + 抢核），
外加一个 18.6ms 的离群帧。

**掩码结果完全一致**：两种模式最后一帧都是 `mask=154241 px (7.44%) faces=1
roi=12.46% protect=0.73% kps=1`。

## 5. 一个差点测错的坑（方法论）

第一版脚本用进程外的 `perf_counter` 计时，得出「异步反而更差」的错误结论 ——
因为 `BeautyCoreRun` 每次调用都要**读写 8MB raw 文件**，文件 I/O 约 15ms，
把信号完全盖住了。改用引擎自报的 `ms=` 才看到真实差异。

**教训**：这个项目的性能数字只有两个可信口径 —— 引擎自报的 `ms=`，
或者 `bench_core.py` 的口径。用 wall clock 测绝对值没有意义。

## 6. 生命周期与已知问题

- worker 在第一次 `updateMask` 时启动，`release()` 时 `join`；`release()` 由
  `obs_module_unload` 调用，在 DLL 卸载之前，所以不会出现「线程还在跑、DLL 已卸载」。
- **已知**：滤镜实例销毁（`releaseSlot`）不会停 worker，它会在 OBS 整个运行期间
  空转等待（挂在 condvar 上，不占 CPU）。模块卸载时才真正退出。要更严谨可以在
  最后一个实例销毁时停，但 CoreEngine 现在不跟踪实例数，留作后续。
- 离线对拍默认**强制同步**（`core_probe` 会设 `BEAUTY_ASYNC_DETECT=0`）：
  异步下「第 k 帧用哪份掩码」取决于线程调度，逐字节哈希会飘。要测异步就显式传 1
  （`async_detect_test.py` 就是这么做的）。

## 7. 开关

- `BEAUTY_ASYNC_DETECT=0` 关掉异步（回到同步检测，行为与 3.0.x 一致）
- `BEAUTY_MASK_EVERY=N` 改**异步路径**的提交周期（帧，默认 **0 = 每帧**）

**副作用提醒**：异步开启时磨皮线程数自动降为「核数−1」。所以关掉异步之后，
磨皮线程数会回到「核数（上限 8）」。

### 7.1 提交周期：两条路径的节奏是分开的（3.1.8）

3.1.7 及之前两条路共用 `kMaskEvery=4`（提交周期 5 帧 = 167ms）。真机 3.1.7 反馈
「脸部遮罩跟不上」—— 滞后是锯齿：刚更新 1 帧（33ms），漂到 5 帧（167ms）再跳回来。
而实测 YuNet 只要 **14.1ms**，慢的从来不是推理，是节流。

| 路径 | 常量 / 配置 | 周期 | 为什么 |
|---|---|---|---|
| 异步（生产默认） | `g_cfg.maskEveryAsync` = 0 | **每帧**，滞后 1 帧（33ms） | 检测在 worker 上，渲染线程一分钱不多花 |
| 同步（离线台架） | `kMaskEverySync` = 4 | 5 帧 | 检测压在渲染线程上，每帧跑就是每帧 +14ms = 掉帧 |

**这两条必须分开**：把 `kMaskEvery` 直接改成 0 会让 `cpu_bench` / `verify_roi` /
`detail_test` 一起变成每帧检测，整套离线基线作废。

**代价**（台架 `cpu_bench.cpp` §3b，`BENCH_FPS=30` 节流、async=1、200 帧）：

| `BEAUTY_MASK_EVERY` | 提交率 | 渲染线程每帧 | 进程 CPU |
|---|---|---|---|
| 4（3.1.7 老节奏） | 0.20 次/帧 | 11.86 ms | 1.29 核 |
| 0（新默认） | 1.00 次/帧 | 13.61 ms | 1.70 核 |

**真实代价 +0.41 核 ≈ 20 核整机 +2.1 个百分点**，渲染线程 +1.75 ms。

> **必须按真实帧率节流再量**。不节流时台架跑到 80fps、8 个磨皮线程把核占满，
> 争用被放大成「每帧多 1.4ms」，那是台架假象。

### 7.2 ORT 线程自旋：高频检测的隐藏代价

把周期改成每帧之后，第一次量到进程 CPU 从 0.66 核跳到 **2.02 核** —— 比「23 次/秒 ×
14.1ms = 0.33 核」的推算高 4 倍。原因是 ONNX Runtime 的 intra-op 线程池**默认忙等**：

```
session.intra_op.allow_spinning = 1（默认）
```

两次 `Run()` 之间线程不睡，原地自旋等下一次调用，省掉线程唤醒的几十微秒。
检测每 167ms 一次时碰不到；每 33ms 一次时 2 个推理线程几乎全程自旋，白烧 1.4 个核。

`beauty_onnx.cpp` 里已显式关掉（`intra_op` + `inter_op` 两个键，忽略返回值以免
未来 ORT 改名把模型加载搞挂）。关掉后单次推理 10.5~12.7ms，**没有变慢**。

**这条对所有「高频小批量推理」都成立**：`SetIntraOpNumThreads` 只管用几个线程，
不管线程在两次推理之间干什么。

**怎么确认节奏真的生效**：日志里 `region=on(every=0)`。提交率用
`beautyCoreMaskSubmits()` 数，`cpu_bench` 已经打出来了。

**60fps + 1080p 的边界**：推理 15ms、帧预算 16.7ms，worker 会接近饱和，
`submitAsync` 在 worker 忙时自己放弃 → 自我节流成隔帧一次，滞后变 1~2 帧，不会堆积。

### 7.3 掩码边界羽化：滞后消不掉，但可以让它看不见（3.1.9）

**真机结论**：3.1.8 把滞后从 167ms 压到 33ms 之后（16:33 日志，`region=on(every=0)`，
CPU 11%），**拖影还在**。所以问题不在"更新得够不够快" —— 33ms 是 worker 架构的下限，
再快只能上预测。而拖影之所以显眼，是因为**边界是硬的**：

```
buildMaskInto 里：mask[y][x] = skinWeight(...)     // 肤色这层本来就是 0..255 软边
                 但 x/y 被硬裁在 [x0,x1) × [y0,y1)  // 框本身是 0/255 硬切
```

框一旧，旧框覆盖的那条带子就被**全额**美颜，与旁边没被覆盖的像素之间是一条 0→255 的
台阶。台阶跟着脸走 = 拖影。

**做法**：框边缘 F 像素内把权重按 smoothstep 降到 0，F = 12% × 脸宽（上限 64px）。

**三条路的取舍**（这是本节的结论，不是没考虑过别的）：

| 方案 | 为什么不选 |
|---|---|
| 运动预测（按框速度把框往前推） | 急停/反向时框会冲过脸（过冲），比拖影更难看 |
| 人脸框时序平滑（EMA） | 平滑的代价就是**增加滞后**，与本节目的相反。开源 `wtnl-zhi` 用 EMA 是因为它检测只有 10fps，我们每帧检测不需要 |
| 羽化 | ✅ 不改时序、不改 ROI、不引入新状态，只改权重曲线 |

**为什么 12% 和 smoothstep**：对齐 `wtnl-zhi/obs-beauty-filter` 的 `beauty.effect`——
`mask_feather` 默认 **12%**、clamp 0.01~0.30、曲线是 `1 - smoothstep(1-f, 1+f, dist)`。
它那条带子骑在椭圆边界上（内外各一半），我们只能向内羽化（框外是硬裁剪，羽化出去没有
像素可落），所以同样 12% 在我们这里等于更厚的一条边，正好补偿 1~2 帧滞后。

**实现细节（都是踩过的）**：

1. **必须查表**。羽化在 worker 上逐像素跑，1080p 脸框约 40 万像素，每像素一次整数除法
   就是 10ms 量级，能把整个异步优化吃掉。`g_featherRamp[65][65]` 在 `ensureReady` 里
   算一次（17KB，常驻 L1/L2），之后每像素只剩一次乘法寻址。
2. **脖子通道的底边不能羽化**。脖子通道从脸框下沿往下延伸，如果底边也羽化，下巴正下方
   会出现一条**水平接缝**（横线）。所以脸框底边在脖子通道宽度内时跳过下羽化。
3. **表没建好时返回"不羽化"**（256），不要返回 0 —— 全局数组默认全 0，一旦哪条路径
   没走 `ensureReady`，整张掩码会变成全 0（磨皮静默失效），这种失败最难查。
4. **`BEAUTY_MASK_FEATHER=0` 必须逐字节等于 3.1.8**。已验证：三档输出哈希与 3.1.8
   完全相同（`3f41f430…` / `40946fc9…` / `fda807e2…`），A/B 才有意义。

**代价（实测，掩码层面）**：

| 分辨率 | 掩码像素 | 受影响 | 掩码总能量 |
|---|---|---|---|
| 640x394 | 18,162 | 21.4% | -10.2% |
| 720p | 68,492 | 20.7% | -9.9% |
| 1080p | 154,241 | 20.9% | -10.0% |

> **这 -10% 要记住**：羽化不是"只动边界几像素"，四条边各削一条 12% 的带子，所以
> **整体磨皮/美白强度会略降**。真机若觉得"没以前有效果"，先想到这个，别去调核参数。

斜坡宽度实测正好等于 12% 脸宽（720p 脸宽 ≈200px → 24px；1080p ≈300px → 36px），
单调、无台阶 —— 确认是 smoothstep 不是硬切。

**还没做的**：按速度做**不对称**羽化（拖尾那一侧加宽、迎头那一侧不变）。这需要记住
上一帧的框来算速度，比现在多一份状态，且急停时方向会突变；等 12% 的真机结论再定。

### 7.4 掩码↔帧对齐：把滞后从「掩码落后画面」变成「整帧落后一档」（3.1.10）

**3.1.9 的真机结论证伪了 7.3 的前提**：装机 3.1.9（17:01 日志，CPU 仍 11%）用户反馈
**拖影还在、硬边还在** —— 羽化只把边变软，消不掉「掩码比画面旧 1~2 帧」**本身**。
真正的拖影本体是时序脱钩：worker 在帧 k 上算掩码，渲染线程在 k+1~k+2 上用它，
皮肤一动，掩码边界每帧都在脸后扫一条带。而且 12% 羽化实测削掉掩码总能量 10%
（上表），正对应真机反馈的「整体效果弱了较多」—— 我们为一条消不掉的拖影付了一大笔强度。

**修法：数据本来就在**。worker 的输入槽 `async_.frame` 存着**它算掩码用的那帧原始图**；
收结果时（`collectAsync`）worker 必然已经空闲 —— `ready` 只在 `working` 结束时置位，
帧槽此刻没人读也没人写，swap **零拷贝、无竞态**（同一约束下 `submitAsync` 的 memcpy
也在空闲期做，两者不会同时发生）：

```
collectAsync（锁内，且只在 ready==true）:
    if (result.valid && async_.frame.size() == w*h*4)
        heldFrame_.swap(async_.frame);   // 掩码 + 它描述的帧，整体扣下
        maskFresh_ = true;
process()（渲染线程）:
    if (maskFresh_ && haveMask) src = heldFrame_;   // 磨皮直接处理那一帧
    maskFresh_ = false;                              // 新鲜度只对到货那帧有效
```

要点与代价：

| 点 | 说明 |
|---|---|
| 竞态安全 | swap 只在 worker 空闲时发生（.ready 为真 ⟺ worker 已交完活），与 §3 的「working 期间锁外读 frame」约束同源 |
| 代价 | **输出整体落后 1 帧**（30fps = 33ms，摄像头链路里不可见）——换来掩码与画面逐像素同源，脸后的背景不再被扫带 |
| 懒帧策略 | 结果慢一帧就退回「当前帧+旧掩码」旧行为，**不重发已显示的帧** —— 持续停顿比一次性淡边更显眼 |
| 失效模式 | 分辨率变了、`async_.frame.size()` 不符 → 不 swap，对齐**静默失效**（退回旧行为而非出错）；没法换的帧诊断计数会显示 ratio<1 |
| 开关 | `BEAUTY_MASK_ALIGN=0` 回到 3.1.9 行为（A/B）；同步/离线路径 `BeautyCoreRun` 的 `maskFresh_` 恒 false，完全不受影响 |
| 可观测 | 180 帧性能日志（`BEAUTY_PROFILE=1`）追加「对齐 used/total（%）」，30fps 下应 ≈100%；<100% = worker 追不上，拖影按比例回来 |

**羽化退到 8%**：对齐生效后边界不再每帧移动，羽化只需软化矩形裁剪的硬角，
不需要再补偿滞后；且 12% 曾削 10% 能量。脖子通道羽化改为按**脖子自身宽度**
（`0.08 × 半宽×2`）—— 旧值等价于脖子半宽 27%，是「效果弱」的又一个主力。
实测掩码能量损失从 **-10% 收到 -6.3%**（受影响像素 21% → 13.6~14.3%）。

> **判定树（装机后若还拖影）**：ratio ≈100% 仍拖影 → 拖影另有来源，抓真机帧定位
> （`grab_obs.py`），别再调羽化；ratio <100% → worker 追不上，调 worker 线程优先级。

## 8. 事实 vs 推测

**事实**：§4 的表格与逐帧数据来自 `async_detect_test.py` 本机实测；
两种模式掩码统计完全一致；`obs-beauty.dll` 编译通过。

**推测**：「60fps 下不再规律性掉帧」是推论 —— 我们只测了引擎内部耗时，
真实 OBS 录制时渲染线程还背着 `stagesurface` 回传（8MB 下载 + 8MB 上传），
那部分开销没算进来，所以真机是否稳过 16.7ms **还没验证**。
