# D1 · 我们自己的技术线路

> 2026-10-28 13:05。依据：五个开源仓库的源码实读 + 本机 golden 实测数据。
> 结论：**我们不该抄任何一家仓库的架构，只抄它们的三条「局部技巧」；主线是
> 「全分辨率分离 + 分尺度增强 + 异步检测」，GPU 化永远排最后。**

## 1. 为什么不能照抄（四个约束和别人都不一样）

| 约束 | 我们 | lumina | wuxiwuhen | wtnl-zhi / iesv |
|---|---|---|---|---|
| 磨皮跑在哪 | **CPU**（texrender→staging→CPU→upload） | GPU shader 1/2 分辨率 | GPU shader 4 pass | GPU shader |
| 皮肤掩码 | 肤色∩人脸框∩脖子通道，IoU 0.844 | 分割模型 + 引导滤波细化 | shader 内 YCbCr | 椭圆（实测 IoU 0.562，不达标） |
| 人脸检测 | YuNet，**ONNX 写死 640** | 自有模型 | 完全不检测 | MediaPipe，原生动态尺寸 |
| 必须保住 | **高低频分离**（用户明确要求） | 无此约束 | 无门控 | 无门控 |

→ 所以：**lumina 的 GPU 架构不能照搬**（我们 CPU 已经达标），它的椭圆 mask 路线
**实测不达标**（IoU 0.562、精确率 0.568，会磨到眼睛和眉毛），wtnl-zhi 的尺寸降档
**我们做不到**（YuNet 固定 640）。

## 2. 抄什么 / 不抄什么

| 来源 | 抄 | 不抄 |
|---|---|---|
| **lumina** | ① **分尺度**：低频降分辨率、合成留全分辨率；② **clarity**（大半径局部对比）补立体感 | GPU 渲染管线、引导滤波做磨皮低频（已实测 31.9ms，超预算） |
| **wuxiwuhen** | ③ **级联小核**替代大核（5-tap 跑两轮 ≈ σ12，采样数只翻倍） | 「无检测 + 全帧 YCbCr」（我们已证明会误磨背景） |
| **wtnl-zhi** | ④ **异步检测**（双缓冲 + 只保留最新帧，渲染端不等推理） | 椭圆 mask、尺寸降档 |
| **iesv/BetterFaceOBS** | — | 全部（GPL + Apple Silicon 专用） |
| **已实测无效、不要再试** | — | lumina 的「颜色差减去大半径差」（C8）、uint8→float（C8）、引导滤波做低频（C7）、椭圆 mask（C3）、降检测输入（C1） |

## 3. 我们的线路（一句话）

```
全分辨率分离 → 低频层按尺度分级算 → 全分辨率合成 → 掩码内主动增强 → 检测异步
```

四条不变式（任何一步都不许破）：
1. `高 = 源 − 低`，只压小幅度；`低` 永不被削。
2. 分离与合成留在全分辨率（`高` 必须覆盖到 1px 层）。
3. 掩码外逐字节不动。
4. 每一步可单独回退（环境变量 / 引擎开关）。

## 4. 排序（按收益/代价），以及今天新测出的一条否定结论

先做了一次**零成本标定**（只扫参数，不改代码），确认有没有白捡的收益：

| magLo,magHi | 磨皮量 | 小幅度% | **中幅度%（立体感代理）** | 大幅度% |
|---|---|---|---|---|
| 6,30（现默认） | 1.347 | 106.0 | **96.7** | 99.1 |
| 6,40 | 1.384 | 106.4 | 96.7 | 99.2 |
| 6,50 | 1.403 | 106.6 | 96.8 | 99.2 |
| 10,45 | 1.411 | 106.8 | 96.8 | 99.2 |
| 6,60 | 1.416 | 106.8 | 96.8 | 99.2 |

**结论：门控阈值几乎不影响画质**（中频 96.7→96.8，磨皮量只涨 5.6%）。
也就是说 —— 我们现在**已经保住了 96.8% 的中频**，立体感的差距不是「磨掉了」，
而是「从来没增强过」。**要提分只能主动加，不能靠调参省。**

这个结论直接决定了顺序：

| 顺序 | 动作 | 收益 | 代价 | 依据 |
|---|---|---|---|---|
| **S1** | **clarity 中频回填** —— ✅ **已完成**（`05_文档/C9_清晰clarity.md`） | 中频 98.6 → **104.7**（面板 100），大幅度 100.0 不涨（无光晕），非皮肤 0 像素 | **+1.4 ms @1080p**（实测） | 中频已保住 96.8%，只能靠加 |
| **S2** | 低频层降半分辨率（lumina 的分尺度） | 1080p 纯磨皮帧 6.43 → 约 2.5 ms | 中：改画质（非逐字节等价）、需验边界 | C4 §7.2 已划红线 |
| **S3** | 检测异步 —— ✅ **已完成**（`05_文档/C10_异步检测.md`） | 最慢帧 22.90 → **18.65 ms**；超 60fps 预算的帧 5/24 → **1/24** | 中：worker 线程 + 单槽位掩码交接 | 实测含检测帧 18.63ms > 16.7ms(60fps) |
| 最后 | GPU 化 | 理论最大 | 最大（全部重标定） | 当前 30fps 已达标（9.48ms/33ms） |

## 5. S1 设计（收益最大的一项，可直接开工）

### 5.1 为什么是「大半径」而不是「小半径」

磨皮的核是 r=2 迭代 2 次，动的是 **≤8px** 的尺度；立体感（鼻翼两侧、眼窝、颧骨
下方的明暗过渡）在 **10~30px** 尺度。所以 clarity 的参照必须是 17~25px 窗口，
否则会把痘印重新加回去。

```
L     = 0.299R + 0.587G + 0.114B        // 只在亮度上做，不动色相
Llow  = box(L, radius = 12)              // 25px 窗口
mid   = L - Llow                         // 大尺度明暗层次
k     = gain × (1 - smoothstep(20, 45, |mid|))   // 软膝：硬边处不加，防光晕
out   = dst + mid × k × maskWeight       // 只在肤色掩码内，按亮度比例回加三通道
```

### 5.2 为什么这样不会引入光晕

`|mid|` 在「脸/背景交界」处很大（>45）→ `k≈0` → 不加。这与磨皮的幅度门控是
同一套思路，参数可复用现有 `magLo/magHi` 的标定经验。

### 5.3 验收指标（先写死，再动手）

| 指标 | 现状 | 目标 |
|---|---|---|
| 中幅度（6~30）保留% | 96.8 | **100~106**（有增强但不夸张） |
| 大幅度（>30）保留% | 99.1 | **≥ 99**（不加光晕） |
| 非皮肤区变化 | 0 字节 | **仍然 0 字节** |
| 脸颊台阶% | 59.4 | **不上升**（不制造新边） |
| 1080p 增量 | — | **≤ 1.5 ms** |
| ROI/多线程等价性 | maxdiff=0 | **maxdiff=0**（新代码必须保持） |

### 5.4 风险

- clarity 是「增强」，天然主观；指标只能保证「有增强、不炸边」，好不好看要真机看。
- 增益过大会出现「HDR 味」的塑料感 → 默认值保守（gain 0.25），面板留 0~100 滑块。
- 只在单张图上标定过，**素材到位前不要精调**（同 C4 的教训）。

## 6. 不做清单

1. **不上 GPU**：30fps 已达标（9.48ms/33ms），且这是代价最大的一项。
2. **不用椭圆 mask**：实测 IoU 0.562，会磨五官。
3. **不用引导滤波做低频**：实测 31.9ms @1080p。
4. **不搬 lumina 的 diff 参照 / float 缓冲**：C8 实测无效。
5. **不复制 GPL 仓库代码**（wtnl-zhi / iesv / BetterFaceOBS）：只读思路。

## 7. 事实 vs 推测

**事实**：§4 标定表是本机实测（`low_path_test.py` 同款调用，`BeautyCoreSetFreq` 扫参）；
性能数字来自 `goldens/masks/bench_tone.md`（1080p 纯磨皮 6.43ms / 含检测 18.63ms / 均摊 9.48ms）；
「中频保 96.8%」是 gauss σ=12 分带的实测值；box 约 1.3ms 是由 C7 引导滤波 24 趟 31.9ms 反推。

**推测**：「clarity 能把立体感从 8/10 拉到 9~10」是判断，**没有客观指标能证明**，
只有「中频能量上升」这个代理指标；「半分辨率能降到 2.5ms」是按面积 1/4 推算，未实测。

## 8. 附：GPU 化到底能不能用核显 / AMD（2026-10-28 13:10 补，已核源码）

> 用户提问：「GPU 化存疑，CPU 的核显能使用吗？AMD 的显卡可以使用吗？」

### 8.1 能用。结论有源码依据，不是猜的

GPU 化不是「我们直接调 D3D11/CUDA」，而是**写一份 `.effect` 交给 OBS 的图形抽象层**。
所以能不能跑，取决于 OBS 自己的最低要求，而不是我们的代码：

| 事实 | 出处（本机 `04_依赖与SDK/obs-studio-32.1.1`） |
|---|---|
| OBS 请求的特性等级是 **11_0 → 10_1 → 10_0**，最低接受 10_0 | `libobs-d3d11/d3d11-subsystem.cpp:278-281` |
| 着色器编译目标是 **`vs_4_0` / `ps_4_0`**（不是 5.0） | `libobs-d3d11/d3d11-shader.cpp:65,100` |
| 运行时能读设备名与后端类型 | `libobs/graphics/graphics.h:501-510`（`GS_DEVICE_OPENGL/DIRECT3D_11/METAL`） |

推论：**任何能正常跑 OBS 32 的显卡，都能跑我们的着色器。**
Intel 核显（HD 4000 及以上）、AMD（GCN 及以上）、NVIDIA 全部覆盖 —— 因为它们全都支持
D3D11 特性等级 10_0 与 Shader Model 4.0。

### 8.2 但「能用」≠「值得」，三个真实约束

1. **我们选不了显卡。** `gs_*` 跟着 OBS 的渲染设备走，插件只能读
   `gs_get_device_name()`，不能强制。笔记本双显卡时跑在核显还是独显由系统/OBS 决定。
2. **核显上 GPU 化的收益本来就小。** 我们现在每帧要 download 8 MB + upload 8 MB（1080p）。
   核显与 CPU 共享内存，这笔拷贝本来就不走 PCIe；独显才是真贵。
   也就是说：**想靠「去掉往返」拿最大收益的那批机器（独显台式），恰恰是我们 CPU 路线已经够用的机器。**
3. **检测跟不上 GPU。** CUDA 只 NVIDIA、ROCm 只 Linux、DirectML 跨厂商但微软已转
   sustained engineering。所以检测必须留 CPU → 那一帧仍要 download，
   只是从「每帧 1920×1080」降到「每 4 帧 640×640」。

### 8.3 着色器侧的两个硬限制（已核实）

- 编译目标是 **ps_4_0**，不能用 SM5 才有的特性（compute、可读写纹理等）。
- **OBS 自带的所有 `.effect` 里没有任何 `for (` 循环**（全仓 grep 结果为空），
  配合 wuxiwuhen 作者在文件头的注释（`smoothstep` / `lerp` 也不在解析器内置表里，
  要手写展开）→ 我们的 25 抽头双边必须**完全展开写死**，不能写循环。

### 8.4 所以排最后的判断不变，但理由更硬了

| 项 | 现状 |
|---|---|
| CPU 路线 1080p 30fps 均摊 | **9.48 ms / 33 ms 预算**（bench_tone.md） |
| 核显机器上 GPU 化能省下的 | 比独显小（共享内存，往返本来就便宜） |
| GPU 化要付的代价 | 全部标定重做 + 着色器不能调试 + 只覆盖 D3D11/Metal/GL 三套后端 |

**结论：不做。** 若将来某天真要做（例如要上 4K），前置条件是：
① 用 `gs_get_device_type()` 判后端、② 着色器全展开不用循环、③ 保留 CPU 兜底并在
着色器编译失败时自动回退、④ 把 `gs_get_device_name()` 打进日志方便排障。
