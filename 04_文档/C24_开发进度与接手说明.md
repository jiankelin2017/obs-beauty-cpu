## 1. 边界（先看这条，别按旧目标干活）

用户 2026-10-29 明确表态：**画质优先，先和 SDK 对齐，性能之后再说。**
所以本轮所有工作的验收线是**像素级画质指标**，不是毫秒数。性能只在「不退化」这个意义上被记录。

磨皮的技术路线也已明确：**照抄，不拟合**。详见 `C23 §8` 的反拟合纪律，摘要：

1. 每个常数必须带证据标签：`【源码】` / `【实测】` / `【推断】` / `【拟合】`。
2. 拟合出来的参数不许冒充真值，注释里必须出现「拟合」二字。
3. 不许为了让某个金标对上而加归一化/缩放项（`scale = fw/532` 就是这类东西）。
4. **不许按金标 RMSE 扫参。** 要对齐的是**传递函数**（光栅表）和**改动量**，不是像素残差。

## 2. 本轮（2026-10-29）做了什么

### 2.1 上午：性能排查收口

真机 720p、blur=100、25 tap 路径：引擎 25.6~28.5 ms/帧，丢帧 0.4%，FPS 稳定 30，CPU 7.8%。

| 结论 | 证据 |
|---|---|
| **性能不是瓶颈** | 30fps 预算 33 ms，实测 26~28 ms，丢帧率 0.4% |
| 检测只占 **~2.4 ms（9%）** | `BEAUTY_MASK_EVERY=2`（检测降到 1/3 频次）只省 1.58 ms → `2/3·D=1.58` |
| 切 surface3 **不提速** | 同帧同参 21 帧中位数：legacy 17.22 vs surface3 16.96 ms |
| blur=0 时引擎整体短路 | 0.27 ms，`对齐 0/0`，检测完全不跑 |
| 固定开销 ~1.35 ms | 下载 0.9 + 上传 0.45，blur=0 时仍在 |

> ⚠️ 本轮**推翻了两个此前写进文档的结论**：
> ①「检测 ≈10–15 ms，是最大单项」——错，实测只有 2.4 ms。错因是把离线 DLL 的绝对毫秒数
> 当成了真机数，而离线 `BeautyCoreRun` **不包含**真机的异步掩码机制、掩码混合、保护、合成。
> ②「切 surface3 能降到 13–15 ms」——错，`C15 §4.2` 那个 2.1× 是 `r=2 it=2` 时代的，
> 当前默认 `s3R1=s3R2=14`，核大 7 倍，速度优势被吃光。

### 2.2 下午：转向画质，建了真机对拍台

此前所有画质验收都用 `goldens/src/face_src.raw`（640×394 合成图）。真脸有噪点、
光照不均、眼镜反光，统计特性和合成图完全不同。本轮第一次把**真机摄像头帧**接进评估。

新建 `06_离线验证/real_frame_eval.py`：

```
真机帧 PNG → nama_golden.dll 离线跑 SDK（blur=100, bt=1）→ 金标 + 肤色掩码
           → beauty_core_test.dll 跑自研（同参数同输入）
           → 像素 RMSE / 改动量 / 空间相关 / 残差热图 / 梯度分带
```

**注意**：输入帧是 OBS 画布分辨率 1920×1080，而摄像头实际是 1280×720 被放大 1.5×。
核是 UV 固定的，两边同图对拍仍自洽，但绝对 RMSE 会因放大插值削高频而偏低。

### 2.3 发现链：25 tap 被证伪 → 双尺度带通

这是本轮最重要的部分，四步递进，每步都有实测数据（详见 `C23 §10 / §11 / §12`）：

| 步 | 发现 | 证据 |
|---|---|---|
| 1 | 25 tap 比盒式好，但仍差一倍 | 真机帧 RMSE 2.884 vs 盒式 6.000，验收线 2.0 |
| 2 | **残差 58% 集中在边缘** | 强边（梯度≥15）RMSE 6.003，平坦区 1.849（已达标） |
| 3 | **不是强度问题、也不是门控问题** | 只缩强度：最好 2.495；只按梯度门控：最好 2.437。地板在 2.44 |
| 4 | **是核的频谱形状问题** | 25 tap 径向频响是**双凹陷**（8–13 与 32–60，中间反弹），SDK 是单凹陷（13–20） |

第 4 步之后又做了两件事，才定位到根因：

- **线性模型拟合**：双高斯（σ₁=2.25 / σ₂=7.25）能把谱形状压到 MAE 0.0194，
  但作用到图上改动量只有 0.915（SDK 2.704）→ **SDK 是非线性/边缘自适应的，LTI 结构上不够**。
- **光栅法测振幅依赖**（`real_grating.py`）：同一张图跑两次，一次原样、一次在绿通道加余弦光栅，
  相减把底图纹理完全抵消，投影到 cos/sin 基得复数增益。结果是 SDK 在 P=8 处
  A=2→A=16 增益 0.289→0.579（**翻倍**，强纹理自动放过），我们是 0.396→0.415（1.05 倍）。

**根因**：`even = C − B1 + B2` 是一个带通，去掉的频段由 **B1 与 B2 的空间尺度差**决定。
25 tap 的 B1/B2 用**同一个核**、只有 `yFactor` 不同（110 vs 55）→ 尺度差为 0 →
带通中心只能靠值域门控挪，落在 12 px 而不是 SDK 的 24 px。

### 2.4 落地结果

真机帧（1920×1080，SDK 金标，肤色掩码内缩 6px）：

| 配置 | RMSE | 改动量 | 空间相关 | 720p 离线 ms |
|---|---|---|---|---|
| legacy 双边 | 3.269 | 1.444 | 0.470 | — |
| surface3 盒式 | 6.000 | 3.977 | 0.629 | — |
| surface3 + 25 tap | 2.884 | 3.008 | 0.721 | 17.82 |
| **surface3 + band（新）** | **1.636** | **2.740** | **0.881** | **10.33** |
| SDK 基准 | — | **2.704** | — | — |

残差结构的变化比 RMSE 更有说服力：边缘像素占皮肤 22%，原来扛 58% 的残差平方，
现在只扛 25%。「把眼镜框/眉毛/下颌描出来」的问题解决了。

## 3. 必须知道的技术结论

### 3.1 站得住的

| 结论 | 数字 | 出处 |
|---|---|---|
| 新核：B1 窄、B2 宽，差 1.8 倍 | B1 = 3×盒式宽 5（半分辨率），B2 = 3×盒式宽 9 | `C23 §12.1` |
| 振幅门控是**与频率无关的标量** | A=2→A=16 各周期改动量都缩到 0.58 倍 | `C23 §12.2` |
| 门控形状 `w = 1/(1+(a/T)²)`，T=14 | 按「改动量=2.704」定，不是按 RMSE | `C23 §12.2` |
| 振幅代理必须用 `\|C−B2\|` | `\|B2−B1\|` 在高频处两者都≈0，门控失效（1.0x） | `C23 §12.3` |
| 3 次盒式 ≈ 高斯 | RMSE 1.353（高斯）vs 1.336（3 次盒式） | `C23 §12.1` |
| 半分辨率几乎无损 | RMSE 1.336（全）vs 1.362（半） | `C23 §12.1` |
| 磨皮实际作用在**轮廓细网**上 | `act=\|out100−out0\|>0` 在 1080p 是 92,405 px，开运算后 78,445，内缩 10px 只剩 4,460 | `C23 §9.3` |
| SDK 在 blur≥100 完全饱和 | 101/105/110/120 与 100 逐字节相同 | `C23 §10.5` |

## 4. 代码地图

源码在 `00_源码/`。磨皮相关的三个入口：

| 文件 | 内容 |
|---|---|
| `beauty_smooth.h` | `Surface3Params`（盒式三层）、`Surface25Params`（25 tap）、**`BandParams`（新，双尺度带通）** |
| `beauty_smooth.cpp:675` | `surface3Rgb()` —— 盒式三层（半径随档位 + `fw/532` 脸宽归一化，**拟合痕迹**） |
| `beauty_smooth.cpp:860` | `surface3Rgb25()` —— 25 tap 表面模糊（**已被证伪，保留做 A/B**） |
| `beauty_smooth.cpp:1014` | `bandBoxW()` / `bandBoxH()` / `bandBoxV()` / `bandBoxN()` —— 多平面盒式，一次并行区域处理 3 个通道 |
| `beauty_smooth.cpp:1104` | **`surface3RgbBand()` —— 新核，当前最优** |
| `beauty_core.cpp:1134` | 调用分支：`if (g_cfg.s3Band) … else if (g_cfg.s3Tap25) … else 盒式` |
| `beauty_core.cpp:753` | 引擎版本号（现 `1.0.0`） |

`surface3RgbBand()` 的内部顺序（改之前务必看懂）：

```
1. 半分辨率 2×2 盒式下采样 → sr/sg/sb（浮点平面）
2. B1 = 3 次盒式（宽 5），3 通道一起算
3. B2 = 3 次盒式（宽 9），3 通道一起算
4. amp = |sg − b2g|，再做 3 次盒式（宽 5）平滑
5. 全分辨率合成：v1/v2/amp 双线性上采样 → ①②③ 混合 → I → eye
```

第 5 步的合成段与 `surface3Rgb25()` **逐行同口径**，只多了一行 ③ 振幅门控。
这样两条路径可以直接 A/B，不会因为合成公式不同而混淆结论。

## 7. 雷区（都是真踩过的）

1. **`BEAUTY_PROFILE` 在创建滤镜时读一次**，中途设无效。必须用启动脚本带环境变量开 OBS。
2. **改 `beauty_core.cpp` 后必须重建两个 DLL**，否则 `verify_roi` / 离线对拍测的还是旧核。
3. **离线 DLL 与真机不等价**。`BeautyCoreRun` 没有真机的异步掩码、掩码混合、保护、合成。
   离线绝对毫秒数**不能**移植到真机，尤其当检测节奏不同时。
4. **`smoothModel` 默认 0（legacy）**。面板的「磨皮算法」下拉是 `blur_type`，跟 `smoothModel`
   是**两个不同的开关**，别混。
5. **md5 不可复现**。MSVC 在 PE 头嵌构建时间戳，同一份源码连编两次 md5 不同。
   md5 只能标识「某一次构建的产物」。要可复现得给 `cl` 加 `/Brepro`（**尚未加**）。
6. **`cmd.exe` 不能从 PowerShell 工具调**，用 Bash 的 `cmd //c xxx.bat`。
   `pause` 在非交互管道里会挂死，要喂 stdin：`printf '\n' | cmd //c xxx.bat`。
7. **构建输出是 GBK**，直接 grep 中文会乱。用 `tr -d '\000' | iconv -f GBK -t UTF-8`。
8. **评估函数的 bug 会让人朝错误方向优化**。本轮 `proto_two_scale.py` 的 `metrics()`
   一度把 RMSE 算成「自己改动量的 RMS」，导致所有结论反转（以为 3.1，实际 1.65）。
   改评估代码后**先拿一个已知答案自检**。
9. **SDK 的 stderr 极吵**（fuai/TFLite/FaceUnity-Auth）。跑 `real_grating.py` 要过滤，
   否则输出被淹没。
10. **摄像头是 1280×720，OBS 画布 1920×1080**。截图拿到的是画布分辨率，即 1.5× 放大。
