# C1 · CPU 性能优化（不上 GPU 的路线）

> 2026-10-28 · 结论已实测，可复现

## 0. 结论

**1080p 从 117.75 ms 降到 7.25 ms（16.2 倍），画质逐字节零变化，没有引入任何 GPU 依赖。**

这推翻了此前「CPU 到不了实时、必须 GPU 化」的判断。那条判断的前提是「现实现已优化过」，
实际不成立 —— 优化前是**单线程 + 全帧**。

| 分辨率 | 优化前（30fps 均摊） | 优化后 | 加速 | 33ms 预算余量 |
|---|---|---|---|---|
| 640×394 | 18.45 ms | **2.95 ms** | 6.3× | 11× |
| 720p | 52.2 ms | **4.64 ms** | 11.2× | 7× |
| 1080p | 117.75 ms | **7.11 ms** | 16.6× | 4.6× |

纯磨皮帧（不含人脸检测）的加速更明显：

| 分辨率 | 优化前 | 优化后 | 加速 |
|---|---|---|---|
| 640×394 | 14.68 ms | 1.05 ms | 14.0× |
| 720p | 52.20 ms | 2.51 ms | 20.8× |
| 1080p | 117.75 ms | 4.88 ms | 24.1× |

## 1. 优化前先纠正一个数据

此前的文档写「1080p 约 120 ms」，标注为**按像素线性外推、未实测**。
本轮实测 **117.75 ms** —— 外推是准的，但性质从「推测」升级为「实测」。

## 2. 四项优化，按收益排序

### 2.1 ROI 裁剪（最大项，约 10 倍）

**问题**：磨皮在全帧上跑（1080p = 207 万像素），而掩码只覆盖 6.91%
（`mask=17413 px`）。剩下 93% 的像素算完之后，在 `blendWithMask` 里被直接丢弃 ——
`blendWithMask` 在 `mask[i]==0` 时逐字节还原原图，**根本不读磨皮结果**。

**做法**：新增 `bilateralRgbaRoi()`，只在掩码包围盒（外扩 `radius+1`）内计算。

**为什么画质零损失**：双边滤波是逐像素独立计算，每个输出像素只依赖原图 `src`
的邻域。裁剪 ROI 不改变任何像素的输入，只是不再计算那些随后会被丢弃的像素。
唯一要求是 ROI 必须覆盖所有 `mask!=0` 的像素并留够 `radius` 边距（否则边界像素
的邻域会被切断）。

实测 ROI 面积：`roi=12.64%`（掩码 6.91% + 包围盒内的非皮肤区域 + 边距）。

### 2.2 多线程按行切分（约 5 倍）

行与行之间没有数据依赖。按 ROI 的行范围切成 N 块，每块一个 `std::thread`。

线程数策略：默认取 `hardware_concurrency()`，上限 8（超线程对内存密集的滤波帮助很小），
且每线程至少 16 行、总行数少于 32 时退回单线程（线程创建/汇合约 20~50 µs，
行数太少时纯亏）。

### 2.3 去掉全分辨率 RGB 中间缓冲（1080p 约 3 ms）

原流程：`src(RGBA)` → `rgb_(w*h*3)` → letterbox → 640×640。

**中间那步是纯浪费**：检测只吃 640×640，却先把整帧转成一份 RGB。
1080p 下这是 600 万字节的写入。

改为 `letterboxRgb(..., stride)` 直接从 RGBA 源取样（`stride=4`），一次遍历出结果。

### 2.4 合并掩码统计遍历（1080p 约 2 ms）

原先掩码生成完之后还要扫两遍全帧：一遍数像素（`maskPixels_`），一遍求包围盒
（`maskBounds`）。1080p 下各是 200 万次内存访问，**全部只为了打诊断日志**。

改为在写掩码时就顺带统计。用「只有从 0 变 255 才计数」避免脸框与脖子通道重叠处重复计。
用 `any` 标志只在真的落了像素的行上扩 bbox，否则脸框下沿没肤色的几行会把包围盒拽满。

## 3. 一个走不通的方案（已排除，别重试）

**降检测输入分辨率到 320，省 4 倍算力 —— 在我们的模型上做不到。**

事实链：
1. 我们用的 `yunet_2023mar.onnx` **把输入声明成固定 640×640**。
2. ONNX Runtime 严格按声明校验，喂 320 直接报
   `Got invalid dimensions for input: index 2 Got: 320 Expected: 640`。
3. **OpenCV 却能跑 320**（实测 1.86 ms vs 640 的 9.34 ms，score 0.913 正常）。
   原因是 cv2.dnn 的引擎不认模型声明的固定维度，会自己重做 shape 推断 ——
   那是 OpenCV 的行为，不是模型的能力。**照 OpenCV 的表现去推断「模型支持动态输入」会踩坑。**
4. 想真正降分辨率只有两条路：换原生动态导出的模型，或改 ONNX 的 `dim_param` 再重做
   shape 推断（后者风险高 —— 网络内部的 Reshape 依赖具体尺寸）。

**替代方案**：检测提速改走「推理多线程」（`kInferThreads = 2`，约 15 ms → 9 ms），
而不是降分辨率。给 2 个线程是因为 OBS 的编码线程通常要占 4~6 核，全占了会掉帧。

`FaceDetector::setInputSize()` 保留但仍对固定 shape 的模型是**空操作**，
`inputSizeFixed()` 可查当前模型是否锁死尺寸。

## 4. 为什么最终没上 GPU

用户 2026-10-28 的决定：**走 C 路线（只优化 CPU），不上 GPU。**

技术依据（上一轮评估）：
- 磨皮 GPU 化走 OBS `gs_effect`，对 AMD/Intel 天然友好（D3D11 跨厂商），**这一环不是问题**；
- 真正的 AMD 陷阱在**神经网络推理**那一环（CUDA 独占 / DirectML 已转入维护模式）；
- 而 CPU 优化后 1080p 只要 7.25 ms，GPU 方案（预估 3~6 ms）换来的差距在 33 ms 预算里没有意义，
  却要付出「画质全部重新标定 + shader 不可调试 + 双后端验证」的代价。

## 5. 验证方法

```bash
cd 06_离线验证

# 1) 像素级等价性：ROI/多线程必须一字节都不改
python verify_roi.py
#   期望：三档分辨率全 PASS，maxdiff=0

# 2) 性能基线
python bench_core.py <tag>
#   输出 bench_<tag>.md / .json 到 goldens/masks/

# 3) 画质回归（对拍 SDK 曲线）
python core_vs_sdk.py
```

`verify_roi.py` 的判定逻辑：用同一份二进制，分别跑
`(ROI关, 1线程)` / `(ROI开, 1线程)` / `(ROI开, 自动线程)`，三者输出必须逐字节相同。
这是「优化没拿画质换性能」的硬证明。

实测输出哈希（优化前后一致）：

| 分辨率 | SHA256 前 16 位 |
|---|---|
| 640×394 | `cec2fd1f3abb4063` |
| 720p | `0bdf5f362c73186c` |
| 1080p | `e5c25551198d86b6` |

## 6. 代价与边界

| 项 | 说明 |
|---|---|
| 内存 | 多线程共享只读的 `src` 与 LUT，无额外拷贝；每帧线程创建开销约 0.1~0.3 ms（已计入上面的数字） |
| 可调试性 | ROI 让「为什么这块没磨」多了一层原因（不在包围盒内）。诊断字段 `roi=12.64%` 已加到日志里 |
| 线程竞争 | 4 个线程磨皮 + 2 个线程推理，峰值 6 核。8 核以下机器会和 OBS 编码抢核 —— **未在 4 核机器上实测** |
| 数值一致性 | 定点整数运算，跨平台/跨编译器结果一致（不依赖 float 舍入） |
| 仍然做不到的 | 掩码每 4 帧才更新，人脸快速移动时 ROI 会滞后最多 3 帧 —— 这是检测频率的固有限制，不是本次优化引入的 |

> 后续补充：加上 Sobel 边缘门控与混合多线程后，1080p 降到 **7.11 ms**
> （见 `C2_边缘门控.md`）。门控本身的开销被混合多线程抵消了。

## 7. 事实 vs 推测

**实测事实**（本机，可复现）：
- 上表所有毫秒数、加速比、SHA256、`roi=12.64%`、`mask=17413 px`
- ORT 对 320 输入报 `Expected: 640`
- cv2 在 320 下 1.86 ms / 640 下 9.34 ms

**未验证**：
- 4 核 / 6 核机器上的表现（线程数策略按 8 核调）
- 多人脸（3 张以上）时 ROI 面积膨胀后的性能
- **真实 OBS 录制场景下的端到端帧率** —— 本文所有数字都是**引擎层**的，
  不含插件层每帧的 `gs_stagesurface_map` 下载与 `gs_texture_set_image` 上传
  （1080p RGBA 各 8 MB）。

> ⚠️ **这笔没测的开销可能是本文结论的盲区**。三个成熟开源实现（lumina / wtnl-zhi /
> wuxiwuhen）**没有一个回读全帧**，它们用椭圆 mask 让磨皮全程留在 GPU 上。
> 如果实测下载开销确实有 3~6 ms，那么 CPU 路线的真实总开销是 9 ms 而不是 7.25 ms，
> GPU 方案的相对优势也随之从 2 倍变成十几倍。
> 已在插件里加了埋点（`BEAUTY_PROFILE=1` 开启，每 180 帧输出一行到 OBS 日志），
> 详见 `05_文档/开源参考仓库_对照与可复用清单.md` §3。
