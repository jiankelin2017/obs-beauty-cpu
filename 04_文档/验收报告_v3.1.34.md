## 二、硬伤 1：参照物里有一半不是 SDK

`ref_golden.dll` / `ref_golden.dll` 跑的**不是裸 SDK**，是本工程自己的
`LegacyEngine` 包装层（`golden_capture.cpp` → `LegacyEngine::process()`）。
这一层为绕开 SDK 缺陷，用 CPU 顶替过五项 —— 源码里写得很直白：

```cpp
// legacy_engine.cpp:1967
// 参考实现自带美白恒关：实测 color_level 是整帧提亮（人脸 11.25 /
// 背景 11.17 无差别，没人脸的照片也 96% 被改），没有任何参数能
// 把它限到人脸。美白改由 applyWhiten 按肤色掩码在 CPU 侧完成。
sehSetParamd(item, "color_level", 0.0);
```

同理 `red_level` 不下发（`:1935`）、`sharpen` 在磨皮 > 0 时不下发（`:1955`）、
`global_sharpen` 根本不是 SDK 参数（`:1950`）。

**后果**：拿包装层当参照时，美白 100 档只测到 **1.264**（应为 14.0）、
红润 **0.000**（应为 1.97）—— 因为包装层的 CPU 美白/红润要读**我们自己的皮肤掩码**，
而这条离线路径根本没产掩码，于是什么都不做。

**这不是产品问题，是参照坏了。** 真正的原生数据在 `native_native_*.json`
（`sdk_native.py` 用 `LEGACY_EXTRA_PARAMS_FILE` 把 panel 全置 0、只注入被测参数，
绕开包装层的全部 CPU 顶替）。换成原生参照后：

| 项 | 我方 | 原生 SDK | 偏差 | Δ亮度（我方 / 原生） |
|---|---|---|---|---|
| 美白 | 13.106 | 14.019 | −6.5% | +12.46 / +13.37（差 **0.91 灰阶**） |
| 红润 | 1.686 | 1.968 | −14.3% | **−2.38 / −2.35（差 0.03 灰阶）** |
| 清晰 | 5.667 | 6.163 | −8.0% | **+2.88 / +2.88（差 0.00）** |

红润和清晰的**亮度偏移逐灰阶重合**，美白的 Δ(R−G) 也重合（+0.87 / +0.77）。
`chg` 差 6~14% 是空间覆盖率的差别（原生 coverage 0.91~0.99，我们被掩码限住），
不是强度不够。**这三项是真对齐，不是「凑出来的」**。

## 三、硬伤 2：多帧共用进程，我方核带着上一帧的状态去渲染

`feat_matrix.py` 的两次调用**不对称**：

```python
# SDK 侧：每档都归还并重新申请槽位
gd.RefGoldenRun(..., resetSlot=1, ...)      # 干净

# 我方：没有任何复位
d.BeautyCoreRun(raw_in, raw_out, ...)       # 沿用上一帧的掩码 EMA / 时序滤波 / faces 滞回
```

跑 `--frames m00,m03,m06` 时，m03 是拿 m00 的掩码 EMA 打底渲染的，m06 又叠 m03。
真实直播里画面是连续的，EMA 是特性；但离线素材是三张**互不相关**的帧，
这样跑等于系统性给我方扣分。

| 项 | 三帧同进程 corr | 逐帧独立进程 corr | 差 |
|---|---|---|---|
| 五官立体 | 0.453 | **0.788** | +0.335 |
| 去黑眼圈 | 0.289 | **0.753** | +0.464 |
| 去法令纹 | 0.636 | **0.768** | +0.132 |
| 全局锐化 | 0.853 | **0.987** | +0.134 |
| 亮眼 | 0.110 | 0.256 | +0.146 |

### 4.3 脸内锐化 —— 设计差异，但有一个 UX 陷阱

面板 100 档、其余全 0 时：**我方 0.000，SDK 1.012**。

原因在 `beauty_core.cpp:1300`：

```cpp
// 脸内锐化以「磨皮开启」为前提，这一条与参考实现路线完全一致
const bool wantFaceDetail = (t > 0.0f) && (shFace > 0.0f);
```

我们的「锐化」是**回填**语义 —— 把磨皮削掉的高频补回来，磨皮为 0 时没有东西可补。
SDK 的 `sharpen` 是**独立锐化器**，与磨皮无关。

语义上我们的更自洽，但**用户把「磨皮」拉到 0、只拉「锐化」，画面毫无变化** ——
这是可感知的 UX 陷阱。三个选项：

| 方案 | 做法 | 代价 |
|---|---|---|
| A 维持现状 | 文档里写清「锐化需配合磨皮」 | 零风险，但用户会以为坏了 |
| B 磨皮为 0 时锐化走全局路径 | `wantGlobalDetail \|\| (shFace>0 && t<=0)` | 一行改动，但要重编 + 重装，直播中不可做 |
| C 面板上禁用 | 磨皮 = 0 时把「锐化」置灰 | 纯 UI，需重编面板 |

**本次不动**（直播中不能重装）。播完后建议做 B，代价最小且行为最接近 SDK。

### 4.4 亮眼 —— 信号太小，判不了

chg 0.098 vs 0.136，Δ亮度 +0.10 / +0.11 灰阶。SDK 满档只改 **0.11 灰阶**，
这在 8bit 里连 1 级都不到 —— corr 0.256 是噪声级的相关，不构成「位置错」的证据。

真要判定需要更高比特素材或人工放大眼白区域。**当前不建议为它改任何参数**：
0.14 灰阶的差距在直播画面上不可见，改参数只会引入过冲风险。

### 4.5 祛斑痘 —— 参照侧完全不动，判不了

SDK `delspot_level=1.0` 在这三帧上改动量 **0.000**（rmse 0.58，即我方动、它不动）。
我方 chg 0.163。

这批素材（m00/m03/m06）是正常皮肤、没有明显痘印，SDK 的祛斑需要检出斑点才动作。
**属于「素材不覆盖」，不是「我们错」**。要判定得用 `C16_合成阳性样本_痘印定量.md` 那套
合成痘印素材重跑。

### 4.6 五官立体 —— 已对齐，但结构仍是「椭圆拼贴」

chg 2.509 vs 2.433（**+3.1%**），corr 0.788，Δ亮度 +0.69 / +0.20。

`acc_3.1.34_threed.png` 第 4 格（差分）能直接看出我们的结构：
**额头椭圆 + 双眼两个斑 + 鼻梁竖条 + 下巴椭圆**，五个高斯块叠出来的。

SDK 是「铺满整脸的极低幅度明暗重塑」（README §5.1 实测：支撑像素 52,389、Δluma 仅 +0.19）。
两者**总量对得上、位置也对得上（0.788）**，但**过渡不像** —— 我们的块边界在侧光下可能显出椭圆轮廓。

这是「能对齐但不耐看」的典型。要根治得换成低频明暗场（导向滤波残差着色），
属结构性改造，**不建议在直播期动**。

**三条铁律**（踩过的坑，写进脚本注释了）：

1. **参照物必须声明**。`feat_matrix` 的 `chg_sdk` 列对美白/红润/锐化/全局锐化**不可用**，
   那四项包装层用 CPU 顶替过。要判定用 `sdk_native.py` / `cmp_native.py`。
2. **一次只跑一帧**。多帧共用进程会让我方核带着上一帧的掩码渲染，corr 被压低 0.1~0.46。
3. **`LEGACY_EXTRA_PARAMS_FILE` 不能只清空**。包装层在「参数没变」分支只对文件里的键重下发，
   清空不会复位。基线要显式写 `color_level=0`。
