## 2. 快速开始（可执行）

### 2.1 构建

```bat
:: 在 02_构建\ 下，默认仍输出到 build_output\
build_manual.bat        :: 编译 obs-beauty.dll（滤镜 / CoreEngine）
build-ui_320.bat        :: 编译 obs-beauty-ui.dll（面板，脚本内定义 /DBEAUTY_UI_CPU_EDITION=1）
```

**请用独立产物目录 `02_构建\build_<版本>\`，不要覆盖 `build_output\` 里的历史定稿 DLL**（当前版 `1.0.13.12`）。以下代码块沿用 `1.0.3.0` 时期的路径示例；施工时把 `build_<版本>` 与 `install_<版本>.bat` 换成 `BEAUTY_BUILD_STR` 的当前值，构建与打包脚本会自动跟随，见 `docs/guides/guide-build-installer.md` §2。

```bat
set BEAUTY_OUTDIR=D:\插件\OBS美颜源码\02_构建\build_1.0.3.0
build_manual.bat
build-ui_320.bat
```

工具链：MSVC 14.51.36231 + Windows SDK 10.0.26100.0 + `C:\Qt` + NSIS 3。
`vcvars64.bat` 在受限环境里因 `reg.exe` 被拦不可直接使用，需手工设置 `INCLUDE` / `LIB` / `PATH`（构建脚本内已硬编码探测逻辑）。
构建脚本按**内容探测**定位依赖目录（源码看 `obs-beauty.cpp`、SDK 看 `obs-studio-32.1.1\libobs`、验证目录看 `deps\runtime\include`），目录编号改动不会失效。

构建后自检：

```powershell
& python '02_构建\verify-ui-imports.py' '02_构建\build_1.0.3.0\obs-beauty-ui.dll'
```

### 2.2 打包

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "06_安装包\build_setup.ps1"
```

## 3. 架构与帧管线

> 本节合并自 `docs/archive/readme-entry-20261106.md`（`Deprecated`） §3、§7（旧仓库入口说明）。

```
OBS Studio 32.1.1
└─ 视频源 → 滤镜链 → obs-beauty.dll · obs_beauty_filter
   └─ CoreEngine（纯 CPU，运行时不加载任何第三方美颜 SDK）
      ├─ YuNet 人脸检测（ONNX Runtime）
      ├─ 肤色掩码 / 区域椭圆 / 5 关键点
      ├─ 保边平滑 + 高低频分离 + 细节回填
      ├─ 色调（美白 / 红润 / 清晰 / 全局锐化 / 脸内锐化）
      ├─ 五官局部（去法令纹 / 去黑眼圈 / 亮眼 / 祛斑痘 / 五官立体）
      └─ 位移场（瘦脸 / 大眼 / 下巴）

obs-beauty-ui.dll · 顶层菜单「美颜·CPU(&A)」（仅 CPU 宏开启时）
└─ 参数面板：遍历滤镜 obs_properties 动态生成，不持有参数副本 → 读写全走滤镜属性
```

帧管线：检测 → 肤色掩码 → 磨皮 → 色调 → 锐化 → 五官局部 → 美形（管线最末端）→ 输出。
全 0 参数时逐字节透传，不进引擎。14 项功能分五页：美颜 / 锐化 / 五官 / 美形 / 高级。

> **色调整帧口径（`1.0.2.0` 起）**：清晰 / 美白 / 红润三段是纯颜色表，改成**整帧施加、
> 不乘皮肤掩码**（`BEAUTY_TONE_GLOBAL=1`，与 GPU 版同口径）；磨皮 / 锐化 / 五官仍只在
> 皮肤掩码内。这一层改的是「手遮脸时手背上出现一块美白」的成因，见 `docs/CHANGELOG.md` §2。

> **性能口径（`1.0.13.0` 真机实测，同会话配对）**：1080p30、ROI≈480×305（约 147k 像素）
> 分项 = 下载 2.07 + 检测掩码 0.67 + 磨皮 **2.72** + 色调 **0.46** + 细节 0.77 +
> 美形/alpha 0.86 + 上传 0.62 ≈ **8.34 ms/帧**（S 组 24 个干净窗口的中位）。
> 占 30 fps 预算（33.3 ms）的 **25%**、60 fps 预算（16.7 ms）的 **50%**。
>
> **跨会话的绝对数一律不可比。** 同日 13:13 用同一份盒式代码测出的是磨皮 6.12 / 引擎
> 10.62，13:44 只有 3.12 / 5.97：逐段比值显示所有多线程段齐降约 1.8 倍，而唯一的
> 单线程段（人脸检测 0.72 → 0.75）纹丝不动 —— 是当时有后台进程抢核，不是代码也不是
> 降频。**因此早期那些 `13.25`、`12.07`、`−1.40` 的读数不再引用**，真机结论只认
> 「同一坐姿、同一会话、交替跑」的配对数据（`live_matrix.py` 已固定跑 S/F 两组）。
>
> 优化分五步走完，每步都可逐字节验证：
>
> | 版本 | 做法 | 效果 |
> |---|---|---|
> | `1.0.8.0` | 磨皮盒式并行粒度按块宽算、ROI 外拷贝并行、A 通道搬进引擎 | 磨皮 −2.5 ms |
> | `1.0.11.0` | 色调整数复合表（整帧模式下清晰→美白→红润对整数输入是纯函数） | 色调 4.56 → 0.84，**全链 −4.88（−27%）** |
> | `1.0.12.0` | A 通道并进色调写的 32 位存；`detailRefill` 跳过用不到的 7×7 中频盒式 | 台架 −1.69（−10.5%），真机按 ROI 对齐 −1.40（同会话口径存疑，见上） |
> | `1.0.13.0` | 磨皮盒式的水平趟三通道融合、垂直趟 SSE 一次 4 列（改的是 `surface3RgbBand` 走的 `bandBoxH/V`） | 台架全开 **−2.83（−18.7%）**；真机同会话 **磨皮 −0.40（−12.8%）、引擎 −0.37** |
>
> **`BEAUTY_ZERO_COPY=1`（下载零拷贝）已实测证伪**：下载段确实省 0.58 ms，但引擎
> +0.41、上传 +0.19，合计反而慢 0.28 —— 映射内存是写合并/非缓存的，而引擎在四个
> pass 里反复读同一片输入。**默认保持关**，代码留作开关（换驱动/GPU 后可能不同）。
>
> **统计口径（踩过的坑，别重复）**：跨录制比引擎耗时**必须先按 ROI 面积对齐** —— 磨皮几乎
> 完全由 ROI 决定，同一配置下 ROI 从 297×270 涨到 561×291，磨皮就从 5.63 涨到 9.77。
> 另外只统计「无脸跳过 = 0」的窗口：早期返回的帧不累加分段计时、分母却是全部帧数，
> 无脸窗口会把每一段同比拉低。**`1.0.7.0` 那条 10.41 ms 的旧基线是场景差异造成的，
> 已作废**（原日志被 OBS 轮转删除，无法复查）；1.0.10.0 的 H 组（= 1.0.7.0 配置）实测 19.02 ms。
> 第三个坑是**抢核**：录制前必须确认没有台架/编译在后台跑（超时的前台命令会被自动转后台
> 继续跑），特征是「所有多线程段一起变慢 1.8 倍、单线程的人脸检测不变」。判据看
> **下载段**：它和引擎无关，两组下载打平才说明两组在同一状态下。
>
> 详见 `docs/design/design-cpu-performance.md` §2.7~§2.10 / §3.0 / §3.0b。

> **脖子口径（`1.0.7.0` 起）**：脖子通道的几何参数化到「立正方向」——`u` 沿画面正下方、
> `v` 为横向，方向向量由 `BEAUTY_INPUT_ROT` / 自动探测给出的 `g_effRot` 决定。
> ≤`1.0.5.0` 一律按源坐标 `+y` 往下画，源要转 90/270° 时那条带子是**横向**的
> （横穿肩膀落到背景上，真正的脖子没磨）；`1.0.6.0` 在旋转源上整段不画（止血）。
> `BEAUTY_NECK=0` 可无条件关掉脖子通道。取证见 `05_验证/ab20261109_neck_dir.md`。

> **头歪口径（`1.0.5.0` 起）**：YuNet 对平面内倾斜的召回边界在 30~40°，45° 歪头时
> 要么一个框都出不来，要么给一个「score 0.76 / 双眼间距只有框宽 28%」的敷衍框。
> 1.0.5.0 在连续 8 次「无脸或框不像人脸」后试 ±45°，命中就记住倾角（`FaceBox.roll`），
> 掩码按**倾斜矩形**画而不是外接盒（45° 时外接盒面积是脸的 2.8 倍）。
> `BEAUTY_AUTO_ROLL=0` 整段关闭，逐字节回到 `1.0.4.0`；`BEAUTY_AUTO_ROLL_MISS` 调阈值（2~600）。
> 取证见 `05_验证/ab20261109_head_roll.md`。
> **真机已验证**（2026-11-09 上午，装机路径 + `UGREEN 35867`）：录制第 17.6 s 自动命中
> `+45°（score=0.871）`，之后 `无脸跳过` 全程 0，回正自动恢复，150 s 录制零丢帧。
> 取证见 `05_验证/ab20261109_install_and_live.md`。
> 同一轮验证发现一个**独立的旧缺陷**（尚未修）：源被转 90/270° 时脖子通道仍按源坐标
> `+y` 往下画，立正画面里变成横向一条 —— 正立帧有 27.9% 的掩码落在脸框之外
> （脖子没磨、窗帘和肩膀被磨）。见 `docs/design/design-head-roll.md` §5。

> **输入方向口径（`1.0.3.0` 起）**：OBS 场景项的旋转只作用于显示合成，滤镜拿到的仍是原始帧。
> 连续检不到脸时引擎会自动试探 90°/270°，命中后按该方向检测并把几何反变换回源坐标
> （`BEAUTY_AUTO_ROT`，默认开；已知方向可用 `BEAUTY_INPUT_ROT=90/270` 手工声明）。
> 这一层改的是「竖屏摄像头美颜完全没有效果」的成因，见 `docs/CHANGELOG.md` §2。

**「纯 CPU」的准确口径（2026-11-06 确认）**：
`obs-beauty.cpp` 中的 `gs_texrender` / `gs_texture_*` / `gs_draw_sprite` 是 **OBS 滤镜框架唯一的帧 I/O 通道**
（源帧 → map 到 CPU `buf_in` → CPU 计算 → 回写 `buf_out` → 画回），不是 GPU 计算。
验收标准是「**不引入自定义 shader / hlsl / GPU 计算管线，美颜算法全部在 CPU buffer 上完成**」，
而非字面上的「无任何图形 API 调用」。`01_源码` 中无 `gs_effect_create*`、无 hlsl / effect 资产，
唯一相关的是 OBS 内置 `OBS_EFFECT_DEFAULT`。
